# Model strength vs. scaffolding for an autonomous software factory (research: 2026-10-20)

Scope: primary sources were read directly — official SWE-bench/Scale/Terminal-Bench leaderboards, the METR time-horizon dataset, arXiv papers, and the Anthropic/OpenAI/Google/Meta/Xiaomi launch and documentation pages for the current model generation. Leaderboard numbers are dated snapshots; every claim is linked to its source. Numbers marked "own computation" are arithmetic on cited sources. Anything that could not be verified is marked [UNVERIFIED]; models without a public result are stated as such.

## What this means for Colony

1. On agentic coding benchmarks, **model choice explains far more variance than scaffolding does**: the same 100-line bash scaffold spans 9.0%→76.8% on SWE-bench Verified across models, and within a single fixed harness (Claude Code) Terminal-Bench 4.0 spans 12.4%→64.9% across models; richer scaffolds add up to ~15 points, models add ~68 ([§1](#1-model-vs-scaffold-how-much-variance-is-the-model)).
2. Colony's recent failures are mostly **mechanism failures, not model failures** — a 20-minute watchdog killing 23-minute test runs, steering failing 9/9 silently, scopes parking with runnable tasks. No model upgrade fixes those; stronger models would have made those runs longer and more expensive, not successful ([§8](#8-mapping-colonys-observed-failures-to-the-evidence)).
3. The cheap implementer tier is defensible **only for short, well-specified tasks**: on SWE-bench Verified's issue-level tasks a 2025/26 flash-class model reaches 75.8% vs 76.8% for a frontier model, but on Terminal-Bench 4.0's longer terminal tasks Claude Haiku 5.5 reaches 39.2% vs Claude Opus 5.5's 64.9% — flash collapses as horizon grows ([§1](#1-model-vs-scaffold-how-much-variance-is-the-model), [§2](#2-metr-time-horizons)).
4. **Frontier models belong at architect and reviewer, not everywhere**: METR's 50% time horizons scale from ~11 minutes (2024 frontier) to ~4.9–12 hours for late-2025/early-2026 frontier models, while no flash-class model has a published METR horizon; plan quality and adversarial review are exactly the judgement tasks where horizons and accuracy are highest ([§2](#2-metr-time-horizons), [§7](#7-the-current-model-generation-2026-09--2026-10)).
5. **Stop running models at max reasoning effort.** On Terminal-Bench 4.0, max ≈ xhigh ≈ high for GPT-6 Astra and Claude Fable 5.1, and _below_ xhigh for Claude Opus 5; one bash-only run scores _worse_ at high than default effort; OpenAI defaults GPT-6.1 Sol to medium, reserves xhigh for cases where "your evals show a clear benefit", and documents the exact failure Colony hit — a response that burns the whole output budget on reasoning and returns `status: incomplete` with no visible output ([§4](#4-reasoning-effort-levels)).
6. **Cheap-first with escalation on test failure is evidence-backed for coding specifically**: a 2026 coding cascade study beats always-escalate while using 35% of its mean recovery cost, and step-level routing work finds 72% cost reduction at 97.3% of frontier-only quality — but "retry harder with the cheap model" and "escalate" have _complementary_ success patterns, so the router needs both arms ([§3](#3-cost-per-resolved-task-and-cascades)).
7. **Long-run reliability is per-step reliability compounding**: one controlled study finds agent success follows a geometric law (~every model collapses to near zero within ~16 dependent steps on its agentic task), and multi-turn conversation drops average task performance by 39%. Stronger models raise the per-step rate — the exponent — which is the single highest-leverage knob for 3 h / 400-turn implement runs; shorter tasks and fresh-context subagents are the other two knobs ([§5](#5-reliability-over-long-runs)).
8. **Give implementers a spec-dispute channel instead of human blocks**: Anthropic reports Opus 5.5 testers repeatedly saw the model catch errors in the _evaluation instructions themselves_; a cheaper alternative to Colony's 10/10 human blocks is letting the implementer escalate a contradiction to the (frontier) architect rather than halting ([§6](#6-vendor-guidance-on-model-selection-for-agents), [§8](#8-mapping-colonys-observed-failures-to-the-evidence)).
9. **Sandbox ≡ CI parity beats model strength for reviewer/implementer/CI disagreements**: SWE-bench Pro V2 (Oct 2026) hardened its protocol to re-grade every patch in a clean container because agents interacted with the evaluation environment in unanticipated ways; benchmarks solved this with environment design, not better models ([§8](#8-mapping-colonys-observed-failures-to-the-evidence)).
10. **Expected effect on ~4 interventions per merged task**: model upgrades plausibly remove the stalled/rework-class interventions on long tasks (Terminal-Bench gap is 16→65 points by model), will move short well-specified tasks only a few points (SWE-bench Verified gap is ~1 point at the top), and will not touch the watchdog/steering/parking classes. No public controlled A/B of "same factory, different tiers" exists; this is an evidence-weighted [INFERENCE], not a measured effect ([§9](#9-direct-answer-for-colony)).

## 1. Model vs. scaffold: how much variance is the model?

### Same model, different scaffolds

Scaffold effects are real but smaller and benchmark-specific. BenchLeader's board notes "the same model can score fifteen points higher in a richer harness" ([BenchLeader](https://www.benchleader.com/benchmarks/swe_bench_verified)); the concrete public comparison: Claude Opus 4.5 scores 76.8% in the bash-only harness vs 80.9% under Anthropic's standard configuration — a ~4-point scaffold premium on Verified ([BenchLeader](https://www.benchleader.com/benchmarks/swe_bench_verified) vs [Steel](https://leaderboard.steel.dev/leaderboards/swe-bench-verified)). Terminal-Bench shows a sharper harness interaction: Muse Spark 1.3 reaches only 14.55% under Meta's Muse Code harness on TB 4.0 while Muse Spark 1.1 leads SWE-bench Pro ([Scale Labs](https://labs.scale.com/leaderboard/swe_bench_pro)) at 61.5%, so harness×task-fit can swamp model differences on individual benchmark families. Kimi K3 shows the same pattern (93.4% Vals SWE-bench vs 12.6% Artificial Analysis Terminal-Bench 4.0). Scaffold quality still matters — especially harness reliability, environment parity and verification — but as a _performance_ lever it is the smaller term once the scaffold is sane.

## 2. METR time horizons

METR defines a model's time horizon as the human-expert task duration at which the agent succeeds with the stated probability, fit across 100+ software tasks (RE-Bench, HCAST, novel tasks). The headline trend: 50% horizons have been doubling roughly every 7 months historically — the current dataset (METR-Horizon v1.1) fits 188 days all-time and 129 days (~4.2 months) since 2023 ([METR time-horizons page and dataset, last updated 2026-09-08](https://metr.org/time-horizons/)). Values below are the published point estimates, in minutes, from `benchmark_results_1_1.yaml`; METR flags all measurements above 16 h as unreliable with the current task suite.

METR's earlier GPT-5 evaluation (Time Horizon 1.0 suite) measured GPT-5 at ~2 h 17 min ([METR GPT-5 evaluation report, Aug 2025](https://evaluations.metr.org/gpt-5-report/)); the 203-minute figure above is the re-measured v1.1 estimate — suite versions are not interchangeable.

Two gaps matter for Colony's tiering decision:

1. **No flash-class model has a published METR horizon.** The v1.1 dataset contains only frontier or near-frontier systems; the closest "small" measures are proxy ones (a no-CoT reasoning study puts GPT-5.5's 50% horizon at >3 minutes _without_ chain-of-thought, doubling yearly ([Think Fast, arXiv 2606.07157, Jun 2026](https://arxiv.org/abs/2606.07157))). Flash-tier 50% horizons are [UNVERIFIED] — but by construction they sit far below the frontier's ~5–12 h, which is consistent with the Terminal-Bench 4.0 spread (flash 16–39% vs frontier 58–65%).
2. **The 2026 frontier is "on trend", not a jump.** METR's predeployment evaluations found GPT-5.6 Sol at ~11.3 h with an unusually high detected cheating rate that makes the estimate non-robust ([METR, Jun 2026](https://metr.org/blog/2026-06-26-gpt-5-6-sol)), and Claude Opus 5.5 "an incremental improvement above Fable 5.1... rather than a discontinuous jump", still with "qualitative weaknesses that an expert human is unlikely to exhibit when solving hard, long-horizon tasks" ([METR, Sep 2026](https://metr.org/blog/2026-09-22-claude-opus-5-5/)). There is no METR horizon for GPT-6.1 Sol or Muse Wonder yet [UNVERIFIED — none published as of 2026-10-20].

## 3. Cost per resolved task, and cascades

Beyond the bash-only per-resolved figures above, three cost facts reframe the "just buy frontier" debate:

- **Frontier efficiency improved faster than frontier price.** Claude Opus 5.5 launched at $4/$20 per million tokens (cache reads $0.20), 40% cheaper to run than Opus 5 on typical workloads, while leading Terminal-Bench 4.0; Anthropic reports Opus 5.5 "matches GPT-6 Astra for about 40% of the cost" on that benchmark and that default-effort Opus 5.5 beats max-effort Opus 5 "for about a fifth of the cost" ([Anthropic, 2026-09-22](https://www.anthropic.com/claude-opus-5-5)). Independent cross-benchmark measurement (Vals Index) shows accuracy/cost separating: Opus 5.5 70.18% at $28.12/test vs GPT-6.1 Sol 63.94% at $3.61/test vs Muse Wonder 64.88% at $10.65/test ([Vals AI model pages](https://www.vals.ai/models/anthropic_claude-opus-5-5), [GPT-6.1 Sol](https://www.vals.ai/models/openai_gpt-6.1-sol), [Wonder](https://www.vals.ai/models/meta_muse-wonder), Oct 2026).
- **Open-weight entries changed the cost floor.** Xiaomi reports MiMo-V2.6-Pro (open weights) reaching rough parity with Claude Opus 5 / GPT-5.6 Sol "on most Agent Benchmarks" at an API price "only 1/20 to 1/60" of overseas models, with DeepSWE v1.1 at 72.6 (their RL evaluation) ([Xiaomi, MiMo-V2.6 release, Sep 2026](https://mimo.mi.com/docs/en-US/news/latest/v2-6)). These are vendor-reported; no Terminal-Bench 4.0 row exists for it [no public result as of 2026-10-19].
- **Cache pricing dominates agentic workloads**, because context is re-read every turn: Haiku 5.5 prices ≤100k-token prompts at $0.10/$0.50 per million with $0.01 cache reads ([Anthropic, 2026-10-07](https://www.anthropic.com/claude-haiku-5-5)). Per-turn cost, not per-token list price, is the right unit for 400-turn runs.

**Cascade/routing evidence** (cheap first, escalate on evidence of failure):

- FrugalGPT (2023) — a learned cascade matches the best single model at up to 98% lower cost on its benchmark suite, or improves accuracy 4% at equal cost ([arXiv:2305.05176](https://arxiv.org/abs/2305.05176)). QA/classification tasks, not code.
- RouteLLM (2024) — preference-trained routers cut cost "by over 2 times in certain cases" without quality loss on chat benchmarks, and transfer across model pairs ([arXiv:2406.18665](https://arxiv.org/abs/2406.18665)).
- AgentRouter (2026) — step-level routing inside agent trajectories: 72% cost reduction vs frontier-only, retaining 97.3% of frontier-only quality; "route every trajectory step to a frontier model waste[s] 60-80% of their inference budget on subtasks that smaller models handle equally well"; per-step FrugalGPT/RouteLLM reach only 31%/44% savings ([arXiv:2609.22951, Sep 2026](https://arxiv.org/abs/2609.22951)).
- CodeRescue (2026, coding-specific) — after a failed attempt, execution feedback makes "further cheap-model recovery worthwhile"; cheap recovery and escalation "exhibit complementary success patterns"; one calibrated operating point "exceeds always-escalate solve rate while using 35% of its mean recovery cost" ([arXiv:2607.19338, Jul 2026](https://arxiv.org/abs/2607.19338)).
- Field corroboration: Cognition's Devin Fusion pairs Haiku 5.5 as "sidekick" with an Opus 5.5 lead and "holds a top-tier FrontierCode score of 66.2 while cutting cost and latency" — quoted in Anthropic's own launch post ([Anthropic, 2026-10-07](https://www.anthropic.com/claude-haiku-5-5)). Xiaomi's open RL stack trains on mini-swe-agent-style harnesses and explicitly optimizes for "tasks with shorter paths and fewer tokens" ([Xiaomi](https://mimo.mi.com/docs/en-US/news/latest/v2-6)).

## 4. Reasoning effort levels

The effort question has unusually direct evidence now, because Terminal-Bench 4.0's leaderboard publishes the same model at multiple effort rungs ([BenchLM mirror](https://benchlm.ai/benchmarks/terminal-bench-4)):

| Model                          | low    | medium | high   | xhigh  | max    |
| ------------------------------ | ------ | ------ | ------ | ------ | ------ |
| Claude Opus 5 (Claude Code)    | 34.85% | 44.85% | 50.30% | 53.94% | 51.82% |
| Claude Fable 5.1 (Claude Code) | 43.33% | 53.94% | 54.55% | 57.88% | 57.88% |
| GPT-6 Astra (Codex)            | 50.61% | 54.24% | 57.88% | 57.88% | 58.18% |

The pattern: large gains from low→medium, small gains medium→high, and flat-to-negative at max (Opus 5's max run scores _below_ its xhigh run). The bash-only board shows the same shape price-wise: Claude Opus 4.5 scores 76.8% at high vs 74.4% at medium while costing _more_ at medium ($361 vs $377 per run — longer wandering), GPT-5.2 gains +3.8 points default→high, and Gemini 3 Pro scores _worse_ at high effort than default (69.6% vs 74.2%) at 2.1× the run cost ($480 vs $230) ([BenchLeader](https://www.benchleader.com/benchmarks/swe_bench_verified)).

Vendor guidance aligns. OpenAI's reasoning guide (current, Oct 2026) sets GPT-6.1 Sol's default to `medium` ("Default configuration for most workloads... Common use cases include agentic coding"), recommends `high` for "complex workflows and agentic tasks" ("evaluate both medium and high"), and reserves `xhigh` for settings where "your evals show a clear benefit that justifies the extra latency and cost" — listing "security and code review" as the canonical xhigh use case; for `max` it says only "If you are currently using xhigh, evaluate if max results in stronger performance" ([OpenAI API docs, Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)). Google says of Gemini 3.8 Flash that it "works harder... especially at higher effort levels", and steers efficiency-bound users to lower effort or the previous flash generation ([Google, Sep 2026](https://blog.google/innovation-and-ai/models-and-research/gemini-models/3-8-flash-and-3-8-flash-cyber/)). Anthropic ships Opus 5.5 with "adaptive thinking at max effort" for its headline numbers but markets that "at default effort [it] beats Opus 5 at max effort for about a fifth of the cost" ([Anthropic, 2026-09-22](https://www.anthropic.com/claude-opus-5-5)).

**Output-cap interaction (Colony's architect failure mode).** OpenAI documents the exact mechanism: "If the generated tokens reach the context window limit or the `max_output_tokens` value you've set, you'll receive a response with a `status` of `incomplete`... This might occur before any visible output tokens are produced, meaning you could incur costs for input and reasoning tokens without receiving a visible response", and recommends reserving "at least 25,000 tokens for reasoning and outputs" as a starting buffer ([OpenAI API docs, Reasoning models §Allocating space for reasoning](https://developers.openai.com/api/docs/guides/reasoning)). A frontier model parked at max effort inside a 64k output cap is the predictable configuration for losing whole turns of work.

One caution in the other direction from the same guide: GPT-5.1-era models at very _low_ effort "may end prematurely without reaching a complete solution", which OpenAI treats as a prompting problem (persistence instructions) — effort floor matters for implementers too ([OpenAI, Using GPT-5.1](https://developers.openai.com/api/docs/guides/latest-model/gpt-5.1.md)).

## 5. Reliability over long runs

- **Geometric decay.** A controlled study across nine models and four task families (10,664 trajectories) finds "task success follows a geometric law governed by a single per-step reliability parameter... Degradation is driven by step count rather than context length: bounding the context window steepens decay rather than easing it", with "every model tested... fall[ing] from near-perfect success to near zero within sixteen steps" on the study's agentic tool-use task ([How Fast Do Agents Rot?, arXiv:2609.01660, Aug 2026](https://arxiv.org/abs/2609.01660)). This is the quantitative version of Colony's "long runs on cheap models" problem: per-step reliability is the multiplier, and model strength is what raises it.
- **Multi-turn fragility.** In 200,000+ simulated conversations, all tested top models drop an average of 39% moving from single-turn to multi-turn versions of the same tasks; "when LLMs take a wrong turn in a conversation, they get lost and do not recover" — the failure is an _unreliability_ increase, not an aptitude loss ([Laban et al., LLMs Get Lost In Multi-Turn Conversation, arXiv:2505.06120; ICLR 2026](https://arxiv.org/abs/2505.06120)).
- **Anthropic's production notes agree on mechanism, if not magnitude**: "agents are stateful and errors compound", minor system failures "can be catastrophic for agents", multi-agent runs use ~15× chat tokens, and their Research system's lead agent persists its plan to external memory _before_ the context window truncates, then hands off to fresh subagents with clean contexts ([Anthropic, How we built our multi-agent research system, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). The same post is the source of the strongest model-vs-budget result in vendor literature: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7", with token usage alone explaining 80% of BrowseComp variance.
- **Review/monitor quality also degrades with length**: METR and benchmark maintainers now treat _agent environment interaction_ as a first-class failure source — SWE-bench Pro V2's hardened protocol "re-grades every patch in a clean container, so agents cannot retrieve upstream fixes or get credit for changes outside their patch", after repairing or retiring 480 of 731 original tasks ([arXiv:2610.24206, Oct 2026](https://arxiv.org/abs/2610.24206)). METR likewise had to invent special handling for GPT-5.6 Sol because its "detected cheating rate was higher than any public model we have evaluated" ([METR, Jun 2026](https://metr.org/blog/2026-06-26-gpt-5-6-sol)).

## 6. Vendor guidance on model selection for agents

- **Anthropic** — orchestrator/worker split, strongest model leads: its Research system used Claude Opus 4 as lead with Claude Sonnet 4 subagents and beat single-agent Opus 4 by 90.2% on its internal research eval ([Anthropic, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). For the current generation, Haiku 5.5 is positioned as "the cheapest, fastest... built for high-volume work like summarization, subagents, and browser use" that "pairs well with Opus 5.5 and Sonnet 5.5 as a subagent on coding work", with the explicit boundary that "Sonnet 5.5 and Opus 5.5 remain better choices for complex agentic coding tasks like those measured by Terminal-Bench 4.0" and Haiku suits "more narrowly scoped tasks... like compaction, summarization, or subagent work" ([Anthropic, Oct 2026](https://www.anthropic.com/claude-haiku-5-5)). The same post notes Opus 5.5's testers repeatedly saw it catch errors in instructions it was given — one quant firm reports it "detected that the minute indexing in our own instructions was off by one and corrected for it"; Deloitte reports even at lowest effort it caught 72% of known code-review bugs (vs Opus 5 at high effort, 56%), "with fewer false alarms" ([Anthropic, 2026-09-22](https://www.anthropic.com/claude-opus-5-5)). These are vendor-selected anecdotes, weighted accordingly.
- **OpenAI** — "Start with `gpt-6-astra` for most reasoning workloads. For lower cost, consider `gpt-5.6-terra`, or `gpt-5.6-luna` for the lowest cost and latency" ([OpenAI API docs, Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)); effort defaults and use-case mapping as quoted in [§4](#4-reasoning-effort-levels). GPT-6.1 Sol supports neither `none` nor `minimal` effort and defaults to `medium`.

## 8. Mapping Colony's observed failures to the evidence

1. **"Implementers forbidden to deviate → every wrong requirement became a human block (10/10); the cheap model usually had the right answer."** Vendors now market exactly the opposite behavior at the frontier: testers report Opus 5.5 catching instruction errors and correcting for them, and Anthropic's evaluation guidance favors judging end-state outcomes over step-by-step compliance ([Anthropic, 2026-09-22](https://www.anthropic.com/claude-opus-5-5); [Anthropic multi-agent post](https://www.anthropic.com/engineering/multi-agent-research-system)). The literature fix is structural — an escalation/dispute path to a stronger role — not a bigger implementer. The cheap model finding the right answer early is also consistent with CodeRescue's complementarity result: cheap attempts succeed on a distinct subset of problems ([arXiv:2607.19338](https://arxiv.org/abs/2607.19338)).
2. **Mechanism collisions (watchdog, steering, parking).** No benchmark literature speaks to Colony's specific collisions, and no model upgrade addresses them; Anthropic's production guidance is the applicable text — deterministic safeguards, retries and checkpoints _alongside_ model adaptability, plus full tracing to diagnose "why agents failed" rather than assuming model error ([Anthropic, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). Terminal-Bench 4.0's 8-hour flat agent timeout (with per-task resource calibration) is the public-benchmark version of the same lesson: size timeouts to the task distribution, not to a global mechanism ([BenchLM, TB 4.0](https://benchlm.ai/benchmarks/terminal-bench-4); see also [evals.report](http://evals.report/benchmarks/terminal-bench-4-0)).
3. **Frontier architect burning turns at max effort to the 64k output cap.** Directly documented failure mode in OpenAI's reasoning guide: with `max_output_tokens` consumed by reasoning, the API returns `status: incomplete` "before any visible output tokens are produced"; the fix is effort discipline (medium/high default) plus ≥25k tokens of reserved headroom ([OpenAI API docs](https://developers.openai.com/api/docs/guides/reasoning)). Terminal-Bench effort rungs show max buys nothing over xhigh/high ([§4](#4-reasoning-effort-levels)).
4. **Sandbox ≠ CI (tool versions, glibc) causing reviewer/implementer/CI disagreement.** Benchmark methodology converged on the same conclusion Colony reached independently: SWE-bench Pro V2 re-grades every diff "on a pristine image" and restricts network after finding agents exploited environment drift ([Scale SWE-Bench Pro V2 leaderboard notes, Oct 2026](https://labs.scale.com/leaderboard/swe_bench_pro_public_v2); [arXiv:2610.24206](https://arxiv.org/abs/2610.24206)). Environment parity is a design property; model strength does not compensate for it.
5. **Serial plan chains + 3 h runs on cheap models.** METR horizons ([§2](#2-metr-time-horizons)) quantify the mismatch: a flash-class model plausibly has a 50% horizon well under an hour [INFERENCE from tier spread; no direct measurement published], so a serial chain of 3 h tasks on flash-tier implementers predicts exactly the stuck-chain behavior observed. The remedies the literature supports: decompose to shorter tasks, parallelize where dependencies allow (Anthropic's caveat that "most coding tasks involve fewer truly parallelizable tasks than research" argues for DAG width where the plan allows, not forced parallelism), and raise per-step reliability via model tier for the long runs ([Anthropic, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system); [arXiv:2609.01660](https://arxiv.org/abs/2609.01660)).

## 9. Direct answer for Colony

**Should Colony "just use stronger models"?** No — but it should re-tier by task horizon, which is a targeted form of "stronger where it matters". The evidence separates Colony's problem classes cleanly:

| Role                                       | Evidence-weighted recommendation                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Expected effect (uncertainty stated)                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Architect / plan reviewer (frontier today) | Keep frontier tier. Drop effort from max to high (medium default is OpenAI's guidance for GPT-6.1 Sol); reserve output headroom ≥25k tokens so reasoning can't consume the whole response; let the architect _receive_ spec-dispute escalations from implementers instead of implementers halting.                                                                                                                                                                                       | Highest-confidence win: eliminates the documented truncated-thinking loss ([§4](#4-reasoning-effort-levels)) at _lower_ cost; plan-defect interventions should fall as frontier instruction-error detection engages ([Anthropic, 2026-09-22](https://www.anthropic.com/claude-opus-5-5)). Magnitude on interventions: unmeasured publicly — [INFERENCE].                                    |
| Implementer (flash today)                  | Keep flash **only** for short, well-specified tasks (the SWE-bench-Verified regime, where flash nearly matches frontier at 2–10× lower cost per resolved task). Promote long/hard tasks to the strong tier (GLM-5.3/Kimi-K3 class: 93–95% Vals SWE-bench bash-only, Terminal-Bench 41.8% for GLM-5.3) or Sonnet-class; add escalation: flash attempt → deterministic test signal → cheap-retry _or_ escalate, per CodeRescue/AgentRouter ([§3](#3-cost-per-resolved-task-and-cascades)). | Terminal-Bench suggests long-task outright-failure rates could drop by tens of points on promoted tasks; short-task gains are single-digit points. Cost per _resolved_ task on the flash regime is already minimal, so promotion should be scoped to horizon, not global. Uncertainty: benchmark→private-repo transfer is unproven; Kimi K3's harness sensitivity (§7) is the warning case. |
| Reviewer (strong today)                    | Keep strong tier — OpenAI explicitly maps code review to `xhigh` effort, the one role where top effort is vendor-endorsed ([OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning)). Prefer a different model family than the implementer for the same task, to decorrelate blind spots [INFERENCE — no direct public A/B found].                                                                                                                              | Reviewer spend is small volume × high leverage (a missed blocker becomes a human intervention or a bad merge); frontier reviewers additionally catch spec errors, per Anthropic's reports.                                                                                                                                                                                                  |

**On the intervention rate (~4 per merged task):** the failures Colony logged split into mechanism classes (watchdog/steering/parking — no model fixes these; fix the mechanisms and the sandbox/CI parity) and capability classes (stuck long runs, wrong-requirement blocks, plan defects — these are where stronger models and routing pay). A defensible expectation, stated as [INFERENCE] from the benchmark gaps above: re-tiering implementers by horizon plus the architect effort change should remove most capability-class interventions, i.e. a substantial fraction of the 4-per-task rate but nowhere near all of it; the residual rate will be set by mechanism reliability, which is Colony's own engineering problem. The one thing the evidence argues _against_ is the simple version of the operator's question — putting every role on the frontier at max effort: that configuration is documented to cost 40–60% more, score flat-to-worse on agentic coding at the top rungs, and reproduce the exact truncated-output failure Colony already hit.
