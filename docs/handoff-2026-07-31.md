# Handoff — 2026-07-31: Colony running unattended on Aether

Session goal: make Colony actually autonomous, deploy it to Aether as prod, and
run a real build scope end to end. Eleven defects were found by running it; nine
are fixed and deployed. Two remain, and the first one is the whole ballgame.

Read this top to bottom, then start at **"Start here"**.

## TL;DR

- Colony is deployed and healthy on Aether (`colony-dev`) at commit `ce7d5da`,
  running the **real** Pi agent runtime (it was silently running the _fake_
  runtime in production before this session).
- **YOLO mode is ON in prod** (`hitl.mode: yolo`). The supervisor auto-passes
  human gates when the bot evidence exists.
- Unattended, with zero human input, Colony now does:
  architect → decomposition review → auto-approve → commit DAG → project task
  issues → merge spec MR → per-task plan → plan review → code → open MR →
  code review → (rework loop on `changes_requested`).
- **No task MR has ever merged.** On a clean run the reviewer approves and
  writes its audit row, but **no gate, review, approval, or pipeline-mirror row
  is persisted at all**, so `checkMrGate` returns `no_open_gate` forever. This
  is a regression introduced during this session. See **"The open bug"**.

## Start here

1. Read **"The open bug"**. It is well-bounded and it is the only thing between
   the current state and a merged task. Everything else below is context.
2. Reproduce with a fresh scope (**"Running a scope"**) — takes ~10 minutes to

3. Fix, gate (`npx tsc --noEmit -p tsconfig.json`, `npm run lint`,

4. **Before deploying, read "Temporal versioning" — a workflow-code change
   wedges every in-flight scope.** Terminate running supervisors first, or the

5. Watch a fresh scope go task → merged → closed. That closes the deliverable.

## The open bug — gate/review records are never persisted

### Evidence (clean run, prod scope `col-v223fb9d`, GitLab project 212)

All fixes from this session were deployed; the workflow was brand new, so no
replay wedge and no stale caches were involved.

```
GitLab pipeline 3741   success at faf30038
GitLab MR !2           head faf30038, detailed_merge_status: mergeable
audit_log              12:33:43  review.approved | reviewer_envelope_approved

gates      for task -> 0 rows
reviews    for task -> 0 rows
approvals  for task -> 0 rows
provider_mirrors entity_kind='pipeline' -> 0 rows
```

The reviewer ran, approved, minted and revoked its token, and wrote
`review.approved` to the audit log — but none of the gate state that
`checkMrGate` reads was written. With no gate row it returns
`{checked: false, reason: "no_open_gate"}` and the task sits in
`review_requested` indefinitely. Task 1 held there for 40+ minutes with tasks
2 and 3 `ready` behind it (the supervisor drives one task at a time).

### Why this is a regression, not longstanding

The earlier scope `col-final5e2c` **did** persist these rows — it has
`gate.open | task_in_review_requested` at 07:51:29, a review row, and three
approvals. That scope ran its review phase on the pre-session worker. The
later clean run on current code persists none of them. Something in this
session's changes to the reviewer/gate path stopped the writes while leaving
the audit trail intact, which is exactly why it looked healthy for hours.

### Where to look

- `apps/worker/src/gate-evaluation.ts` — `createOpenMrGate` (upserts the
  artifact, creates the gate, writes `gate.open`). Confirm it is still called
  when a task enters `review_requested`, and that its result is not being
  discarded.
- `packages/workflows/src/index.ts` — the `openMrGate` call site. It was
  changed this session to stop ignoring the result; verify the new branch
  doesn't skip the call, and that `driveClaimedTask` still reaches it on the
  YOLO path.
- `apps/worker/src/reviewer-run.ts` — heavily edited this session (outcome
  fields, MR/diff failure handling, `agent_runs` persistence). The review row
  is written via `deps.reviewGate`; check an early return doesn't bypass it.
- `apps/worker/src/activities.ts` `recordPipelineStatus` — the missing pipeline
  mirror suggests this never ran for this task, so also confirm pipeline events
  are still reaching it (the dispatcher returns 200, so ingestion is fine).

Fastest triage: add a failing test that drives a task to `review_requested` and
asserts a gate row exists. The DB-gated worker integration tests
(`apps/worker/src/phase2-flow.test.ts`) already have the fixtures for this.

## Temporal versioning — read before deploying

Colony has **no Temporal workflow versioning**, so any change to
`packages/workflows/src/index.ts` breaks replay for in-flight executions:

```
[TMPRL1100] Nondeterminism error: Activity type of scheduled event
'checkProviderHealth' does not match activity type of activity command
'readScopeState'
```

That is a real failure from this session (`supervisor-col-final5e2c`, event
1989). The workflow stays `Running` but its history freezes and it never
progresses again; `supervisor-col-run3ac5c` went to `Failed` outright. I lost
several hours testing three fixes against workflows that had stopped executing
before the fixes could run.

Until this is fixed, **terminate running supervisors before deploying workflow
changes**, and validate on a fresh scope. The durable fix is Temporal's
`patched()` / `deprecatePatch` API or Build-ID-based worker versioning.

```sh
kubectl port-forward -n temporal svc/temporal-server 7233:7233 &
temporal workflow list --query "WorkflowType='scopeSupervisorWorkflow'"
temporal workflow show --workflow-id supervisor-<scope>   # look for WorkflowTaskFailed
temporal workflow terminate --workflow-id supervisor-<scope> --reason "workflow code change"
```

## Fixed, but keep the reasoning — stale `head_commit_sha`

This was diagnosed as the blocker mid-session and **fixed** in `ce7d5da`. It
turned out not to be what was holding `col-final5e2c` (that scope was wedged by
the Temporal replay failure above), but the defect was real and the reasoning
generalises, so it is kept here.

### Evidence (prod scope `col-final5e2c`, GitLab project 211)

```
MR mirror head_commit_sha : f88aa1d0   <- what Colony thought the head was
actual GitLab MR !2 head  : cfe4de6c
pipeline mirrors for task : f88aa1d0 = failed
                            cfe4de6c = success
```

Both pipelines were ingested correctly and the MR was `mergeable`.

### Cause

`apps/worker/src/developer-run.ts:466-478` writes the `mr_pr` mirror with
`head_commit_sha` at the moment the developer opens/updates the MR. **Nothing
ever updates it again.** When any later commit lands on the branch — a rework
push, a CI fix, anything — the recorded head goes stale.

Everything head-bound then evaluates the wrong commit:

- `apps/worker/src/gate-evaluation.ts` `checkMrGate` derives
  `head_commit_sha` from the MR mirror (`mirrorHeadCommitSha`, ~line 555-570),
  then selects the pipeline matching it and compares approval SHAs to it.
- Approval staleness (`evaluateMrGate`, ~line 397) invalidates approvals whose
  `commit_sha` differs from that stale head.
- Re-review eligibility (`isReReviewEligible`, ~line 467) requires a
  `success` pipeline at that stale head.

Note: commit `3a92a96` fixed a _related but different_ bug — `checkMrGate` used
to read an arbitrary pipeline mirror (`listMirrorsForColony(...)[0]`) instead of
the one matching the head. That fix is correct and deployed, but it matches
against the stale head, so it selects the stale failed pipeline. Necessary, not
sufficient.

### How it was fixed (`ce7d5da`)

`checkMrGate` now reads the head from the provider when a `providerAdapter` is
supplied on `GateDependencies` and treats the mirror as a cache, falling back to
the cached value when the adapter is absent or the provider read fails. The
adapter is optional so existing construction sites are unaffected.

Still worth doing, and cheaper at scale: refresh the mirror's
`head_commit_sha` from the `merge_request_hooks` webhook the dispatcher already
receives, so the gate doesn't need a provider call per evaluation.

The invariant to preserve if you touch this: **stale approvals must stay
invalid.** The bug was that Colony compared against the wrong head, not that it
compared at all. Do not "fix" anything here by relaxing the SHA check.

## Deploying

CI builds five images then parks on a **manual** `apply` job.

```sh
# after pushing to main, find the pipeline
glab api projects/49/pipelines?ref=main | jq '.[0]'
# play the apply job once builds are green
glab api --method POST projects/49/jobs/<apply-job-id>/play
```

Local apply is also possible and much faster when images already exist:

```sh
cd tofu
export VAULT_ADDR=https://bao.home.shdr.ch VAULT_TOKEN=$(cat ~/.colony-toolbox/bao/token)
tofu init -reconfigure -backend-config="username=<user>" -backend-config="password=<PAT>"
tofu apply -var image_tag=<sha> -var enforce_pinned_images=true
```

Two CI gotchas seen repeatedly: the k8s runner hits `exceeded quota:
requests.cpu` when pipelines overlap (just retry the job), and a worker
rollout kills any in-flight agent activity — check `agent_runs` for a
`RUNNING` row before applying.

## Running a scope

The target project needs: Auto DevOps **off** (its buildpack pipeline needs a
Docker daemon the runner lacks, so it fails permanently and the merge gate can
never open), a working `.gitlab-ci.yml` on `main`, and a webhook to
`https://colony-webhook-dev.home.shdr.ch/webhook/gitlab` with the
`GITLAB_WEBHOOK_SECRET` from bao.

The CI baseline matters more than it looks. A Colony DAG normally implements
code and tests as **separate tasks**, so an early task's branch legitimately has
no test files — and `vitest run` exits 1 on "No test files found", which turns
the pipeline red and deadlocks the gate. Only add `--passWithNoTests` if the
project's own test script hasn't already (passing it twice also fails). Working
baseline is on `main` of GitLab projects 210 and 211.

Then:

```sh
API=https://colony-api-dev.home.shdr.ch
H=(-H "X-Actor-Id: human:op-1" -H 'Content-Type: application/json')
curl -sX POST "$API/admin/provider/projects" "${H[@]}" \
  -d '{"provider":"gitlab","provider_id":"<id>","path":"<group/proj>","default_branch":"main"}'
curl -sX POST "$API/scopes" "${H[@]}" -d @scope.json          # id must match ^col-[a-z0-9]{4,}$
curl -sX POST "$API/scopes/<id>/decomposition-request" "${H[@]}" \
  -d '{"provider_targets":[{"provider_project_id":"<uuid>","role":"primary"}],"reason":"run"}'
```

`X-Actor-Id` is trusted with **no authentication** — see "Known gaps".

## Debugging playbook

`agent_runs` is now the fastest way to see what happened (this session added it):

```sh
kubectl exec -n colony-dev colony-postgres-0 -- psql -U colony -d colony -At -F' | ' -c \
 "SELECT role,status,COALESCE(task_id::text,scope_id::text),started_at::time(0),
         COALESCE(finished_at::time(0)::text,'RUNNING')
  FROM agent_runs ORDER BY started_at DESC LIMIT 10;"
```

Other high-value queries: `audit_log` filtered by `task_id` with
`action NOT LIKE 'event.%'`; `provider_mirrors` by `colony_id` (this is where
the open bug shows); `gates` / `reviews` / `approvals` for gate state.

Webhook delivery is visible from the GitLab side and tells you immediately
whether ingestion works:

```sh
glab api projects/<id>/hooks/<hook>/events | jq '.[]|"\(.created_at) \(.trigger) -> \(.response_status)"'
```

## Known gaps (not fixed, roughly by severity)

1. **Stale `head_commit_sha`** — the open bug above. Blocks all task merges.
2. **`gates` / `reviews` / `approvals` rows are sometimes absent** despite
   reviewer runs reporting success. Seen repeatedly; never explained. Worth a
   dedicated look — it may share a cause with (1).
3. **API trusts `X-Actor-Id` with no authentication.** Anyone who can reach the
   API can impersonate a human with `policy.override`.
4. **Circuit breaker can't be reset by an operator** — the scope override API
   only supports `cancel`. A tripped breaker clears only on a successful run.
5. **Three stranded scopes**: `col-tempodd7a`, `col-slug61f5`, `col-final5e2c`.
   Their workflows started before the projection/recovery fixes; Temporal
   resumed them past the startup sync, so they will not self-heal.
6. **Tool gateway boots with no deps** — always returns NOT_CONFIGURED.
7. **Policy fields are resolved but unenforced** (`packages/policy/src/evaluate.ts`
   ignores `always_human_review`, `review_loop_cap`, `protected_paths`).
8. **Agents run unsandboxed on the host**; sandbox profile is metadata only.
9. Freshness fields (`provider_event_ts`, `policy_version`) are hardcoded
   constants, weakening stale-envelope detection.

The full audit that found most of these is summarised in
`docs/research/dark-factory-2026-07-31.md` alongside the research.

## Aether incident (2026-07-31 ~06:00 UTC)

A node went NotReady and triggered a cluster-wide `TaintManagerEviction`.
Kyverno's **fail-closed** webhook became unreachable at the CNI layer
(`operation not permitted`), which blocked **all pod creation cluster-wide**,
including Temporal's CNPG database. Colony's worker crash-looped on
`no usable database connection`.

Recovery exposed a **circular deadlock** that could not self-heal:

```
affine pod init container "wait-for-litellm"
   -> waits on litellm Service (no endpoints)
   -> litellm pod held unready by affine-mcp-server sidecar
   -> that sidecar's /readyz 503s because affine is down
```

Broken by removing the sidecar's readiness probe so an unrelated MCP sidecar
can no longer take down the shared LLM gateway — committed in
`aether:tofu/home/kubernetes/litellm.tf` and applied live via `kubectl patch`.
**The live patch will be reverted by the next Aether tofu apply unless the
committed change is applied too.**

Two things Aether should consider: a fail-closed Kyverno webhook turns one bad
node into a cluster-wide outage, and colocating many MCP sidecars with LiteLLM
in one pod means any one of them can delist the gateway.

## Two mistakes I made — don't repeat them

1. I pushed `.gitlab-ci.yml` directly onto agent branches twice. That moves the
   MR head out from under Colony's recorded state; it correctly detected drift
   (`reconcile.stale_commit_approval` → `pending_sync`) and invalidated
   approvals. **Don't hand-push to a branch Colony is driving** — it looks like
   a Colony bug and isn't.
2. I iterated the CI baseline three times in prod instead of reasoning it
   through once. See "Running a scope" for the working version.
