# Lessons for Colony — Anthropic's agent-factory engineering (2024-12 → 2026-10)

Research compiled 2026-10-21. All sources are Anthropic first-party: engineering blog posts, one research post, official Claude Code docs, and the public repo of the C-compiler project. Colony problem references: **(1)** 46% of implement runs died to non-model causes; **(2)** big-task churn (11–13 implement runs, 3–6 review rounds, cold repairs); **(3)** no-deviation-from-spec rule turning impossible requirements into human blocks (since changed); **(4)** hand-built reliability mechanisms colliding and failing silently; **(5)** agent sandbox differs from CI. Design decisions under consideration: run agents on daimyo (durable journaled sessions), one writer owning each leaf through review/CI, small leaves, planners that can add leaves at runtime.

## 1. Lessons for Colony

1. **The verifier is the product: invest in the test oracle before the orchestrator, because agents will optimize whatever you measure — including the wrong thing.** Carlini spent most of his effort on "the tests, the environment, the feedback" rather than scaffolding: "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem"; when agents began breaking existing functionality with each new feature late in the project, the fix was a CI pipeline with "stricter enforcement… so that new commits can't break existing code" (C compiler, 2026-02-05). Bears on **(2)** (review rounds are where Colony catches regressions today — move that signal into per-leaf CI the agent can run itself) and **(5)** (the oracle agents iterate against must be the same one CI enforces, or agents solve the wrong problem).

2. **Durability comes from a journaled session log plus a stateless, resumable harness — not from nursing containers or watchdog-killing hung ones.** Managed Agents decoupled session (append-only log: `emitEvent`/`getEvents`), harness (rebooted with `wake(sessionId)`, resumes from the last event), and sandbox (`execute(name, input) → string`, `provision({resources})`); a dead container is surfaced to the model as an ordinary tool-call error, and "we no longer had to nurse failed containers back to health" — p50 TTFT fell ~60%, p95 over 90% (Managed Agents, 2026-04-08). Bears on **(1)** (the five named categories — 129 colonyd restarts, 117 sandbox provisioning, 75 rate limits, 106 unclassified, 31 watchdog — account for 458 of the ~540 non-model run deaths) and directly validates the **daimyo decision** — daimyo's journaled tasks/sessions are the same architecture; Colony should delete its watchdog/restart machinery in favor of crash-resume.

3. **Parallelism only pays when work decomposes into truly independent units; one giant task means N agents rediscover the same bug and overwrite each other's fixes.** When the 16-agent C-compiler team moved to compiling the Linux kernel, "every agent would hit the same bug, fix that bug, and then overwrite each other's changes. Having 16 agents running didn't help"; the fix was a GCC-as-oracle differential harness (compile most files with GCC, vary Claude's subset) that turned one monolithic task into many per-file tasks (C compiler, 2026-02-05). The research team states the general rule: multi-agent excels at "heavy parallelization, information that exceeds single context windows" — and as of June 2025 "most coding tasks involve fewer truly parallelizable tasks than research" (Multi-agent research, 2025-06-13). Bears on Colony's **fixed up-front plan** (a serial chain of ≤20 tasks cannot parallelize) and **planners adding leaves at runtime** — runtime decomposition is exactly the mechanism that converts monolithic blockers into parallelizable leaves.

4. **Every harness mechanism encodes an assumption about what the model can't do; those assumptions go stale each model generation, so mechanisms must be re-audited and deleted — remove one at a time.** Context resets were added because Sonnet 4.5 "context anxiety" made agents wrap up early; on Opus 4.5 "the behavior was gone. The resets had become dead weight," and the sprint construct was removed entirely on Opus 4.6, which "ran coherently for over two hours without the sprint decomposition" (Harness design, 2026-03-24; Managed Agents, 2026-04-08). A radical all-at-once simplification attempt failed — "it became difficult to tell which pieces of the harness design were actually load-bearing" — so they moved to removing one component at a time. Bears on **(4)**: Colony's watchdogs, attempt budgets, review epochs, adoption, autosave, steering, and parking each encode a model/infra assumption; each needs a stated assumption and periodic ablation, or it will silently become dead weight that still fires.

5. **Handoffs between cold-started agents belong in durable artifacts (feature JSON, progress file, git history, init script), not in conversation summaries — compaction alone is not sufficient.** Even Opus 4.5 in a compaction loop failed at long builds: one-shotting the app and "running out of context in the middle of its implementation, leaving the next session to start with a feature half-implemented and undocumented," or later "declare the job done"; the fix was an initializer agent writing a 200+-item `feature_list.json` (all `"passes": false`; JSON chosen because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files"), a `claude-progress.txt`, an `init.sh`, and a per-session ritual: read progress + git log, start the server, smoke-test basic functionality _before_ starting new work (Effective harnesses, 2025-11-26). Bears on **(2)**: Colony's repair runs restart cold with only findings — give each repair the same structured handoff (progress journal, prior failed approaches, a fast smoke check) instead of raw review output, which daimyo sessions make natural.

6. **Separate the doer from the judge, but budget real operator effort to tune the judge — and only pay for the judge where the task exceeds what the model does reliably solo.** "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work"; "out of the box, Claude is a poor QA agent" that "identifie[d] legitimate issues, then talk[ed] itself into deciding they weren't a big deal and approve[d] the work anyway" — fixed by iterating on the evaluator prompt against human judgment over several rounds, calibrating with few-shot score breakdowns, and giving it Playwright to exercise the running app (Harness design, 2026-03-24). On Opus 4.6 the evaluator moved to a single end-of-run pass: "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." Bears on Colony's **adversarial strong-model reviewer**: the design is right, but expect to tune it against operator-labeled disagreements, give it execution tools (not just diffs), and consider scaling review depth by leaf size — which addresses **(2)**'s 3–6 review rounds on large tasks.

7. **Specify deliverables and acceptance criteria, not implementation paths — granular up-front specs cascade their errors, while negotiated "done" contracts catch misunderstanding before code is written.** The planner was deliberately constrained to "product context and high level technical design rather than detailed technical implementation," because "if the planner tried to specify granular technical details upfront and got something wrong, the errors in the spec would cascade into the downstream implementation"; before each sprint, generator and evaluator negotiated a written **sprint contract** "agreeing on what 'done' looked like for that chunk of work before any code was written" — Sprint 3 alone had 27 testable criteria (Harness design, 2026-03-24). Carlini likewise specified that the compiler "should have an SSA IR" but "did not go into any detail on how to do so" (C compiler, 2026-02-05). Bears on **(3)**: Colony's already-made change (deviate/rebut with evidence) is directionally confirmed; go further — express acceptance as executable criteria (tests/behavior) owned by the leaf, so "impossible requirements" are detectable as failing oracles rather than agent-versus-spec deadlock.

8. **Size leaves small and let agents self-claim them; file-level ownership is the merge-conflict mitigation, and small tasks finish in 1–4 runs while big ones churn.** The C-compiler team coordinated with no orchestrator at all: agents claim work by writing lock files to `current_tasks/` in git ("if two agents try to claim the same task, git's synchronization forces the second agent to pick a different one"), merge upstream frequently, and "merge conflicts are frequent, but Claude is smart enough to figure that out" (C compiler, 2026-02-05; the repo's `current_tasks/` and `ideas/` directories survive as artifacts). Claude Code's agent-teams docs institutionalize the same pattern — shared task list, "task claiming uses file locking," self-claim of unblocked tasks — while warning "two teammates editing the same file leads to overwrites," recommending 3–5 teammates, 5–6 tasks each, and tasks that are "self-contained units that produce a clear deliverable" (Agent teams docs, 2026). Bears on Colony's **one-writer-per-leaf** and **small-leaves** decisions: Colony's own data (1–4 runs on small tasks vs 11–13 on large) matches Anthropic's guidance exactly; keep leaves file-disjoint and let a backlog with dependencies replace the serial chain.

9. **Silent mechanism failure is the default failure mode of agent infrastructure; the countermeasures are decision-level tracing, per-change evals/ablation, soak periods, and gradual rollouts — not more mechanisms.** Anthropic's April 2026 postmortem traced weeks of "Claude feels worse" reports to three interacting changes, including a cache optimization whose bug "cleared [thinking] on every turn for the rest of the session" so Claude kept "executing, but increasingly without memory of why it had chosen to do what it was doing" — it passed human review, automated review, unit tests, e2e tests, and dogfooding, was masked by two unrelated experiments, and took over a week to root-cause; remediation was per-model evals for every system-prompt change, line-by-line ablations, soak periods, and gradual rollouts (Postmortem, 2026-04-23). The research team likewise needed "full production tracing" of "agent decision patterns and interaction structures" to diagnose failures users reported as "not finding obvious information" (Multi-agent research, 2025-06-13). Bears on **(4)** — this is Colony's exact wound (spec steering failing 9/9 for 3 weeks unnoticed; a 20-minute watchdog killing 23-minute test runs): every Colony mechanism needs an observable "did it fire, and did it help" signal and a tripwire when its fire rate goes to zero or 100%.

10. **Spend the model budget where capability is binding: cheap models for routine execution, strong models where judgment is scarce — and expect multi-agent token burn of ~4–15× chat to be the price of parallelism.** Anthropic's mixes: Opus 4 lead with Sonnet 4 subagents for research (Multi-agent research, 2025-06-13); Opus 4.6 for all C-compiler agents at just under $20k for ~2,000 sessions (C compiler, 2026-02-05); in the app harness the first QA round cost $3.24 against a $71.08 build round (~5%), and all three QA rounds totaled ~$10 against ~$114 of build (Harness design, 2026-03-24). Their effort-scaling rule of thumb: simple tasks = 1 agent with 3–10 tool calls; medium = 2–4 subagents with 10–15 calls each; complex = 10+ subagents (Multi-agent research, 2025-06-13). Bears on Colony's **flash-implement/strong-review mix** (validated — review is cheap relative to generation, so strong-model review is not where to economize) and on **cost expectations** for running one writer per leaf through review/CI.

11. **Mitigate time-blindness and context pollution in the harness, or agents burn hours and tokens re-orienting — and infra timeouts must be set relative to what the harness actually runs.** The C-compiler harness printed minimal incremental progress, logged detail to files with "ERROR" and the reason on the same line "so grep will find it," pre-computed aggregate statistics, and offered a `--fast` mode running a deterministic-per-agent random 1–10% sample "so Claude still covers all files but each agent can perfectly identify regressions" — because "Claude can't tell time and, left alone, will happily spend hours running tests instead of making progress" (C compiler, 2026-02-05). Bears on **(2)** (big-task churn is partly agents drowning in unfiltered test output and re-computing project state every cold run) and **(4)** (the watchdog killed 23-minute test runs at 20 minutes: give agents fast sampled test paths and they won't need the long ones mid-iteration; the long suite belongs in the merge gate).

12. **Keep humans on oracle-building, trace-reading, and steering — not on babysitting stuck tasks; and don't run teams fully unattended.** Every Anthropic system kept the human in the same three jobs: writing/curating the tests and criteria (Carlini: "A human guided some of this process by writing test cases that Claude was told to pass"), reading traces to find where agent judgment diverges from theirs ("read the evaluator's logs, find examples where its judgment diverged from mine, and update the QA's prompt"), and monitoring/steering ("Letting a team run unattended for too long increases the risk of wasted effort" — agent teams docs; Carlini's closing unease about "programmers deploying software they've never personally verified"). Bears on Colony's **operator-load problem** (4–6 actions/merge on the hard project): the lever isn't approving more runs faster, it's converting each recurring intervention class into an oracle, criterion, or trace signal — the 9-merges-in-19-h zero-intervention project is what success looks like.

## 2. Per-source findings

### 2.1 Building a C compiler with a team of parallel Claudes — Nicholas Carlini, 2026-02-05 (+ repo `anthropics/claudes-c-compiler`)

**Architecture.** "Agent teams": 16 parallel Claude Code (Opus 4.6) instances, each in a Docker container with a bare git repo mounted at `/upstream`, cloned to `/workspace`. The harness is a bare bash `while true` loop invoking `claude --dangerously-skip-permissions -p "$(cat AGENT_PROMPT.md)"`, logging per-commit. "I don't use an orchestration agent… I leave it up to each Claude agent to decide how to act." One accidental self-kill observed: Claude ran `pkill -9 bash`, ending its own loop.

**Coordination / merge strategy.** Lock files committed to git (`current_tasks/parse_if_statement.txt`-style); git push synchronization arbitrates double-claims. Agents pull/merge/push around each task; "merge conflicts are frequent, but Claude is smart enough to figure that out." The public repo still shows the mechanism: `current_tasks/` holds 13 lock files (e.g. `fix_arm_asm_caspal_instruction.txt`, `implement_string_literal_deduplication.txt`) and an `ideas/` backlog (e.g. `high_codegen_runtime_perf.txt`, `register_allocator.txt`, `docs_verified_2026_01_29.txt`) at read time (2026-10-21). Stuck agents maintain "a running doc of failed approaches and remaining tasks."

**Failure modes and fixes.**

- Agents breaking existing functionality with each new feature late in the project → built a CI pipeline with stricter enforcement "so that new commits can't break existing code."
- All 16 agents colliding on the same Linux-kernel bug, overwriting each other → GCC used "as an online known-good compiler oracle": compile a random mix of kernel files with GCC and the remainder with Claude's compiler; if the kernel boots, the bug is outside Claude's subset, otherwise refine the subset — converting one monolithic task into parallel per-file bug hunts; delta debugging then found pairs of files that failed only together.
- LLM-written code "frequently re-implements existing functionality" → a dedicated dedup agent coalescing duplicate code.
- Context pollution → harness prints only a few lines, logs detail to files, `ERROR` + reason on one greppable line, pre-computed aggregate statistics.
- Time blindness → infrequent progress prints; `--fast` runs a 1% or 10% random sample, "deterministic per-agent but random across VMs."

**Stuck/drift detection; deliberately not built.** The only stuck signal is the agent's own "running doc of failed approaches and remaining tasks"; there is no global stuck detector, and the Linux-kernel episode showed the cost — all 16 agents could be stuck on the same bug with no mechanism noticing. Explicitly absent by design: "I haven't yet implemented any other method for communication between agents, nor do I enforce any process for managing high-level goals. I don't use an orchestration agent." Direction-finding is left to the model: "In most cases, Claude picks up the 'next most obvious' problem."

**Specialized roles added.** Dedup agent; compiler-performance agent; generated-code-performance agent; Rust-code-quality critic ("critique the design of the project from the perspective of a Rust developer"); documentation agent.

**Verification.** The bulk of human effort: "improving the testing harness required finding high-quality compiler test suites, writing verifiers and build scripts for open-source software packages, and watching for mistakes Claude was making, then designing new tests as I identified those failure modes." Repo test layout (per-directory `main.c` + `expected.stdout`/`expected.ret` + arch skip markers); CI once regressions appeared.

**Stated limits (their words).** Lacks "the 16-bit x86 compiler that is necessary to boot Linux out of real mode"; it can emit correct 16-bit code via the 66/67 opcode prefixes but the output is "over 60kb, far exceeding the 32k code limit," so "Claude simply cheats here and calls out to GCC" for that phase; assembler/linker "the very last bits that Claude started automating and are still somewhat buggy"; "not yet a drop-in replacement for a real compiler"; generated code "less efficient than GCC with all optimizations _disabled_"; Rust quality "nowhere near the quality of what an expert Rust programmer might produce"; "New features and bugfixes frequently broke existing functionality" — "I tried (hard!) to fix several of the above limitations but wasn't fully successful." Clean-room: no internet access during development.

**Human role.** Wrote tests/verifiers, watched failure modes, designed new tests. Repo README: "100% of the code and documentation in this repository was written by Claude Opus 4.6… I do not recommend you use this code! None of it has been validated for correctness." His stated motivation: stress-test capability limits ("the best way to understand what language models can do is to push them to their limits, and then study where they start to break down").

**Published numbers.**

| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 2.2 Effective harnesses for long-running agents — 2025-11-26

**Architecture.** Two-part harness on the Claude Agent SDK: an **initializer agent** (first session only) and a **coding agent** loop (every subsequent session). Reference code: `anthropics/claude-quickstarts` `autonomous-coding`.

**Failure modes and fixes** (their summary table, paraphrased against the text):

- One-shotting / running out of context mid-feature, next session "start[s] with a feature half-implemented and undocumented" → initializer writes a comprehensive `feature_list.json` (200+ features for a claude.ai clone, all `"passes": false`); coding agents work on **one feature at a time**.
- Declaring victory early → feature list gives "a clear outline of what full functionality looked like"; coding agents may only flip `passes`, with strongly-worded instructions ("It is unacceptable to remove or edit tests…"). JSON chosen over Markdown because the model "is less likely to inappropriately change or overwrite JSON files."
- Marking features done without real testing → "make code changes, and even do testing with unit tests or `curl`… but would fail [to] recognize that the feature didn't work end-to-end" → explicit prompting to use browser automation (Puppeteer MCP) "and do all testing as a human user would," which "dramatically improved performance."
- Cold-start re-orientation cost → session-start ritual: `pwd`, read `claude-progress.txt` + git log, read feature list, run `init.sh` to start the dev server, smoke-test basic functionality first ("If the agent had instead started implementing a new feature, it would likely make the problem worse").
- End-of-session hygiene → "clean state": mergeable-to-main code, descriptive git commits, progress-file summaries; git also enables reverting bad changes.

**Memory/context strategy.** Compaction "isn't sufficient… doesn't always pass perfectly clear instructions to the next agent"; durable artifacts (feature JSON, progress file, git history, init.sh) carry state across context windows.

**Stuck/drift detection.** The feature list is the drift detector: every feature starts `false`, sessions pick "the highest-priority feature that's not yet done," and only flip `passes` after testing; the session-start smoke test detects a broken environment before new work. The failure it does not catch is a session that wrongly marks a feature passing — hence the explicit anti-test-editing instruction and end-to-end testing prompt.

**Known limits.** Claude can't see browser-native alert modals through Puppeteer MCP, and "features relying on these modals tended to be buggier as a result."

**Open question they flag.** Whether one general-purpose coding agent across contexts beats specialized agents (testing agent, QA agent, code-cleanup agent) — the question the next two sources answer.

**Human role / model mix / numbers.** Human designed the harness and prompts; Opus 4.5 named as the frontier coding model used. No cost numbers published.

### 2.3 Harness design for long-running application development — 2026-03-24

**Architecture.** GAN-inspired three-agent system on the Claude Agent SDK: **planner** (1–4-sentence prompt → full product spec, deliberately high-level; also told to weave in AI features), **generator** (builds feature-at-a-time in "sprints," self-evaluates, hands to QA), **evaluator** (Playwright MCP, clicks through the running app, grades per-sprint against criteria with hard thresholds — any criterion below threshold fails the sprint). Inter-agent communication is files on disk. Frontend-design variant: generator + evaluator with four weighted grading criteria (design quality, originality, craft, functionality), evaluator calibrated with few-shot score breakdowns "to reduce score drift across iterations."

**Failure modes and fixes.**

- **Context anxiety**: Sonnet 4.5 "begin wrapping up work prematurely as they approach what they believe is their context limit" → **context resets** (fresh agent + structured handoff) rather than compaction, which "doesn't give the agent a clean slate." Opus 4.5 removed the behavior → resets dropped entirely; automatic compaction sufficed for the whole build.
- **Self-evaluation leniency**: agents "confidently prais[e] the work—even when… the quality is obviously mediocre" → separate evaluator; "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work."
- **Out-of-the-box QA weakness**: evaluator talked itself into approving, tested superficially → tuning loop: "read the evaluator's logs, find examples where its judgment diverged from mine, and update the QA's prompt" over several rounds; even then, limits remained (small layout issues, unintuitive interactions, undiscovered bugs "in more deeply nested features that the evaluator hadn't exercised thoroughly").
- **Sprint contract negotiation**: generator proposes what it will build and how success is verified; evaluator reviews; iterate until agreement — "bridge the gap between user stories and testable implementation."

**Stuck/drift detection.** Per-sprint contracts with hard-threshold criteria are the drift detector; any criterion below threshold fails the sprint and returns specific feedback. They added no separate stuck detector — the evaluator is it — and its known blind spot is "more deeply nested features that the evaluator hadn't exercised thoroughly." On 4.6 the single end-of-run pass shifts drift detection later, accepting more rework risk in exchange for less QA overhead.

**What they removed, and why.** "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing… they can quickly go stale as models improve." A radical cut-everything rewrite failed (couldn't tell what was load-bearing) → switched to removing one component at a time. On Opus 4.6: removed the sprint construct (generator ran coherently 2+ hours); evaluator moved from per-sprint to a single end-of-run pass. Conclusion: "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo" — on 4.5 the builds were at that edge, on 4.6 the boundary moved outward. Planner retained: without it, "the generator under-scoped."

**Evaluator output quality.** Findings were specific and actionable: e.g. `FAIL — Delete key handler at LevelEditor.tsx:892 requires both selection and selectedEntityId…`; `PUT /frames/reorder` shadowed by `/{frame_id}` route returning 422. Sprint 3 contract had 27 criteria for the level editor.

**Human role.** Wrote grading criteria, calibrated the evaluator, read traces, compared solo vs harness outputs by hand. Notes the base model's "product intuition" gaps (e.g. UI not suggesting sprite→entity→level ordering) as beyond harness scope.

**Published numbers.**

### 2.4 How we built our multi-agent research system — 2025-06-13

**Architecture.** Orchestrator-worker: LeadResearcher (Opus 4) plans, saves its plan to memory to survive 200k-token truncation, spawns 2–N specialized subagents (Sonnet 4) in parallel; subagents search with interleaved thinking and return condensed findings; a CitationAgent attributes claims at the end.

**When multi-agent helps / doesn't (their stated boundary).** Helps: "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools" — breadth-first queries especially (+90.2% over single-agent Opus 4 on their internal research eval). Doesn't (as of that date): "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit… most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time." Token economics: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats" — viable only where task value exceeds this. BrowseComp analysis: token usage alone explains 80% of performance variance; tool-call count and model choice the other two of the three factors explaining 95%.

**Failure modes and fixes.**

- Early agents "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates" → prompt-embedded effort-scaling rules (simple: 1 agent, 3–10 tool calls; comparison: 2–4 subagents × 10–15 calls; complex: 10+ subagents with divided responsibilities).
- Vague delegation ("research the semiconductor shortage") → duplicated/gapped work → teach the orchestrator to delegate: each subagent gets "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."
- Sequential searches "painfully slow" → lead spawns 3–5 subagents in parallel + subagents use 3+ tools in parallel → "cut research time by up to 90% for complex queries."
- Tool ergonomics failures → a tool-testing agent that uses a flawed MCP tool, then rewrites its description; "40% decrease in task completion time for future agents."
- Source-selection bias (SEO content farms over authoritative sources) caught by _human_ testers → source-quality heuristics added to prompts.

**Verification/review.** Start evals immediately with ~20 real queries (a prompt tweak moved success 30%→80%); single LLM-as-judge call with rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) scoring 0.0–1.0 + pass/fail was "the most consistent and aligned with human judgements"; human evaluation still catches what automation misses. Judge outcome, not path: "evaluate whether it achieved the correct final state… break evaluation into discrete checkpoints."

**Production reliability lessons (directly relevant to Colony's problem 1).** "Agents are stateful and errors compound… restarts are expensive and frustrating… we built systems that can resume from where the agent was when the errors occurred"; combine model adaptability ("letting the agent know when a tool is failing and letting it adapt works surprisingly well") with deterministic retry logic and checkpoints. Debugging needed "full production tracing" of decision patterns, not conversation contents. Deployment: rainbow deployments, because running agents can't all be updated at once. Synchronous subagent execution is a bottleneck (lead can't steer mid-flight); async adds coordination/consistency/error-propagation complexity.

**Stuck/drift detection.** Full production tracing of "agent decision patterns and interaction structures" is the detector; effort-scaling rules in the prompt prevent over-investment in simple queries; the stated coordination gap is that "the lead agent can't steer subagents, subagents can't coordinate" while running synchronously — steering only happens between waves.

**Memory/context strategy.** Subagent outputs written to a filesystem "to minimize the 'game of telephone'" — subagents store artifacts and return lightweight references; subagents spawn fresh contexts on overflow; agents retrieve the stored plan from memory rather than losing it.

**Human role / model mix / numbers.** Tight research/product/engineering collaboration; Opus 4 lead + Sonnet 4 subagents; numbers as above (90.2%, 80%, 95%, 4×/15×, 90% time cut, 40% completion-time cut, ~20 seed queries).

### 2.5 Building effective agents — 2024-12-19

**Architecture taxonomy.** Workflows (predefined code paths) vs agents (model-directed loops); patterns: augmented LLM → prompt chaining → routing → parallelization (sectioning/voting) → orchestrator-workers ("well-suited for complex tasks where you can't predict the subtasks needed (in coding, for example, the number of files that need to be changed… likely depend on the task)") → evaluator-optimizer (effective "when we have clear evaluation criteria"). Agents = "LLMs using tools based on environmental feedback in a loop."

**Core principles.** "Find the simplest solution possible, and only increase complexity when needed"; agentic systems "trade latency and cost for better task performance"; frameworks obscure prompts/responses — start with the raw API; three principles: simplicity, transparency of planning steps, careful agent-computer-interface (ACI) design.

**ACI / tool lessons.** Invest in tool design as much as HCI; poka-yoke tool arguments; on SWE-bench "we actually spent more time optimizing our tools than the overall prompt" — e.g. relative paths broke after `cd`, fixed by requiring absolute paths, after which "the model used this method flawlessly."

**Agents in production guidance.** Agents suit open-ended problems with unpredictable steps; "higher costs, and the potential for compounding errors"; "extensive testing in sandboxed environments, along with the appropriate guardrails"; agents must "gain 'ground truth' from the environment at each step"; stopping conditions (max iterations) to maintain control. On coding agents: "automated testing helps verify functionality, [but] human review remains crucial for ensuring solutions align with broader system requirements."

**Human role / model mix / numbers.** No cost numbers; advocates routing easy inputs to Haiku-class and hard to Sonnet-class models.

### 2.6 Scaling Managed Agents: Decoupling the brain from the hands — 2026-04-08

**Architecture.** Virtualizes three components behind stable interfaces: **session** (append-only log of everything; `getSession(id)`, `emitEvent(id, event)`, `getEvents()`), **harness** (the agent loop; stateless; rebooted via `wake(sessionId)`, resumes from last event), **sandbox** (`execute(name, input) → string`, `provision({resources})`). Explicit OS analogy: interfaces that outlive implementations, "opinionated about the shape of these interfaces, not about what runs behind them." Self-described "meta-harness."

**Failure modes and fixes.**

- Pets-vs-cattle: single-container session+harness+sandbox meant "if a container failed, the session was lost"; debugging stuck sessions was near-impossible (only a WebSocket stream; container held user data, so shelling in was unacceptable) → decouple; container death becomes an ordinary tool-call error Claude can retry; new container via standard recipe.
- Harness assumed resources were co-located (VPC customer complaint) → brain leaves the container; sandboxes provisioned lazily per tool call.
- Cold-start cost: every session paid container setup up front → decoupled brains: "our p50 TTFT dropped roughly 60% and p95 dropped over 90%."
- Prompt-injection blast radius: generated code ran next to credentials → "make sure the tokens are never reachable from the sandbox": git tokens wired into the remote at sandbox init; OAuth in an external vault; MCP calls via a proxy holding the session token; "the harness is never made aware of any credentials."

**Memory/context strategy.** "The session is not Claude's context window": the durable session log is a context object outside the window; the brain pulls positional slices via `getEvents()` (resume where it stopped, rewind to see lead-up to a moment); the harness transforms fetched events (cache-hit optimization, context engineering) before they enter the window — recoverable storage (session) separated from context management (harness) because "we can't predict what specific context engineering will be required in future models."

**Stale-assumption doctrine.** Opening example: context resets built for Sonnet 4.5's context anxiety "had become dead weight" on Opus 4.5. "Harnesses encode assumptions that go stale as models improve" — the reason interfaces, not mechanisms, are the durable layer.

**Human role / model mix / numbers.** No model-specific costs; TTFT numbers above.

### 2.7 Claude Code docs: Orchestrate teams of Claude Code sessions (agent teams) — accessed 2026-10-21 (experimental; docs reference versions up to v2.1.296)

**Architecture.** One **team lead** session + **teammates** (full independent Claude Code instances, own context windows), a **shared task list** (pending/in-progress/completed + dependencies; dependent tasks unblock automatically), and a **mailbox** (per-agent JSON inbox files at `~/.claude/teams/{team}/inboxes/{agent}.json`). Enabled by `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; disabled by default. Teammates load project context (CLAUDE.md, MCP, skills) but _not_ the lead's conversation history — the spawn prompt must carry task-specific context. Teammates can message each other directly, not just via the lead; a message from lead/peer wakes an idle teammate into immediate retry.

**Coordination / merge strategy.** "Task claiming uses file locking to prevent race conditions"; teammates self-claim the next unassigned unblocked task or the lead assigns. File-ownership discipline is on the user: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." Quality gates via hooks: `TeammateIdle`, `TaskCreated`, `TaskCompleted` (exit code 2 vetoes with feedback). Shutdown is negotiated: the teammate "can approve, exiting gracefully, or reject with an explanation."

**Stated best practices / limits.** Use for research/review, new modules, debugging with competing hypotheses, cross-layer work; _not_ for sequential tasks, same-file edits, or heavy dependencies. 3–5 teammates to start; 5–6 tasks per teammate; task size "self-contained units that produce a clear deliverable"; "Agent teams add coordination overhead and use significantly more tokens than a single session"; "Letting a team run unattended for too long increases the risk of wasted effort." Known limitations (verbatim themes): no session resumption with in-process teammates (after `/resume`, "the lead may attempt to message teammates that no longer exist"); "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks" (manual fix or nudge); shutdown can be slow; one team per session; no nested teams; lead is fixed; permissions set at spawn. Troubleshooting includes "Agents stopping early" (teammates stop after errors instead of recovering — message them or spawn a replacement) and the lead declaring the team done early ("tell it to keep going").

**Cost guidance.** Token usage scales linearly with teammates; "for routine tasks, a single session is more cost-effective." No absolute numbers published in the docs.

### 2.8 An update on recent Claude Code quality reports (postmortem) — 2026-04-23

**What broke.** Three independent changes over March–April 2026 combined into what looked like broad model degradation: (1) default reasoning effort `high`→`medium` (Mar 4) — "the wrong tradeoff," reverted Apr 7 after user feedback; (2) a cache optimization (Mar 26) meant to clear old thinking _once_ after 1h idle instead cleared it "on every turn for the rest of the session" — Claude kept "executing, but increasingly without memory of why it had chosen to do what it was doing," and the resulting cache misses drained usage limits faster (fixed Apr 10, v2.1.101); (3) a ≤25-words-between-tool-calls verbosity line in the system prompt (Apr 16) that cost 3% on evals for Opus 4.6 _and_ 4.7 (reverted Apr 20, v2.1.116).

**Why it stayed invisible for weeks.** "Because each change affected a different slice of traffic on a different schedule, the aggregate effect looked like broad, inconsistent degradation"; internal usage and evals didn't reproduce it; two unrelated experiments masked bug (2) — including a display change that suppressed the bug in most CLI sessions "so we didn't catch it even when testing external builds." The bug "made it past multiple human and automated code reviews, as well as unit tests, end-to-end tests, automated verification, and dogfooding," in a corner case (stale sessions) "at the intersection of Claude Code's context management, the Anthropic API, and extended thinking"; over a week to confirm root cause.

**What they changed.** Larger share of staff on the exact public build; per-model eval suites for every system-prompt change plus line-level ablations; tooling to review/audit prompt changes; model-specific changes gated per model in CLAUDE.md; "for any change that could trade off against intelligence, we'll add soak periods, a broader eval suite, and gradual rollouts." Notably: back-testing Code Review with Opus 4.7 (with full repo context) found the caching bug that Opus 4.6 missed — evidence for strong-model review of infrastructure changes, and for giving reviewers full context.

### 2.9 Effective context engineering for AI agents — 2025-09-29 (supporting source)

Context rot is universal ("as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"); context is "a finite resource with diminishing marginal returns"; the goal is "the smallest possible set of high-signal tokens." Long-horizon techniques, in order: **compaction** (tune the compaction prompt on real traces; "maximizing recall" first, then precision; clearing old tool results is "the safest lightest touch"); **structured note-taking** (NOTES.md-style agentic memory; Pokémon agent tracking "for the last 1,234 steps…"); **sub-agent architectures** (subagents burn tens of thousands of tokens and return "a condensed, distilled summary… often 1,000-2,000 tokens"). Prefers just-in-time retrieval (file paths, grep) over pre-computed indexes, with CLAUDE.md as the hybrid up-front layer. Selection guidance: compaction for conversational flow, note-taking for "iterative development with clear milestones," multi-agent for "complex research and analysis where parallel exploration pays dividends."
