# Cursor's agent factories: what they learned, for Colony

Research date: 2026-10-21. Sources are Cursor's own engineering posts, the FastRender repository's agent-facing docs and README, the minisqlite repository README, and Simon Willison's contemporaneous notes from a recorded interview with Wilson Lin; each is dated in §3. Claims I could not verify are marked `[UNVERIFIED]`, inferences `[INFERENCE]`. Numbers are quoted as published; where two posts disagree or describe different artifacts, I say so rather than reconcile silently.

---

## 1. Lessons for Colony

Colony problem key: **(1)** 46% of implement runs die to non-model causes; **(2)** big tasks churn 11–13 implement runs / 3–6 review rounds, repairs restart cold; **(3)** no-deviation rule turned impossible specs into human blocks (already changed); **(4)** hand-built reliability mechanisms collide and fail silently; **(5)** agent sandbox differs from CI. Design decisions in play: keep factory policy; run agents on daimyo; one writer owns each leaf through review/CI; small leaves; planners can add leaves at runtime.

1. **Environment quality is the dominant and silent variable — treat the sandbox as a product, because its failures present as "the model is bad," not as errors.** Cursor: "the single biggest factor in cloud agent output quality is ensuring it has a full development environment" and "often the only indication is a subtle degradation in output quality… you might chalk it up to the model" ([cloud-agent-lessons](https://cursor.com/blog/cloud-agent-lessons), 2026-06-02); the environment post calls it "a product in its own right, only one whose users are agents" ([cloud-agent-environment](https://cursor.com/blog/cloud-agent-environment), 2026-07-30). Bears on **Colony 1 and 5**: 117 sandbox-provisioning deaths and a sandbox that differs from CI are not infra chores, they are silent quality taxes.

2. **Durability belongs in a real durable-execution engine, not in hand-built watchdogs and retry budgets.** Cursor's work-stealing cloud-agent loop ran at "one 9 of reliability"; after migrating to Temporal it "moved past two 9s," handling "more than 50 million actions per day across more than 7 million unique workflows" ([cloud-agent-lessons](https://cursor.com/blog/cloud-agent-lessons), 2026-06-02) — and they only migrated because they "found ourselves on the verge of rebuilding a lot of the durable execution primitives that Temporal already solves." Bears on **Colony 1 and 4** and directly validates the move to daimyo's journaled tasks: watchdogs that kill 23-minute tests are a symptom of owning durability in application code.

3. **Flat self-coordination among equal agents does not work: locks serialize it and status anxiety makes agents risk-averse, so no one owns the hard end-to-end work.** With a shared coordination file, "20 agents would slow to the throughput of 1-3," agents held or forgot locks, and "the lack of structure between agents meant no single agent took on big, complex tasks… opting for smaller and safer changes" ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). This is the empirical case for Colony's "one writer owns each leaf through review/CI": ownership is what fixes risk aversion, not more coordination protocol.

4. **Use a recursive planner/worker tree instead of a fixed up-front plan, and let planners add work at runtime from worker handoffs.** The fixed planner→executor→workers pipeline "was bottlenecked by the slowest worker. It was too rigid," and upfront planning "made it hard for the system to dynamically readjust as new issues were discovered"; the final design has recursive sub-planners and workers that send a single handoff ("notes, concerns, deviations, findings, thoughts, and feedback") back to the requesting planner, which keeps planning ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). The July post frames the same tree as a _memory_ device: planners never implement so their context stays high-level, workers never plan so their context stays narrow ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). Bears on **Colony 2** (task size, cold restarts) and the runtime-leaf design: Colony's fixed ≤20-task plan is the exact shape Cursor abandoned.

5. **Drift is a context-budget problem, and the countermeasures are fresh starts plus a curated shared field guide — not longer contexts on cold repair runs.** "We think this explains why long-running single agents drift. They can either focus on the work in front of them and lose sight of the bigger picture, or hold the big picture and do a worse job on the piece"; the January post already concluded "we still need periodic fresh starts to combat drift and tunnel vision," and the February post added in-run mitigations (rewrite `scratchpad.md` rather than append, auto-summarize at context limits, self-reflection/alignment reminders, encouragement to pivot) without claiming they replace fresh starts ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20; [scaling-agents](https://cursor.com/blog/scaling-agents), 2026-01-14; [self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). The Field Guide — an agent-owned folder whose `index.md` is injected into every agent at start, constrained only by a line budget — is the stigmergic fix for institutional memory ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). Bears on **Colony 2**: cold repair runs should inherit a handoff + field guide, not the whole task again.

6. **Optimize throughput, not per-commit perfection; require 100% correctness and the whole swarm serializes.** "When we required 100% correctness before every single commit, it caused major serialization and slowdowns… Many agents would pile on and trample each other trying to fix the same issue"; Cursor accepted "a small but stable rate of errors that requires a final reconciliation pass" and a periodic "green" branch fixup ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). Corollary from the SQLite rerun: commit volume is not progress — the old Grok run made 68,000 commits in two hours (~70× the new run) and accumulated >70,000 merge conflicts before being paused ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). Bears on **Colony 1/2 and the merge gate**: gate the release branch, not every leaf commit, and do not read run count or commit count as productivity.

7. **At swarm tempo, collisions need dedicated mechanisms — a neutral third-party merge resolver, a shared design record, megafile decomposition, and licensed out-of-scope breakage — not a central gate.** Workers "are bad at" resolving conflicts and "either overwrite the other change or abandon their own," so a neutral agent resolves on behalf of all parties, "similar to the way merge queues work"; two planners fighting over the same files are fixed by shared design docs with "a compile-checked reference back to its doc" plus a reconciler; bloated files are flagged, commits blocked, and an outside agent decomposes them; "ossification" is fixed by licensing "intentional breakage" — a focused out-of-scope patch with a comment that the compiler then propagates to every dependent agent ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). Results: hottest file went from 7,771 conflicts across 1,173 agents to 47; crates went from 54 (including three SQL packages) to 9. Bears on **Colony 2 and 4**, and on the deterministic merge gate: keep the gate deterministic, but put an _agent_ resolver in front of it.

8. **Delete central roles and hand-built safeguards aggressively; every added gate becomes a bottleneck, and every overloaded agent becomes pathological.** Cursor removed the integrator ("more bottlenecks than it solved… Workers were already capable of handling conflicts themselves"), removed the independent planner, removed the judge once instruction-following proved reliable, removed harness double-checks/forced commits, and replaced "eternal" Temporal workflows with "shorter ones that exit after completing a single task" ([scaling-agents](https://cursor.com/blog/scaling-agents), 2026-01-14; [self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05; [cloud-agent-lessons](https://cursor.com/blog/cloud-agent-lessons), 2026-06-02). But the same history shows the failure mode of over-deletion: the continuous executor that absorbed planner+judge duties "would sleep randomly, stop running agents, do work itself… and claim premature completion," because it had "too many roles and objectives simultaneously." Bears on **Colony 4**: Colony's watchdogs, steering, epochs and adoption are the continuous-executor mistake at the scope level; the right amount of structure is "somewhere in the middle."

9. **Treat the prompt/spec as the primary engineering surface, and assume literal compliance — that is why "don't deviate" produced blocks.** "The harness and models matter, but the prompts matter more" ([scaling-agents](https://cursor.com/blog/scaling-agents), 2026-01-14); "Agents have immense engineering skill but will follow instructions to the end, good or bad" ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). Specific levers: constraints beat exhortations ("No TODOs, no partial implementations" works better than "remember to finish implementations"); give numeric ranges ("Generate 20-100 tasks" vs "generate many tasks"); don't instruct what the model already knows; avoid checkbox lists that narrow attention. Model sensitivity is real: GPT-5.6 Sol showed "runaway spirals unlike anything the other models produced" under "literal and emphasized wording" and was dropped from the comparison ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics) fn. 2, 2026-07-20). Bears on **Colony 3**: Cursor's fix is not "permission to deviate" alone but _licensed, attributable_ deviation (comment + compiler propagation) and specs that state intent and non-goals.

10. **Stack decorrelated review lenses instead of relying on one reviewer or one rubric.** Cursor tried review agents given the worker's full transcript, only its output, or only the codebase, plus reviewers on different models and "different personality"; "No single lens catches everything, but decorrelated lenses stack, the way self-driving systems reach above-human reliability without any single perfect component," and "review is much cheaper than the work it audits," so review compute is high-return ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). Bears on **Colony 2's 3–6 review rounds**: the alternative to one strong adversarial reviewer is several cheap, uncorrelated ones — not more rounds of the same lens.

11. **Split models by role: frontier planner, cheap workers — planning is where the expensive tokens pay for themselves, and a better planner makes workers cheaper.** Same quality, wildly different cost across mixes: $1,339 (Opus 4.8 planner + Composer 2.5 workers) vs $10,565 (GPT-5.5 everywhere); workers carried ≥69% of tokens (over 90% in most runs), but in the Opus hybrid the planner produced a small token fraction and roughly two-thirds of the cost; GPT-5.5 workers alone cost $9,373 while "the entire worker fleet" of Composer 2.5 cost $411 ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20). "Few moments in a large task genuinely require frontier intelligence… Once a frontier planner has collapsed the ambiguity into a detailed, explicit instruction, less expensive models simply have to follow it." Cursor's production router agrees that no model dominates: Auto Balance beats Opus 4.8 at 41% lower cost, Auto Intelligence is above Fable-level satisfaction at 68% lower cost ([how-cursor-router-works](https://cursor.com/blog/how-cursor-router-works), 2026-08-06). Bears on Colony's cheap-"flash" implementers: the data supports cheap execution but says the frontier budget belongs in **planning and review**, and that a weak planner inflates worker token spend (the Fable 5 planner had a smaller bill than Opus 4.8 but its workers burned several times more tokens).

12. **Build observability before scaling, and hill-climb from logs and outcome metrics rather than importing human-org or distributed-systems designs by assumption.** "We spent more time up front on proper observability… We logged all agent messages, system actions, and command outputs, with timestamps so we could analyze and replay sessions"; they found the `git restore` contention storm by mining logs against prompts, and state as a principle "Empirical over assumption-driven… rather than coming in with assumptions about how it should work based on human organizations" ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases), 2026-02-05). They also graded against a suite the swarm was never told about, with manual anti-cheat review, and the kernel benchmark invalidated results that "use cheating tactics like caching" ([agent-swarm-model-economics](https://cursor.com/blog/agent-swarm-model-economics), 2026-07-20; [multi-agent-kernels](https://cursor.com/blog/multi-agent-kernels), 2026-04-14). Bears on **Colony 4**: "spec steering failed 9/9 for 3 weeks unnoticed" is precisely the class of silent failure a replayable event log plus outcome dashboards makes impossible.

## 2. Per-source findings

### 2.1 Scaling long-running autonomous coding — Wilson Lin, Cursor (2026-01-14)

Source: <https://cursor.com/blog/scaling-agents>. Seven-minute summary post; the earlier of the two swarm posts.

**Architecture.** Hundreds of concurrent agents on one project. Planners "continuously explore the codebase and create tasks" and can spawn sub-planners (recursive planning); workers "pick up tasks and focus entirely on completing them… They don't coordinate with other workers"; at the end of each cycle "a judge agent determined whether to continue, then the next iteration would start fresh."

**Failure modes and fixes.** The first design was flat self-coordination through a shared file with locking. Three failures: (a) locks held too long or never released, and "Twenty agents would slow down to the effective throughput of two or three, with most time spent waiting"; (b) brittleness — agents failing while holding locks, re-acquiring held locks, or writing without the lock; (c) after switching to optimistic concurrency ("simpler and more robust") the deeper problem remained: "With no hierarchy, agents became risk-averse. They avoided difficult tasks and made small, safe changes instead. No agent took responsibility for hard problems or end-to-end implementation." Fix: role separation (planner / worker / judge).

**What they removed.** An integrator role built for "quality control and conflict resolution" was deleted: "it created more bottlenecks than it solved. Workers were already capable of handling conflicts themselves." (This is contradicted in substance by the July post, which found workers bad at conflicts and added a neutral resolver — see 2.3. Reconciliation: a _central gate_ was the bottleneck; an _on-demand impartial resolver_ is not the same mechanism.) They also abandoned the ambition of modeling the system on distributed computing or organizational design: "not all of them work for agents."

**Coordination and merge.** Hundreds of workers push to the same branch "with minimal conflicts"; the harness's task decomposition, plus the code structure, keeps agents off each other's files.

**Verification.** Judge agent per cycle; CI and "early checks" on a +266K/−193K Solid→React migration that still "needs careful review."

**Stuck/drift.** "Agents occasionally run for far too long. We still need periodic fresh starts to combat drift and tunnel vision."

**Human role.** One instruction up front; no steering during a run. The human sets the goal and the harness; agents own decomposition and execution.

**Model mix and cost.** "GPT-5.2 models are much better at extended autonomous work: following instructions, keeping focus, avoiding drift"; "Opus 4.5 tends to stop earlier and take shortcuts when convenient, yielding back control quickly"; GPT-5.2 is a better planner than the coding-specialized GPT-5.1-Codex; "We now use the model best suited for each role rather than one universal model."

**Published numbers.** Browser: close to a week, "over 1 million lines of code across 1,000 files." Solid→React in-place migration: 3+ weeks, +266K/−193K. A product experiment: video rendering 25× faster in Rust, merged. Other runs: Java LSP 7.4K commits/550K LoC; Windows 7 emulator 14.6K commits/1.2M LoC; Excel 12K commits/1.6M LoC. "Trillions of tokens."

**Quotable.** "Many of our improvements came from removing complexity rather than adding it." "The right amount of structure is somewhere in the middle. Too little structure and agents conflict, duplicate work, and drift. Too much structure creates fragility." "The harness and models matter, but the prompts matter more."

### 2.2 Towards self-driving codebases — Wilson Lin, Cursor (2026-02-05)

Source: <https://cursor.com/blog/self-driving-codebases>. The 19-minute design history; the most useful single document for Colony because it shows each design being falsified.

**Architecture evolution.** Five successive designs, each actually run; the last is the one still in use:

| Stage                                   | Structure                                                                                                                                                    | Why it was abandoned                                                                                                                                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Single agent                         | One agent, repeatedly nudged to "keep going"                                                                                                                 | Lost track, "frequently stopped to proclaim success despite being far from it," stuck on implementation details                                                                                         |
| 2. Hand-spawned dependency graph        | Human/agent spawns tasks manually, nudges stopped agents                                                                                                     | Better throughput, but agents "couldn't communicate with each other or provide feedback on the project as a whole"                                                                                      |
| 3. Planner → executor → workers + judge | Planner lays out plan, executor owns delivery and spawns tasks, independent judge decides whether to iterate                                                 | "Bottlenecked by the slowest worker. It was too rigid"; upfront plan couldn't readjust; agents went "in counterproductive directions, unable to self-correct until the next iteration"                  |
| 4. Continuous executor                  | Executor also plans, spawns, merges; no independent planner; judge removed                                                                                   | Pathological: "sleep randomly, stop running agents, do work itself, refuse to plan and spawn more than a few narrowly focused tasks, not properly merge worker changes, and claim premature completion" |
| 5. Final: recursive planners + workers  | Root planner owns scope and does no coding; sub-planners own slices recursively; workers own tasks end-to-end, work on their own repo copy, emit one handoff | (Running design; "No major further iterations have been necessary on the harness")                                                                                                                      |

Diagnosis of stage 4, verbatim: "it was being given too many roles and objectives simultaneously, including: plan, explore, research, spawn tasks, check on workers, review code, perform edits, merge outputs, and judge if the loop is done. In retrospect, it makes sense it was overwhelmed."

**Failure modes and fixes (stage 1–3).** Lock contention (see 2.1); an explicit "wait on another agent's work" tool that "they rarely used"; optimistic concurrency that reduced overhead "but didn't eliminate confusion"; agents avoiding big tasks. Fixes, in order: role separation; removing the static plan; freshness mechanisms; handoff messages; removing the integrator; removing the judge ("We found agents were reasonably good at following instructions to completion, so the judge was removed to keep the system simple").

**Coordination and merge.** Workers never talk to each other; information flows up only, via handoffs, to owners "with increasingly global views, without the overhead of global synchronization or cross-talk." Each worker has its own repo copy and pushes to a shared branch; conflicts are accepted as turbulence rather than stamped out.

**Memory/context.** `scratchpad.md` "should be frequently rewritten versus being appended to"; auto-summarization at context limits; self-reflection and alignment reminders in system prompts; explicit encouragement to pivot and challenge assumptions. The handoff is the cross-agent memory primitive.

**Verification/review.** Judge removed; per-commit correctness explicitly relaxed (see lesson 6); a final "green" branch where "an agent regularly takes snapshots and does a quick fixup pass before release." Observability as verification: all messages, actions and command outputs logged with timestamps for replay and log-mining.

**Stuck/drift.** Drift countered by freshness + handoff + the ability to "proactively explore code, reconsider decisions, manage workers, interleave tasks."

**Human role.** Instructions once, then no intervention: "Once the system started, it didn't require any intervention from us." The human's leverage is entirely in the initial spec and the harness.

**Model mix and cost.** Switched from Claude models to GPT-5.1/5.2 during this period specifically because of instruction-following; no cost numbers in this post.

**Infrastructure findings (directly relevant to Colony 5).** One large VM per run, not distributed; most runs peaked at "several hundred agents"; after capping agent RAM "the disk became the hotspot" with "many GB/s reads and writes of build artifacts" from simultaneous compilation; therefore "the project structure, architectural decisions, and developer experience can affect token and commit throughput, simply because working with the codebase (e.g. compilation) dominates time." Git and Cargo use shared coarse locks that are fine for one developer and unworkable for hundreds; they float copy-on-write/deduplication and database-style concurrency control as the fix. A later run restructured the monolith into self-contained crates, starting from "a heavily broken state," and "converged toward working code in a few days" at "multiple times more throughput."

**Specification lessons (the direct ancestor of Colony 3).** The first browser architecture "was unfit to evolve into a full browser. This was a failure of the initial specification." Vague instructions ("spec implementation") sent agents "deep into obscure, rarely used features rather than intelligently prioritizing." Performance expectations had to be stated explicitly and enforced with timeouts. Memory leaks and deadlocks needed "explicit process-based resource management tools." Agents pulled dependencies they could have implemented; a later run "explicitly laid out the dependency philosophy and which libraries must not be used."

**Prompt craft, verbatim.** "We found it was better to not instruct for things the model knows how to do, only things it doesn't know… Treat the model like a brilliant new hire who knows engineering but not your specific codebase and processes." "Constraints are more effective than instructions." "Avoid checkbox mentality for higher-level or deeper tasks… giving specific things to do tends to make the model focus on achieving those rather than the wider scope." "Generate 20-100 tasks" produced very different behavior from "generate many tasks."

**Published numbers.** ~1,000 commits/hour peak; 10M tool calls over a week; one week continuous with no intervention; several hundred agents per run, hundreds of workers per machine.

### 2.3 Agent swarms and the new model economics — Wilson Lin, Cursor (2026-07-20)

Source: <https://cursor.com/blog/agent-swarm-model-economics>. The most quantitatively useful source; the SQLite-from-documentation benchmark and the second-generation harness.

**Architecture.** Two roles over a task tree: "Planner agents, powered by the smartest models, split a goal into pieces and delegate them. Worker agents, generally powered by faster and less expensive models, execute those pieces." The design is "a superset of more rigid orchestration systems": the shape grows to the problem rather than being imposed. "Planner agents… can spawn sub-planners" is carried over from 2.2.

**Why the tree helps (memory argument).** A single agent "has to walk the entire tree itself, descending to each leaf while holding its ancestors, its current position, and the wider goal in context the whole time," which explains drift; planners never implement, workers never plan. "We suspect the ability to scale the agent swarm comes from this context efficiency, more than from parallelism itself." Cites Coase's _The Nature of the Firm_ on coordination costs producing tiers.

**Custom VCS.** Git at ~1,000 commits/hour was the ceiling; the new system "peaks at around 1,000 commits per second," so they "built a new version control system (VCS) from scratch." Throughput was not the only reason: "Every change in the system passes through the VCS, so it is where collisions first become visible, and several of the coordination mechanisms… are implemented directly inside of it."

**Failure modes at 1,000 commits/second, each with its fix:**

| Failure mode       | Mechanism                                                                                                                                                           | Fix                                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Split-brain design | Two unaware planners implement the same concept differently in different parts of the codebase                                                                      | Prompting: planners make design decisions themselves instead of delegating them; "no two delegated subtrees decide the same question"                                                              |
| Planner contention | Two planners aware of each other fight through changes over the same files; "merge tooling can't fix a disagreement"                                                | Shared design docs; code carries "a compile-checked reference back to its doc"; a reconciler merges docs and the references propagate the resolution                                               |
| Merge conflicts    | Workers must "stop, absorb the other agent's context, and merge around it"; they "either overwrite the other change or abandon their own"                           | "A neutral third-party agent intervenes on merge conflicts and resolves them on behalf of all parties… similar to the way merge queues work"                                                       |
| Megafiles          | Popular files accrete small additions; "no single agent is responsible for keeping the files small"; expensive to transport/diff/merge and constant collision sites | Workers can flag bloated files; "we block new commits and an outside agent decomposes the overgrown file into smaller modules"                                                                     |
| Ossification       | Agents learned from human codebases "not to touch core code even when it needs to change"                                                                           | "We license intentional breakage": a focused out-of-scope patch plus a comment; "the compiler carries the change through the rest of the system," and dependent agents find the comment and update |

**Review lenses.** Experimented with reviewers given the worker's full transcript, only its output, or "nothing but the codebase," plus reviewers on different models "with different training and a different personality." "No single lens catches everything, but decorrelated lenses stack"; "The compute spent on review is high return, since review is much cheaper than the work it audits"; "We suspect this stacked review system was a major contributor to the sustained quality of the runs."

**Memory/context: the Field Guide.** "An experiment in self-authored, shared context… a folder owned entirely by the agents, whose index.md is automatically injected into every agent at start… their only constraint is a line budget." Rationale: "model weights are frozen, so it's precisely surprise encounters that are worth capturing so the next agent trajectory is shorter." Status: "early experiment with promising results"; expected to matter more on codebases agents don't own.

**The SQLite experiment.** Input: the 835-page SQLite manual only; "withheld the source code, test suites, SQLite binary, and internet access." Grade: fraction of `sqllogictest` passed; "The swarm was never told the suite existed"; after each run humans reviewed code and run "checking for cheating and shortcuts, and confirming the system was built out evenly." Four model configurations (GPT-5.5 solo; Grok 4.5 solo; Opus 4.8 planner + Composer 2.5 worker; Fable 5 planner + Composer 2.5 worker). New harness beat old in every mix; all new configurations eventually passed 100%; by the 4-hour cutoff new runs were 73–85% vs old 11–77%. Grok 4.5 new: 80% in four hours; old Grok run "spiraled and had to be paused before its second hour."

**Old-vs-new harness numbers (Grok 4.5 unless noted):**

| Metric                          | Old harness                              | New harness                           |
| ------------------------------- | ---------------------------------------- | ------------------------------------- |
| Commits (first 2h)              | 68,000 (~70× the new run's pace)         | ~970 (implied by the 70× comparison)  |
| Merge conflicts                 | >70,000 before pause, accelerating       | <1,000 over full 4h                   |
| Hottest file                    | 7,771 conflicts, touched by 1,173 agents | 47 conflicts                          |
| Rust crates                     | 54, incl. three separate SQL packages    | 9, settled early, never added another |
| LOC to pass suite (Fable 5 mix) | 64,305                                   | 9,908                                 |
| LOC to pass suite (Opus mix)    | 19,013 at 97%                            | 4,645 at 100%                         |

**Model economics, exact figures.** Cost range across mixes: $1,339 (Opus 4.8 + Composer 2.5) to $10,565 (GPT-5.5 throughout). "Workers carrying at least 69% of the tokens, and over 90% in most" runs. In the Opus/Composer hybrid, Opus-as-planner was "a small fraction of the tokens but roughly two-thirds of the cost," while Composer workers did "the vast majority of the tokens for the remaining third of the cost." GPT-5.5 workers alone: $9,373. Entire Composer 2.5 worker fleet: $411. The Fable 5 planner had a smaller bill than Opus 4.8 "despite roughly twice the per-token price, because it used far fewer planning tokens," but its workers "went through several times as many tokens," making the run substantially more expensive overall.

**Specs as prompts.** "With swarms, the unit of work becomes the spec." "What was scarce in this experiment… is the right description of intent." The swarm "starts to resemble a compiler… The difference is that a compiler preserves meaning at every step while the swarm is probabilistic at every one. Everything described in this post exists to close that gap."

**Model-fit footnote.** They wanted GPT-5.6 Sol as the frontier configuration but it "appears more sensitive to literal and emphasized wording than the others we tested, and we encountered runaway spirals unlike anything the other models produced"; with no time to tune prompts per model they fell back to GPT-5.5.

**Published artifact.** `github.com/cursor/minisqlite` is public for the solo Opus 4.8 run (see 2.8); they had "not done a deeper manual analysis."

### 2.4 What we've learned building cloud agents — Josh Ma, Cursor (2026-06-02)

Source: <https://cursor.com/blog/cloud-agent-lessons>. Production reliability post; the closest analogue to Colony's 46%-non-model-death problem.

**Environment as the product.** "Over the last year we've learned that the single biggest factor in cloud agent output quality is ensuring it has a full development environment, like a developer has." Cloud agents must reconstruct what laptops give for free, "and it's surprisingly hard to tell when you haven't done it perfectly. Instead of a crash or an error message, often the only indication is a subtle degradation in output quality… you might chalk it up to the model." Requirements listed: tools to build the environment; VM hibernate/resume between messages; "pipelines to quickly and durably checkpoint, restore, and fork VM images"; tight harness/client integration. Plus "what is essentially enterprise IT for agents, complete with secret redaction, network policies, and credential management."

**Durability.** Started with "a work-stealing architecture, where worker nodes could pick up agents and loop them to completion" — "a fragile setup — our early beta of cloud agents often operated at one 9 of reliability." They were "on the verge of rebuilding a lot of the durable execution primitives that Temporal already solves," migrated, and "that migration alone took us past two 9s." Scale now: "more than 50 million actions per day across more than 7 million unique workflows"; "more than 40% of our PRs come from cloud agents."

**Workflow shape.** "We've moved from 'eternal' agent workflows to multiple shorter ones that exit after completing a single task, which makes version upgrades easier. We've also split out activities to better capture timeouts and retries as async tool calls, subagents, and inference provider outages have changed our underlying assumptions."

**Decoupling.** Agent loop, machine state, and conversation state are separate components. The loop lives in Temporal, not the VM, enabling independent pod lifecycle management and prewarmed/readonly VMs. Conversation storage is append-only and streams to clients; because steps can fail after partial streaming and be retried, "the client can detect this, rewind its stream, and show the new data instead of the old."

**Harness boundaries — what they removed.** "Early on, we didn't trust the agent very much, so the harness would double-check its work after every task, force a commit, and push. As models got smarter, we started moving logic out of the harness and into tools the agent controls." Multi-repo setups used to require "hardcoded harness behavior"; now the agent gets the repo layout and branch/PR tools and decides. CI Autofix used to grab job failure logs and write them to the VM; now "we just give the agent access to the GitHub CLI and automatically write large outputs to files it can search through. The notification to the agent got much simpler." The harness remains, but "what it contains is changing" (e.g. a computer-use subagent with its own model routing, prompting and screen recording, whose VNC/Chrome belongs to the shared environment).

**Cloud-specific prompting.** "Cloud agents also need different kinds of prompts in the harness than local agents do. We encourage them to be more autonomous, because the cost of blocking is much higher… in the cloud, it could sit there for hours before you go back and check on it."

**Self-healing direction.** Agents should "report when secrets are missing, network access is blocked, or when their environment is otherwise preventing them from making progress, and to then be able to act in a self-healing way" (points to their "autoinstall" research).

### 2.5 Environment-setup companions

Two posts; the second supersedes the first's product framing but both are useful.

**Development environments for your cloud agents (2026-05-13)** — <https://cursor.com/blog/cloud-agent-development-environments>. Thesis: "agents are only as capable as the environments they run in. An agent that can write code but can't run tests, query services, or reach APIs cannot close the loop on its work." Ships: multi-repo environments (enterprise work spans repos; a single-repo agent "has limited usefulness because it can't reason across all the required context"); Dockerfile-based environment config as code with build secrets scoped to the build step; layer caching so cached builds "run 70% faster"; agent-led setup that "will ask you questions, flag missing credentials, and validate that your environment is set up properly"; version history with rollback; per-environment egress allowlists and secret scoping; and a deliberate degradation rule — if environment configuration fails, "Cursor will default to a base image with clear warning signs so that your cloud agents can keep running instead of immediately failing." (Colony parallel: a broken sandbox should degrade visibly, not silently produce worse output.)

**How we set up our cloud agent environment (2026-07-30)** — <https://cursor.com/blog/cloud-agent-environment>. "The development environment is a product in its own right, only one whose users are agents. You have to make cloud match local development, make the repo legible enough that agents can run and test code without tribal knowledge, and keep that environment healthy as the codebase changes."

- **Match cloud to local.** Devs on macOS, VMs on Linux: "we had to agnosticize various dev utilities and setup scripts to work on Ubuntu VMs." Added security: egress restrictions, scoped/proxied git remotes, secret scanning in commits and messages, secret redaction in tool results.
- **Simplify the interface.** "Even after we had our dev setup working on Ubuntu VMs, agents were still bad at running our code… our devex was messy and involved learning and remembering numerous build commands, build flags, and utility scripts. We wrote skills for how to build and run many parts of the system, but this only helped on the margins. Skills can document the right commands, but those commands themselves were convoluted and filled with footguns." Fix: a CLI (`anydev`) to start all services, `--help` menus, and "a supervisor process which monitors and restarts long-running build commands, removing that responsibility from the model entirely." Only then did cloud agents add real value, because they could run and prove their changes end-to-end (with computer use and `recordScreen`), sharing demos on PRs/Slack.
- **Self-healing.** `Cursor Cloud MCP` gives "dynamically discoverable tools with interfaces we could change without rebuilding the agent loop"; agents inspect their own environment (setup failures, egress policy, changed secrets). On top: an automation called **Cloud Doctor** that "periodically checks for failures, remembers which errors might be transient versus salient, does root cause analysis, and can open PRs to fix issues with high confidence." It also inspects other agents' traces "to find where another agent went wrong, which skills or commands were misleading, and which workflows are systematically slow," then fixes the skill, the path, or the environment.
- **Published numbers.** "In December, cloud agents authored roughly one in ten PRs merged to the Cursor monorepo. Today, they write more than half."
- **Readiness checklist (worth reusing verbatim as Colony acceptance criteria).** "1. Do agents have access to the same tools and data a developer would? 2. Can agents find skills that document how your developers actually work? 3. Can agents test and verify core workflows?"

### 2.6 How Cursor Router chooses the right model for the task — Connor O'Keefe & Yuri Volkov (2026-08-06)

Source: <https://cursor.com/blog/how-cursor-router-works>. Production model-routing evidence, relevant to Colony's flash-implementer / strong-reviewer split.

**Architecture.** Routing learned from "how models perform on real developer work, rather than inferred from benchmark scores." Signals: task category, recent tool calls, conversation context. Two stages: **Compass**, a complexity predictor, decides whether a turn is simple enough for a price-efficient model; if not, a **task router** picks a frontier model using a taxonomy of **domains** (backend, database schemas, frontend), **tasks** (fixing bugs, running commands, writing tests) and **modifiers** (bounded edits, product questions, visual-heavy changes).

**Data and labels.** "Hundreds of thousands of turns" of live traffic with privacy settings respected. Performance is inferred from user behavior: "Moving on to the next task is a strong positive signal, while correcting the agent is a strong negative one." Cost is computed from API pricing and token usage, and because it is live traffic it "captures costs that benchmarks often miss, including cache misses caused by switching models."

**Calibration and policy.** Turns Compass rated most likely to succeed got a positive signal 96% of the time; least likely, 71%. Routing rules: a candidate frontier model is eligible only when its observed performance "clears a one-sided 75% uplift threshold against the price-efficient model"; the optimizer then picks the traffic-weighted mix with the largest expected gain inside the mode's cost budget. Evaluated by cross-validation, then a held-out set, then live traffic.

**Results and model strengths.** Auto Intelligence: "above Fable-level user satisfaction at 68% lower cost" (a further 18% reduction since launch). Auto Balance: "outperforms Opus 4.8 at 41% lower cost," plus 3% higher satisfaction. "We found that no model dominates every kind of work": Grok for "broad, routine work" (Git commands, general DB ops); Sol for "planning and codebase comprehension"; Opus for "execution-heavy work… devops, database queries, and performance optimization"; Fable for "debugging and visual implementation."

**Relevance to Colony.** Confirms (a) per-role rather than per-org model choice, (b) that switching models has hidden costs (cache misses), and (c) that the right label for quality is downstream user/consumer behavior, not benchmark score — for Colony, MR survival and absence of repair rounds.

### 2.7 Speeding up GPU kernels by 38% with a multi-agent system — Wilson Lin (Cursor) with Sahil Modi, Yuan Zhang, Edward Lin (NVIDIA) (2026-04-14)

Source: <https://cursor.com/blog/multi-agent-kernels>. A different task shape (open-ended optimization) that stress-tests the same harness.

**Architecture.** "A planner agent that distributed and rebalanced work across autonomous workers based on performance metrics." Notably: "The entire coordination protocol lived in a single markdown file that specified the output format, rules, and tests." The system "independently learned to call the benchmarking pipeline during its runs," forming a test/debug/optimize loop with no developer intervention. Two runs in different languages: CUDA C with inline PTX (low-level) and CuTe DSL ("minimal presence in public training data," learned from provided docs).

**Verification and anti-cheat.** SOL-ExecBench compares against baselines and theoretical hardware limits; "If agents use cheating tactics like caching and deliver performance beyond what a B200 can support, the pipeline invalidates the result."

**Published numbers.** 235 problems generated from 124+ production open-source models; three weeks autonomous; 27 Blackwell B200 GPUs. 38% geomean speedup; beat baseline on 149/235 (63%); 45/235 (19%) exceeded 2×; median SOL score only 0.56. BF16 grouped-query attention: 0.9722 SOL, 84% geomean over baseline, and a 3% end-to-end TTFT improvement when swapped into SGLang. NVFP4 MoE linear: 39% geomean, 0.58 SOL. BF16 GEMM: 86% of a tuned cuBLAS baseline, and up to 9% faster on small-M decode cases.

**Stated limitation (honest capacity accounting).** Hundreds of problems and agents on only 27 GPUs "limited our ability to take full advantage of the multi-agent system."

**Relevance to Colony.** Shows the planner/worker split generalizes beyond "write code to spec" to metric-driven search, and that a single markdown protocol plus a machine-checkable scorer can replace a lot of bespoke orchestration.

### 2.8 FastRender: Wilson Lin's account and Simon Willison's notes (2026-01-19 and 2026-01-23)

Wilson Lin's own FastRender write-ups are the two Cursor posts above (2.1/2.2); his spoken account is the 47-minute interview recorded and annotated by Simon Willison. I read Simon's full written notes, not the video transcript; anything below attributed to the video is as reported by Willison (direct quotes from the video are his transcriptions). Repository docs (`AGENTS.md`, `docs/philosophy.md`) are undated living documents, read 2026-10-21.

**What FastRender is.** A Rust browser engine (HTML/CSS parse, style, layout, paint; desktop shell; embedded JS) built as the benchmark for the swarm, not a product: "We never intended for it to be a production software or usable, but we wanted to observe behaviors of this harness of multiple agents" (Wilson, via [Willison 2026-01-23](https://simonwillison.net/2026/Jan/23/fastrender/)).

**Scale, from the interview.** ~2,000 agents concurrently at peak during the one-week continuous run; "about 300 agents concurrently on each" large machine; "thousands of commits per hour"; nearly 30,000 commits (the GitHub repo showed 29,858 commits when I checked on 2026-10-21). Multiple harnesses ran per workstream on separate machines to parallelize further. Merge conflicts were rare: "the harness itself is able to quite effectively split out and divide the scope and tasks such that it tries to minimize the amount of overlap of work."

**Human role.** "Once you give an instruction, there's actually no way to steer it, you can't prompt it… The only thing you can do is stop it." Longest run ~one week; the research project itself lasted ~three weeks.

**Feedback loops (the part Colony should copy).** Specs are vendored as git submodules — csswg-drafts, tc39-ecma262, whatwg-dom, whatwg-html — and agents cite them in code comments. Visual feedback: screenshots compared against a golden sample ("these models are visual models"). Compiler feedback: "The nice thing about Rust is you can get a lot of verification just from compilation." Model fit: general GPT-5.1/5.2 beat the coding-specialized GPT-5.1-Codex because the instructions were "more expansive than merely coding… how to operate and interact within a harness, or how to operate autonomously."

**Dependency drift (an instruction failure, not a model failure).** The agents chose their own dependencies, including Taffy for flex/grid — which undercuts the from-scratch goal — and vendored QuickJS to unblock JS work while other agents built the real engine. Wilson's diagnosis: "I actually never encoded specifically the level of dependencies we should be implementing ourselves." A later run removes Taffy entirely.

**The throughput trade-off, in his words.** "If you wanted every single commit to be a hundred percent perfect, make sure it can always compile every time, that might be a synchronization bottleneck… errors get introduced, but small errors… then they get fixed really quickly after a few commits… People may say, well, that's not correct code. But it's not that the errors are accumulating. It's a stable rate of errors."

**Simon Willison's own notes (2026-01-19)** — <https://simonwillison.net/2026/Jan/19/scaling-long-running-autonomous-coding/>. He records the initial skepticism: "their GitHub Actions CI was failing and there were no build instructions in the repo," citing a critical post; Cursor fixed the README within 24 hours. He then built and ran it on macOS and posted screenshots: Google's homepage "mostly correct" with mis-styled buttons; his own blog with visible glitches in a background-image quotation mark. His conclusion: "very impressive," clearly not wrapping an existing engine, and the conformance-suite hypothesis is the "cheat code" for AI-built browsers. He also flags the spec-submodule trick as "a smart way to make sure the agents have access to the reference materials."

**The repo's agent instructions (FastRender `AGENTS.md` and `docs/philosophy.md`, read 2026-10-21).** These are the operational artifacts behind the numbers and the best available example of "field guide as instruction surface":

- **Workstream ownership table** — ten workstreams (capability buildout, pageset loop, browser chrome, responsiveness, interaction, JS engine, JS DOM, JS web APIs, JS HTML integration), each with an explicit "Owns / Does NOT own" row. This is Cursor's answer to split-brain at the instruction level.
- **Non-negotiables** — no page-specific hacks or hostname special cases; no spec-deviating "compat shortcuts" ("incomplete is OK; wrong is not"); no post-layout pixel nudging; no panics in production code; keep Taffy vendored and scope it to flex/grid; bounded JS execution.
- **Anti-drift definition of done** — a change counts only if it lands a capability, bugfix, stability, termination, conformance, or UX win _with a regression_; "tooling/infra-only work" and "docs-only work" explicitly do not count: "If you find yourself 'improving the harness' without changing renderer behavior, stop and implement the missing behavior."
- **Operating model** — "90/10 rule" (90% accuracy/capability, 10% perf/infra); priority order "Panics → Timeouts → Accuracy failures → Hotspots → Polish → Spec expansion"; "No vanity work"; "Ruthless triage."
- **Resource safety as agent policy** — every command wrapped in `timeout -k` (SIGKILL fallback because "misbehaving code can ignore SIGTERM"), memory caps (`run_limited.sh --as 64G`), forbidden unscoped `cargo build/test/check` ("you will compile 100+ binaries with LTO… exhaust all RAM, and render the machine unusable"), disk budget with auto-`cargo clean` at 400 GB, scoped test threads. "If a process exceeds limits, treat it as a bug to investigate — not a limit to raise." (Colony's 20-minute watchdog killing a 23-minute test is the mirror image: a limit that punished the workload instead of the pathology.)
- **Evidence requirements** — "Looks better" without artifacts is not evidence; preferred is an offline repro with a golden/regression, acceptable is a deterministic offline Chrome-vs-FastRender diff, best-effort is a cached-HTML diff. Philosophy doc also lists failed and successful patterns from the project's own history ("CSS-only solutions," "batching fixes without validation" failed; "one fix at a time," "simple detection beats complex selectors" worked). This is the Field Guide idea before it was named.

### 2.9 minisqlite README (Cursor, public repo; README read 2026-10-21)

Source: <https://github.com/cursor/minisqlite>. Per the swarm post, this is "the codebase from the solo Opus 4.8 run" (2026-07-20). The README is a specification of the artifact and, implicitly, of what a strong single agent plus verification can produce.

**What it is.** "A reimplementation of SQLite in Rust: the SQL dialect, the query planner and executor, transactions, and the storage engine, down to the official on-disk file format. It opens database files that `sqlite3` wrote and writes files that `sqlite3` reads back." About "200,000 lines of Rust across 14 crates, with 5,650 tests, one external dependency (`elsa`, for the page cache), and no `unsafe` in library code." Public API is "one type, four methods" (`Connection::{open, open_in_memory, execute, query}`); no CLI, C API, or prepared statements.

**Architecture.** 14 crates with "a strict dependency direction; each layer owns one concern and exposes it through one seam": facade → engine → (sql, plan, exec, catalog, pager); plan → expr/funcs; exec → btree; btree → pager; pager → journal/wal/fileformat. A table gives per-crate src LOC (facade 52; engine 4.6k; sql 6.3k; plan 29.5k; exec 20.0k; catalog 14.5k; expr 2.8k; functions 12.2k; btree 6.6k; pager 9.0k; journal 1.2k; wal 1.4k; fileformat 4.6k; types 2.1k).

**Verification (the most transferable part).**

- **Seams enforced by tests**: `crates/minisqlite/tests/seams.rs` pins "exactly one trait per named seam, in its named crate," one `pub fn parse`, no orphan crates ("an unused crate is treated as an abandonment signal"), no behavior-selecting Cargo features, no backup files. Intended refactor style: "expand-then-contract behind these seams."
- **Conformance tests**: 110 `conformance_*.rs` files run only against the public facade; "every expected value is transcribed from the SQLite documentation… never from what the engine currently returns. A failing assertion is the signal that the engine diverges from the spec; assertions are not weakened to pass."
- **Format and durability tests**: byte fixtures "transcribed by hand from the file-format spec," deliberately not produced by the engine's own writers, so "the check is not circular"; tested in both directions (parse fixture, then write and compare byte-for-byte); crash states "fabricated at the byte level (hot journals, torn WAL frames, half-applied checkpoints)" and reopened.
- **Benchmarks**: std-only harness sweeping five workloads at 1k/10k/100k/1M rows, reporting wall clock, peak heap and RSS, plus a durability round trip; "Nothing in it gates a build; the point is to expose a quadratic plan or a statement that copies the whole database."

**Noted discrepancy.** The swarm post reports the _new swarm_ needed 4,645 (Opus mix) to 9,908 (Fable mix) "lines of engine code" to pass the suite, while this README describes a ~200,000-line, 14-crate artifact. These are different artifacts and metrics (solo run vs swarm runs; whole repository incl. tests vs "engine code"), and the post does not reconcile them. Treat both as Cursor's own characterizations; do not use the LoC numbers as directly comparable.

**Relevance to Colony.** The seams-plus-conformance style is exactly what a merge gate and reviewer should be anchored to: machine-checkable architecture invariants and spec-transcribed tests, not reviewer taste. It is also evidence that a long solo run can be steered by a spec plus an executable oracle — but see the caveat that Cursor says it had not deeply reviewed this code.
