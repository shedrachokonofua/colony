# Software factories and cloud coding agents: what their builders published (snapshot: 2026-10-20)

Scope: first-party documentation, engineering blogs, papers and source repositories for the systems named in the brief. Marketing pages are labelled as such; claims that only appear in marketing copy are repeated here as claims, not as measurements. Dates are publication dates where the source states one, otherwise the last-modified or access date. No vendor was contacted. "Factory" here means a system that takes a unit of work end-to-end to a merge request; "coding agent" means a single interactive or background session. Colony is both, so both are covered.

## What this means for Colony

1. **Nobody runs a planner/implementer/reviewer chain with a rigid spec contract.** Cognition moved from "Don't Build Multi-Agents" (2025) to a 2026 position where writes stay single-threaded and only read-only intelligence is parallelized; OpenAI's Symphony tells orchestrators to give agents _objectives, not strict transitions_; Factory's mission orchestrator is a conversational agent the operator can steer and re-plan. Colony's "implementer may not deviate from spec or findings" rule is the outlier — and it is the direct cause of failure 1 ([Cognition](https://cognition.com/blog/multi-agents-working), [Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/), [Factory](https://docs.factory.ai/missions/overview)).
2. **Blocking on impossible requirements should be rare because peers move adjudication into the loop, not up to the human.** Devin's coding agent and Devin Review iterate natively, with the coder filtering findings against its broader context before a human sees the PR; Jules adds a _Planning Critic_ to the auto-approval path and reports a 9.5% cut in task failures ([Devin](https://cognition.com/blog/how-cognition-uses-devin-to-build-devin), [Jules changelog 2026-01-26](https://jules.google/docs/changelog)).
3. **The strongest published lesson on harnesses is subtraction.** Anthropic deleted context resets once Opus 4.5 removed the behaviour they compensated for, then deleted sprint decomposition once Opus 4.6 could sustain long tasks; Cursor deleted its integrator role because it became a bottleneck; Symphony deleted its repository coupling and Linear MCP server. Anthropic's rule: every harness component encodes an assumption about what the model cannot do, and those assumptions go stale ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps), [Cursor](https://cursor.com/blog/scaling-agents), [Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/)).
4. **Failure 2 (mechanisms colliding) is a known failure mode with a known fix: decouple policy from execution.** Cursor moved from in-process coordination to Temporal-backed durable workflows, reports that the migration took it "past two 9s of reliability", and says over 40% of Cursor's PRs now come from cloud agents; OpenHands restricts its watchdog to deterministic merge decisions and routes everything else to a reviewer; Symphony's spec deliberately does _not_ mandate sandbox, approval or merge policy ([Cursor](https://cursor.com/blog/cloud-agent-lessons), [OpenHands](https://docs.all-hands.dev/usage/software-factory), [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)).
5. **Failure 3 (frontier architect thinking into the output cap) is an artifact of unbounded planning steps.** Peer harnesses keep the planner deliberately high-level (granular specs cascade errors), persist plan state outside the context window (JSON feature lists, checked-in exec plans), and expose per-step model _and reasoning-effort_ settings rather than running everything at max effort ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps), [Anneal](https://github.com/mosonlab/anneal), [Factory reference](https://docs.factory.ai/missions/reference), [Kiro models](https://kiro.dev/docs/models/)).
6. **Failure 4 (sandbox ≠ CI) is treated as an environment-contract problem, not a review disagreement.** GitHub's coding agent literally runs inside GitHub Actions, with setup steps defined as an ordinary workflow file that is validated on PRs and can target self-hosted runners "to match how you run CI/CD"; Cursor calls environment quality "the single biggest factor" and describes silent output degradation when it is incomplete; Jules and Devin make fixing CI the agent's own job ([GitHub](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment), [Cursor](https://cursor.com/blog/cloud-agent-lessons), [Jules](https://jules.google/docs/changelog)).
7. **Failure 5 (serial chains, 3 h cheap runs) is countered by smaller units and wider parallelism.** Devin's own guidance is a ~3-hour rule per session; Copilot enforces a hard 59-minute session cap and tells users to split work; Kiro builds a dependency graph and runs waves concurrently; OpenHands' documented factory runs six parallel developers; Ralph deliberately sizes each story to one context window ([Devin docs](https://docs.devin.ai/get-started/devin-intro), [GitHub best practices](https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/coding-agent-best-practices), [Kiro](https://kiro.dev/docs/specs/parallel-task-execution/), [Ralph](https://github.com/snarktank/ralph)).
8. **"Just use stronger models" is not what the strongest shops do — but a too-weak primary does cap quality.** Jules' default _base_ model is Gemini 3 Flash; Cursor's learned router beats a frontier model's satisfaction at 68% lower cost; Factory documents "strong orchestrator + faster worker" as the common cost-quality trade-off; Cognition found SWE-1.5 "not good enough" as a primary because the primary sets the quality ceiling ([Jules 2026-01-30](https://jules.google/docs/changelog), [Cursor router](https://cursor.com/blog/how-cursor-router-works), [Factory](https://docs.factory.ai/missions/reference), [Cognition](https://cognition.com/blog/multi-agents-working)).
9. **Verification is a loop before it is a gate.** Devin's clean-context Devin Review iterates natively with the coder (~2 bugs/PR with 58% severe); OpenAI's harness iterates until "all agent reviewers are satisfied"; Anneal runs two blind reviews, an adjudication step, then mechanical merge checks; Bugbot's default finding status is `neutral`, and only an opt-in makes unresolved findings fail the check ([Devin](https://cognition.com/blog/multi-agents-working), [OpenAI](https://openai.com/index/harness-engineering/), [Anneal](https://github.com/mosonlab/anneal), [Bugbot docs](https://cursor.com/docs/bugbot)).
10. **Published outcomes are real but modest, and nobody publishes Colony's intervention rate as normal.** Symphony: ~500% more landed PRs in three weeks "among some teams"; Cognition: 659 merged Devin PRs in one week; Cursor: >40% of PRs from cloud agents; Jules: −9.5% failures. Colony's ~4 interventions per merged task is the metric to attack, not a fact of life ([Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/), [Cognition](https://cognition.com/blog/how-cognition-uses-devin-to-build-devin), [Cursor](https://cursor.com/blog/cloud-agent-lessons), [Jules](https://jules.google/docs/changelog)).

## Factory (Factory.ai): Missions, Droids, Mission Control

Sources: [Missions overview](https://docs.factory.ai/missions/overview), [Missions planning](https://docs.factory.ai/missions/planning), [Missions reference](https://docs.factory.ai/missions/reference), [announcement 2025-02-26](https://factory.ai/news/missions), [product page](https://factory.ai/product/missions). Docs accessed 2026-10-20.

- **(a) Decomposition and size.** Missions is the most explicit published decomposition model found. The documented heuristic is **1–500 features** per mission; work is grouped into **milestones**, and the operator "collaborates with Droid upfront to build a plan (features, milestones, and the skills needed to accomplish each)". The plan is approved before execution; the mission orchestrator then manages workers and can "re-plan around the obstacle, reorder features, and steer individual workers". Planning guidance: "The biggest value we have found in Missions is in the planning phase … Getting the upfront plan right (the features, the ordering, the milestones, the skills involved, and what gets validated) … determines whether the execution succeeds". Validation-milestone frequency is a planning decision, and the reference says a single milestone is often enough for "smaller, straightforward projects".
- **(b) Single vs multi-agent; authority.** `[orchestrator agent] → [worker agents]`, plus a **separate validator role**. Mission mode "uses the session state to track plan and worker state". Model and reasoning effort are configurable _per role_:
  - `--worker-model`, `--worker-reasoning-effort`
  - `--validator-model`, `--validator-reasoning-effort`
  - `--orchestrator-model`, `--orchestrator-reasoning-effort`

  The reference's own tip: "Pairing a strong orchestrator model with a faster worker model is a common cost-quality tradeoff." Workers are "Droids running in their own sessions"; skills are available to all of them; subagents are restricted by `missionPolicy`.

- **(c) Human in the loop.** Plan approval; live steering through `/missions` (Mission Control); `droid exec --mission` for headless/CI execution; enterprise `missionPolicy` restricts who may start missions at all (`allowAllUsers` vs `allowedUsers`). Troubleshooting guidance is explicitly operator-driven: if a worker "is stuck or taking too long", "the orchestrator can mark the worker's current task as complete and move on" — the human tells the orchestrator, there is no automatic kill rule. Other listed remedies: "worker hit retry limits" → adjust budgets; "validation failing" → disable QA in settings or improve the setup.
- **(d) Environment and CI parity.** Missions require an **Agent Readiness Level of 4+** and the project to be startable/mockable from a script, with logs written to the filesystem "where Droid can inspect them". The QA/validation section is a checklist for _agent-verifiable_ environments: one-command start, logs to disk, agent-drivable inputs (it names `tuistory` and `agent-browser`), and "validate what users see with the browser" rather than only HTTP responses. If QA-style validation is unusable, the docs say to disable it rather than fight it.
- **(e) Verification.** Validation runs at milestone boundaries; "Validation surfaces issues that require follow-up work, and the orchestrator can create additional fix features during execution". Cost model: `total runs ≈ #features + 2 × #milestones` — "a floor rather than a ceiling". Two validation styles are documented: QA-style automation and **user-testing** (scripted agent testers). Validation milestones are skippable.
- **(f) Model choice.** Model independence is a product claim; the concrete routing guidance is the strong-orchestrator/fast-worker tip above, with per-role reasoning effort.
- **(g) Outcomes.** No merge rate, autonomy duration or intervention rate is published. The announcement's claim is scope, not measurement: "whether they take six hours or six days" (2025-02-26).
- **(h) What they simplified or removed.** Nothing published about removals. Open questions in the overview are notable: "Is parallelization necessary? … we are testing this", which suggests parallelism is not assumed for small missions.

## Cognition (Devin): the reversal, and what actually survived

Sources: [Don't Build Multi-Agents, 2025-06-12](https://cognition.com/blog/dont-build-multi-agents), [Multi-Agents: What's Actually Working, 2026-04-22](https://cognition.com/blog/multi-agents-working), [How Cognition uses Devin to build Devin, 2026-02-27](https://cognition.com/blog/how-cognition-uses-devin-to-build-devin), [Devin intro](https://docs.devin.ai/get-started/devin-intro), [When to use Devin](https://docs.devin.ai/essential-guidelines/when-to-use-devin), [AI productivity measurement, 2026-06-04](https://cognition.com/blog/ai-productivity).

- **(a) Decomposition and size.** The 2025 essay argued the opposite of decomposition: "Context Engineering … single-threaded linear agent", because parallel subagents make conflicting implicit decisions and the summarizer loses detail. The 2026 follow-up keeps that for _writing_: "we write code in a single thread" but "we build intelligence in parallel". The practical split is **multi-agent for read-only intelligence** (search, review, exploration, verification) and **single-threaded for writes**. Devin's own docs give the size rule of thumb: "As a rule of thumb, if you can do it in three hours, Devin can most likely do it"; "break down large tasks into smaller ones"; "keep individual sessions small"; use multiple parallel Devin sessions. The build-Devin post adds: "Large-scale challenges should be broken into smaller, isolated tasks across separate sessions."
- **(b) Roles and authority.** Current Devin stack, as described by its own builders:
  - A **manager Devin** can spawn and coordinate child Devins via an internal MCP server ("Manager Devin: break task into pieces, spawn child Devins, coordinate via internal MCP"). Their warning: "overly prescriptive managers backfire: agents assume shared state … agents assume other agents' work is correct, and don't validate their assumptions". Their preferred pattern is "map-reduce-and-manage" with a clean-context reviewer.
  - **Devin Review** runs on every PR. The reviewer has a **completely clean context** and can be the same model as the coder: "putting the same model in two agents … does not quite make them self-biased/correlated", and the clean context "makes the agent smarter". Reported yield: "2 bugs per PR, of which roughly 58% are severe".
  - The **communication bridge** is what prevents loops and scope creep: the coding agent uses its broader context to filter review findings, which Cognition calls "key to preventing looping, disobeying the user, doing work that is out of scope", and says models make "reasonable judgment calls" here with dedicated prompting.
  - **Autofix**: "Devin also tackles CI/lint issues until all checks pass, closing the agent loop". **Playbooks** let operators pin procedures, including "Forbidden actions".
- **(c) Human in the loop.** Ask Devin for scoping before implementation; plan/session visibility; Devin Review output is visible on the PR; humans still review PRs but the stated aim is "most bugs resolved before human opens PR". Devin can be corrected in-session, and corrections persist via Memory/Skills. The productivity paper's workflow is human-authored prompts with human merge decisions, and its measurement deliberately filters to _merged_ PRs.
- **(d) Environment and CI parity.** Workspace setup is called out as a first-class failure source: "If Devin is struggling with its dev environment, revisit the Workspace setup". Autofix closes the CI loop itself. The build-Devin post describes running Devin against large monorepos, with "verification mechanisms in place" as the stated precondition for autonomy, and a CI-triage playbook (`!triage-bug`) that reproduces failures before fixing.
- **(e) Verification.** Devin Review (clean context) iterates natively with the coding agent, plus Autofix on CI/lint. Daily **design-system audit** agents file Linear tickets and open fix PRs — verification as continuous background work rather than a terminal gate.
- **(f) Model choice.** The 2026 follow-up is the most candid published account: "SWE-1.5 was not good enough to be our primary model. The quality ceiling is set by your primary model. A smarter primary model makes the whole system better." They paired **SWE-1.5 (fast) for planning with Sonnet 4.5** for the hard steps ("smart friend"), and reported "cross-frontier: Claude + GPT worked in production". They also note prompt/harness asymmetry: "more context engineering than we expected".
- **(g) Outcomes.** 659 merged Devin PRs in a week (2026-02-27) versus a 2025 best week of 154; ~8x enterprise usage over six months; Devin Review averages 2 bugs/PR with 58% severe (self-reported, 2026-04-22). The productivity paper (2026-06-04) reports a within-user estimator with `r_log = 0.74` across 258 sessions from 126 users, and explicitly argues merged-PR counts and lines of code are poor proxies.
- **(h) Simplified/removed.** The intellectual reversal itself: from "don't build multi-agents" to a taxonomy of where multi-agent works, with the write path kept single-threaded. They discarded "manager writes detailed specs for children" as an anti-pattern and replaced it with objectives plus a clean-context reviewer.

## OpenAI: Codex cloud, harness engineering, Symphony

Sources: [Harness engineering, 2026-02-11](https://openai.com/index/harness-engineering/), [Symphony announcement, 2026-04-27](https://openai.com/index/open-source-codex-orchestration-symphony/), [Symphony SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md), [openai/symphony](https://github.com/openai/symphony).

- **(a) Decomposition and size.** The harness post is a report from a product with **zero human-written code**: ~1M LOC, ~1,500 PRs by three engineers (≈3.5 PRs/engineer/day), with _single agent runs of six or more hours_. Work is decomposed by **execution plans checked into the repository** ("exec-plans … checked into the repo"), so plan state is durable and inspectable. Agents are expected to work "for six hours or more" in one run, which is the longest published single-run figure found. Symphony adds a second layer: tasks are a **DAG** ("tasks … unblocked only"), created in Linear, and agents may "file new issues for out-of-scope improvements" rather than expanding scope silently. The docs recommend tasks sized so that one agent can finish one issue in one run.
- **(b) Roles and authority.** The core loop is one implementer with **local and cloud reviewer agents**: "review own changes locally, request additional specific agent reviews locally and in the cloud, respond to feedback, iterate until all agent reviewers are satisfied (Ralph Wiggum Loop)". Humans "may review PRs but aren't required to". Symphony's stated redesign lesson is the key authority finding: **"treating agents as rigid nodes in a state machine doesn't work well"**; they moved from strict transitions to giving agents objectives and tools (`gh` CLI, CI-log skills), letting them "cook". Orchestrator authority is therefore _goal-setting and scheduling_, not step sequencing.
- **(c) Human in the loop.** Escalation is explicit: "Escalate to a human only when judgment is required". Symphony's workflow handoff state is configurable in `WORKFLOW.md` — a successful run may end at **Human Review** rather than merged, and the spec deliberately does **not** mandate sandboxing, approval or merge policy: those are the deployer's choices. Symphony itself is "not maintained as a product".
- **(d) Environment and CI parity.** The harness post is unusually concrete: each worktree boots the app and drives it through **Chrome DevTools Protocol**; each worktree has its own **observability stack** (LogQL/PromQL queries); lint rules carry custom error messages that "inject remediation" into the agent's context. Local validation is expected to match CI, and "flakes are addressed with follow-up runs" rather than muted. Symphony runs an isolated **per-issue workspace** and watches CI: "watches CI, rebases, resolves conflicts, retries flaky checks, shepherds to merge".
- **(e) Verification.** Layered: local self-review → targeted reviewer agents locally and in the cloud → CI → "all agent reviewers satisfied" → merge. Mechanical enforcement is preferred over prose: custom linters, structural tests, and a "minimal blocking merge gate". They also ran **garbage collection**: recurring cleanup tasks guided by golden principles, because "Fridays cleaning AI slop didn't scale".
- **(f) Model choice.** Not disclosed as a routing table. The reported practice is homogeneous Codex agents with review specialization by prompt. Symphony's `SPEC.md` treats the coding agent as a pluggable component behind an app-server JSON-RPC boundary.
- **(g) Outcomes.** 0 human-written lines / ~1M LOC / 1,500 PRs / 3 engineers (2026-02-11). Symphony: **"500% increase in landed PRs in the first three weeks among some teams"** (2026-04-27). No external merge-rate benchmark is published; the PR and LOC figures are internal to OpenAI.
- **(h) Simplified/removed.** Symphony removed the dependency on internal repositories and on the Linear MCP server: "removed a lot of incidental complexity"; Linear is now the _control plane_, not an integration. The harness post records the anti-pattern of one giant `AGENTS.md` and replaced it with a ~100-line table of contents plus progressive disclosure. They also abandoned manual "AI slop cleanup days" for scheduled, repeating cleanup tasks.

## GitHub Copilot coding agent

Sources: [About the coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent), [best practices](https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/coding-agent-best-practices), [customizing the agent environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment). Docs accessed 2026-10-20.

- **(a) Decomposition and size.** The unit is the **issue or PR assignment**: "assign an issue to Copilot … Copilot works in the background, then requests a review from you". Hard limit: **one session is capped at 59 minutes and "cannot be extended or bypassed"**, and the agent works on **one branch at a time, one PR per task**. Best-practices guidance therefore pushes decomposition onto the human: "break complex tasks into smaller, well-scoped issues" and "keep tasks focused".
- **(b) Single vs multi-agent.** Single agent, no planner/implementer split. The agent may be asked to review PRs and leave comments (`/copilot review`), but its own output is a pull request for human review; merge remains governed by branch protection and repository review rules. Repository-scoped by design.
- **(c) Human in the loop.** Assignment, session-log visibility, PR review, merge. The agent opens a pull request rather than landing it; the session log is the audit surface. Custom instructions (`copilot-instructions.md`, `AGENTS.md`) and **Copilot Memory** shape behaviour without a plan-approval gate.
- **(d) Environment and CI parity.** This is the strongest CI-parity design found: the agent's environment **is GitHub Actions**. A single `copilot-setup-steps` job preinstalls tools/dependencies; "the setup steps file runs as a normal GitHub Actions workflow", so it is validated whenever it changes and can be debugged like CI. It supports larger runners and **self-hosted runners "to match how you run CI/CD"**, recommends ephemeral single-use runners, and gives the agent `actions: read` so it can read CI results. Git LFS is handled by adding an `actions/checkout` step with `lfs: true`. Limits: Ubuntu/Windows runners only, no macOS; firewall configurable.
- **(e) Verification.** CI plus the agent's own iteration on failing checks; the agent can read workflow results and push fixes. A separate [Copilot code-review](https://docs.github.com/en/copilot/concepts/agents/code-review) pass can comment and gives an approval assessment; by default its reviews do not count toward required approvals, though repositories can enable Copilot approvals. No adversarial reviewer beyond that.
- **(f) Model choice.** Model is selectable per task from the supported list; no published routing policy. This is "bring your own preference", not a router.
- **(g) Outcomes.** No merge rate, acceptance rate or autonomy-duration metric is published in these pages. The 59-minute cap is the only hard number.
- **(h) Simplified/removed.** Nothing published as a removal; the notable simplification is architectural — no custom sandbox, no bespoke environment builder, just Actions with a setup workflow.

## Cursor: background/cloud agents, Bugbot, the scaling post-mortem, and the router

Sources: [Scaling long-running autonomous coding, 2026-01-14](https://cursor.com/blog/scaling-agents), [Cloud agent lessons, 2026-06-02](https://cursor.com/blog/cloud-agent-lessons), [How Cursor Router chooses the right model, 2026-08-06](https://cursor.com/blog/how-cursor-router-works), [Bugbot docs](https://cursor.com/docs/bugbot), [Bugbot product page](https://cursor.com/bugbot). Related posts cited by Cursor: [cloud agent environment, 2026-07-30](https://cursor.com/blog/cloud-agent-environment), [agent swarms and model economics, 2026-07-20](https://cursor.com/blog/agent-swarm-model-economics).

- **(a) Decomposition and size.** Two product shapes: interactive/background agents on a task, and **long-running autonomous coding** where the unit is a _project_ (browser from scratch, framework migration). Sizes are large: "~1M LOC browser in about a week" with the planner/worker/judge system; "Solid → React … three weeks, +266K/−193K lines". This is the most aggressive scale reported by any vendor, and it comes with the most explicit failure analysis.
- **(b) Roles and authority.** The scaling post's first architecture — "flat self-coordination" — failed for four reasons: "locks held and forgotten; twenty agents produced the throughput of two or three; agents became risk-averse; no one took the hard problems; the system drifted". The replacement: **recursive planners** (sub-planners) → **workers** → a **judge** deciding per cycle, with **hundreds of concurrent agents**. Cursor's summary: "planners plan; workers execute; a judge decides whether the cycle continues". They then **removed the integrator role**: "we added an integrator to merge work; it became the bottleneck". The 2026-06 lessons add: "we moved logic out of the harness into tools the agent controls" (CI autofix, multi-repo operations), because harness-embedded policy kept needing upgrades.
- **(c) Human in the loop.** Background agents: user sets task, reviews PR, may attach video/screenshots/logs; "remote desktop takeover" for blocked agents; Slack/GitHub/Linear mentions. Long-running runs: humans define the project and review the result. Cloud lessons: "cloud prompts need to be more autonomous because blocking is expensive" — a human waiting is the failure mode.
- **(d) Environment and CI parity.** "Environment quality is the single biggest factor" for output quality; incomplete environments cause "subtle degradation in output quality" that is hard to attribute. Cloud agents get dedicated VMs with repo, dependencies, secrets and network policy. Lessons include **autoinstall / self-healing environment setup** and treating enterprise IT constraints (proxy, egress, secrets) as product requirements. The 2026-07-30 companion post is titled "How we set up our cloud agent environment" (not read in full here).
- **(e) Verification.** The judge inside long runs; CI autofix as an agent tool; **Bugbot** on PRs. Bugbot runs automatically on every PR update (or on `cursor review` / `bugbot run`), reads existing PR comments "to avoid duplicate suggestions and build on prior feedback", publishes a `Cursor Bugbot` check, and supports **Autofix** (new branch or existing branch). Default finding conclusion is `neutral`; a `failure` conclusion requires opt-in "fail on unresolved issues", and Cursor notes that requiring the check alone "does not block merges on findings". Marketing claim on the product page: "70%+ of flags get resolved before merge".
- **(f) Model choice.** The router post is the most detailed public account of production routing. **Compass** is a learned complexity predictor that scores every request 0–1; a threshold sends the simple tail to a cheaper model and the rest to a stronger one. Requests are classified by domain, task and modifiers (language, framework, context size, tool use). Documented per-model strengths: Grok is positioned as strong value on broad routine work (Git commands, general database operations); Sol on planning and codebase comprehension; Opus on execution-heavy work (devops, database queries, performance optimization); Fable on debugging and visual implementation. Results: Auto Intelligence "delivers above Fable-level user satisfaction at 68% lower cost"; Auto Balance "outperforms Opus 4.8 at 41% lower cost". Router design rule: switch only when predicted uplift exceeds **75%**. They are explicit that this is a _learned_ policy from production outcomes, not a static tier table, and that it will keep changing.
- **(g) Outcomes.** >40% of Cursor's PRs produced by cloud agents; the Temporal migration took the system "past two 9s of reliability"; Temporal handles "more than 50 million actions per day across more than 7 million unique workflows"; router economics above; Bugbot resolution claim above (vendor marketing).
- **(h) Simplified/removed.** Removed the integrator role; moved harness logic into agent tools; replaced "eternal" agent workflows with "multiple shorter ones that exit after completing a single task" because that "makes version upgrades easier"; replaced work-stealing with **Temporal** for durable execution; deleted bespoke plumbing in favour of platform primitives. The through-line: "the harness and models matter, but the prompts matter more" — a claim worth testing against Colony's experience, where prompt/spec rigidity is the observed blocker.

## Google Jules

Sources: [Jules docs](https://jules.google/docs), [FAQ and limits](https://jules.google/docs/faq), [changelog](https://jules.google/docs/changelog), [product site](https://jules.google). Changelog dates as published.

- **(a) Decomposition and size.** Jules is a **VM-based asynchronous agent**: it clones the repo, installs dependencies, writes a **plan**, then executes. The unit is a task/issue, not a mission. Plan review can be **human-approved or auto-approved after a timer**; in the auto-approve path a **Planning Critic** reviews the plan first. Limits (FAQ): Free 15 tasks/day and 3 concurrent; Pro 100/day and 15 concurrent; Ultra 300/day and 60 concurrent. No published task-duration cap.
- **(b) Roles and authority.** Two-agent shape: **planner → executor**, with the Planning Critic as a third, review-only agent (2026-01-26) that will "review all plans that do not require human intervention". The critic is explicitly a _replacement for the human approval gate_ on the fast path, not an extra approval layer. Jules "acts on PR comments" (2025-09-23), so review feedback re-enters the same session.
- **(c) Human in the loop.** Plan approval (or timed auto-approval), PR review, merge. Memory (2025-09-30) carries preferences across sessions; scheduled and suggested tasks (2025-12) move initiation off the human.
- **(d) Environment and CI parity.** The agent runs in a Google-managed VM with the repo checked out and dependencies installed, so the environment is _its own_ rather than the user's CI. The parity mechanism is behavioural: **auto-fix CI failures** (2026-02-19) — the agent reads failing CI and pushes fixes, rather than the human reconciling sandbox vs CI. `AGENTS.md` is supported for repo-level instructions.
- **(e) Verification.** Planning Critic before execution; CI-failure autofix after; PR-comment iteration. No adversarial code reviewer comparable to Devin Review/Bugbot is documented.
- **(f) Model choice.** This is the clearest cheap-tier data point: **Gemini 3 Flash became the base model on 2026-01-30**, described as "faster and significantly more capable than our previous base model, Gemini 2.5 Pro"; **Gemini 3.1 Pro** became selectable on 2026-03-09. So the default executor is a Flash-class model, with a Pro option — the same tiering Colony uses, but with the frontier model in the _planning/review_ seat rather than only in the architect seat.
- **(g) Outcomes.** "9.5% reduction in task failure rates" attributed to the Planning Critic (2026-01-26) — the only published failure-rate eval among the consumer-facing agents reviewed here. No merge rate.
- **(h) Simplified/removed.** No removal narrative published. The notable simplification is the elimination of mandatory human plan approval via the critic + timer.

## Amazon: Kiro and Q Developer

Sources: [Kiro specs](https://kiro.dev/docs/specs/), [feature specs](https://kiro.dev/docs/specs/feature-specs/), [quick specs](https://kiro.dev/docs/specs/quick-specs), [correctness](https://kiro.dev/docs/specs/correctness/), [parallel task execution](https://kiro.dev/docs/specs/parallel-task-execution/), [plan agent](https://kiro.dev/docs/chat/plan-agent/), [steering](https://kiro.dev/docs/steering/), [hooks](https://kiro.dev/docs/hooks/), [autonomous agent](https://kiro.dev/docs/web/autonomous-agent/), [cloud sandbox](https://kiro.dev/docs/web/cloud-sandbox/), [Crew](https://kiro.dev/docs/crew/), [models](https://kiro.dev/docs/models/), [Q Developer](https://aws.amazon.com/q/developer/). Accessed 2026-10-20.

- **(a) Decomposition and size.** Kiro is the most _specification-centric_ design found. A feature spec is three artifacts: `requirements.md` → `design.md` → `tasks.md`, produced in three phases **with review checkpoints** ("Markdown Review"). **Quick Spec** is the explicit escape hatch: "skips the approval gates" for small changes. Parallel execution builds a **dependency graph** and runs **waves**: independent tasks in a wave run concurrently, dependents wait. The autonomous web agent takes a prompt to a PR without a plan gate by default; "Needs attention" is the state for clarification. Crew (2026) is an always-on orchestrator: a task runner that takes a spec file and handles checkpoints, retries, per-step git commits, self-review and pause/resume, plus workflows that act as a declarative graph conductor.
- **(b) Roles and authority.** Kiro _is_ a planner/implementer split in the IDE: spec agent (requirements/design/tasks), then implementation agent, with `steering` markdown as persistent context and **hooks** that can gate tool calls (event-driven policy, e.g. block a command). The autonomous agent "picks the model automatically, delegates to sub-agents" and produces PRs; the operator can steer via commands (`/kiro all`, `/kiro fix`). Crew's agent backends are pluggable and include Claude Code, Codex, OpenCode, Pi, goose and DeepSeek — Kiro Crew is an orchestrator over _other vendors'_ agents, which is a notable 2026 direction.
- **(c) Human in the loop.** Spec review checkpoints (skippable via Quick Spec); "Needs attention" for clarification; PR review/merge. The autonomous agent opens PRs; the operator is not in the execution loop unless a task needs attention.
- **(d) Environment and CI parity.** Web agent runs in a **cloud sandbox** with the repo; property-based correctness checks are generated from the spec (`correctness/`); hooks run deterministic checks at tool boundaries. CI parity as such is not documented; the spec's correctness properties are the substitute for "does CI agree".
- **(e) Verification.** Property-based tests derived from requirements; parallel task waves with per-task checkpoints; Crew's "self-review" step and per-step git commits (so a failed step is recoverable); hooks as enforcement. No published adversarial reviewer model.
- **(f) Model choice.** Kiro exposes a **models page and a reasoning-effort control**; the autonomous agent chooses the model itself, and Crew delegates to external agent backends. Q Developer's page claims agentic capabilities across "implementing features, documenting, testing, reviewing, refactoring" without publishing a routing policy.
- **(g) Outcomes.** No published merge/acceptance rates. Amazon's public positioning for Q Developer is capability breadth, not measured autonomy.
- **(h) Simplified/removed.** The visible simplification is **Quick Spec**: the heavy three-phase gate is optional, acknowledging that most changes don't need it. Crew's pluggable backends suggest Amazon expects orchestration to outlive any single agent implementation.

## Anthropic: Claude Code headless/Actions, and the harness research

Sources: [Building effective agents, 2024-12-19 (updated 2026-08-10)](https://www.anthropic.com/engineering/building-effective-agents), [How we built our multi-agent research system, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system), [Effective harnesses for long-running agents, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Harness design for long-running app development, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps), [Managed agents, 2026-04-08](https://www.anthropic.com/engineering/managed-agents), [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions). Related and cited: [The advisor strategy](https://claude.com/blog/the-advisor-strategy).

- **(a) Decomposition and size.** Two research results matter. The long-running _coding_ harness starts with an **initializer agent** that writes a **`feature_list.json` with 200+ features** — chosen over Markdown because "models are less likely to overwrite a JSON file than a Markdown file" — and then a coding agent implements **one feature at a time**, leaving a clean git state, a progress file (`claude-progress.txt`) and a runnable `init.sh` after every step. The app-development harness (2026-03) adds a **planner/generator/evaluator** triad, with each sprint scoped by a **sprint contract** negotiated between generator and evaluator. The earlier research-system post explicitly warns that **coding is "not yet a good fit" for multi-agent** because it has fewer parallelizable subtasks than research.
- **(b) Roles and authority.** The 2026 harness: planner (high-level, deliberately _not_ granular), generator (implements one sprint), evaluator (tests like a user, files findings). The planner is kept coarse because "granular spec errors cascade". Authority for scope lives in the **sprint contract**, not in a static spec. In Claude Code GitHub Actions, the agent gets a prompt and repository access, and opens a PR; skills and `CLAUDE.md` carry standing instructions. The review workflow is instructed to **skip PRs it judges don't need review** — the reviewer has discretion not to comment.
- **(c) Human in the loop.** Plan review is optional in the harness (the planner/evaluator mediate). In Actions, humans trigger via `@claude` mentions or event-driven automation prompts; write-permission and human-actor checks gate who can invoke. Merge remains human/branch-protection governed.
- **(d) Environment and CI parity.** The coding harness insists on a **runnable init script**, a clean git state per feature, and **browser automation (Puppeteer MCP)** for end-to-end verification — "the model can't verify UI without a browser". The managed-agents post describes the production substrate: **session / harness / sandbox** as three interfaces, "brain decoupled from hands", `wake(sessionId)` for crash recovery, and token isolation (git push via a cloned remote; MCP OAuth via a vault proxy). Reported reliability effect: p50 time-to-first-token −60%, p95 −90% after rebuilding the harness around these interfaces.
- **(d′) Headless/CLI automation.** `claude -p` (or `--print`) runs "the same tools, agent loop, and context management that power Claude Code" non-interactively, with JSON/stream-JSON output and `--json-schema` for machine-readable results and a non-zero exit code on failure. For CI, `--bare` is "the recommended mode for scripted and SDK calls" because it skips hooks, skills, MCP servers, auto memory and `CLAUDE.md`, giving "the same result on every machine"; it will become the default for `-p`. Limits are explicit rather than emergent: a run stops waiting on background work after 10 minutes of idle unless `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` is raised, and `--max-budget-usd` stops remaining work at the cap ([docs](https://code.claude.com/docs/en/headless)).
- **(e) Verification.** Evaluator as a first-class role; the harness post is blunt that a default evaluator is weak: a "poor QA agent out of the box … talks itself into approving". It was made useful by reading evaluator logs and iterating on its prompt, and it is **single-pass at the end** after the sprint construct was removed. The evaluator is judged worth its cost "when the task sits beyond what the current model does reliably solo".
- **(f) Model choice.** The advisor strategy (smaller model calls a larger one for advice) is referenced from Cognition's post as a routing pattern. The harness posts are a natural experiment in **model-capability-driven simplification**: context resets were needed for Sonnet 4.5's "context anxiety" and were **removed** for Opus 4.5; sprint decomposition was **removed** for Opus 4.6. Costs: a solo 20-minute run at $9 versus a 6-hour harness run at $200 for one app; a DAW built in 3h50m for $124.70. Their conclusion: harness complexity must be re-justified per model generation.
- **(g) Outcomes.** The multi-agent _research_ system reported a **90.2% improvement** over a single Opus agent on an internal research eval, with token usage explaining **80% of variance** — but that is research, not coding. No merge-rate metric is published for the coding harnesses.
- **(h) Simplified/removed.** Removed context resets (Opus 4.5), removed the sprint construct and per-sprint evaluator passes (Opus 4.6), and simplified the initializer's job once models improved. The 2026-04 managed-agents redesign removed bespoke session plumbing in favour of three explicit interfaces.

## OpenHands (All Hands AI)

Sources: [Software Factory use case](https://docs.all-hands.dev/usage/software-factory), [documentation index](https://docs.all-hands.dev/), [issue lifecycle](https://docs.all-hands.dev/usage/how-to/issue-lifecycle). Accessed 2026-10-20.

- **(a)/(b) Decomposition and roles.** The documented factory is four automations over a Kanban board: **triage, developer, reviewer, watchdog**. The separation of authority is explicit and is the most Colony-relevant design found:
  - The **reviewer runs with a separate, differently-scoped token** ("3 scoped tokens") and **cannot push code**. It can only comment/request changes.
  - The **watchdog is deterministic**: it merges only when an independent acceptance status and independent CI checks pass on the **exact head SHA**; it does not judge quality.
  - The developer agent works one issue per sandbox; multiple developers can run concurrently (documented demo: six issues, six concurrent devs, all merged).
- **(c) Human in the loop.** Board membership is the human control: moving an issue to "ready for dev" is the approval; PR review and merge policy are configurable; the watchdog's deterministic rule can be replaced by a human merge.
- **(d) Environment and CI parity.** Each developer runs in a **Docker sandbox per issue**; the factory docs stress that acceptance checks must run in the same image/CI as the merge gate. Their own repo requires a **"ready for dev" gate** plus a PR-description check in the issue-lifecycle workflow.
- **(e) Verification.** Reviewer comments on the PR; watchdog merges only on exact-head passing statuses; a **stale-branch path** updates the branch and requires a _fresh_ exact-head review. Their docs also describe "graceful restart resume" so a restarted orchestrator picks up in-flight work rather than duplicating it.
- **(f) Model choice.** The broader product documents LLM profiles with **model switching, routing, fallback, ask-oracle, a stuck detector, a goal-completion judge loop, critic with iterative refinement**, and **ACP agents** (Claude Code, Codex, Gemini CLI, Pi, OpenCode). This is the most modular model layer among open-source factories.
- **(g) Outcomes.** The six-issue concurrent demo is the only concrete outcome; no rate or duration metric published.
- **(h) Simplified/removed.** No removal narrative; the design philosophy is "small deterministic kernel, agentic periphery".

## Sourcegraph Amp

Sources: [Amp manual](https://ampcode.com/manual), [models and subagents](https://ampcode.com/docs/models-and-subagents), [parallel agents](https://ampcode.com/how-to/parallel-agents), [orbs](https://ampcode.com/news/orbs), [agent-to-agent](https://ampcode.com/news/agent-to-agent), [decision models](https://ampcode.com/news/decision-models), [ultra](https://ampcode.com/news/ultra). Docs last-modified 2026-09-14 to 2026-10-14.

- **(a) Decomposition and size.** Amp's primary mode is single-agent with **explicit modes** (low/medium/high/ultra) trading cost for reasoning. Decomposition is delegated to **subagents** the main agent can spawn ("subagents run in isolation and return a single report"), and to **agent-to-agent** coordination (2026-01-07) where one agent can message another with its own ID; `amp sync` shares a thread across machines. Orbs give each task "a fresh, isolated environment" that can sleep and wake, with **spawn pacing** (bursts then one every ~5 minutes) as an explicit resource-control mechanism.
- **(b) Roles and authority.** Roles are configured separately: "the main agent, the oracle, and subagents" each get a model, and "roles stay stable while models change over time". Specialist subagents are **isolated** — "you can't guide a subagent mid-task" — which is a deliberate authority boundary: subagents are for bounded, independent work, not for steering. `amp.ai.decide` (Jev or GPT-6 Luna) is a **decision model** used to adjudicate. The `forbidden-actions` docs page is the policy layer.
- **(c) Human in the loop.** Interactive by default; Puck is a coordinator agent that starts/monitors/steers other agents ("start monitoring, steering agents, coordinate parallel work, split my request across agents and report back"). Automations/event-driven orbs remove the human from routine triggers.
- **(d) Environment and CI parity.** Orbs are the isolation unit; the docs emphasize thread/workspace separation rather than CI identity. No CI-parity mechanism documented beyond running commands the user's environment provides.
- **(e) Verification.** Subagent reports + oracle consultation + decision model; no dedicated adversarial reviewer or merge gate documented.
- **(f) Model choice.** Per-role model assignment with **BYOK** and **model routing**; the manual notes models change over time while roles stay fixed. The "ultra" mode exists precisely because a stronger reasoning budget is a per-task choice, not a global default.
- **(g) Outcomes.** No published merge/acceptance metrics.
- **(h) Simplified/removed.** The agent-to-agent post reads as a walk-back of heavy orchestration: from "manager agents that own workers" to lightweight messaging between peers, plus explicit spawn pacing to stop runaway parallelism.

## Replit Agent

Sources: [Agent 3 announcement, 2025-09-10](https://blog.replit.com/introducing-agent-3-our-most-autonomous-agent-yet), [Agent docs](https://docs.replit.com/replitai/agent). Accessed 2026-10-20.

- **(a) Decomposition and size.** Agent 3 is a single conversational agent that builds an app end-to-end; the docs expose **modes** (Free / Power / Max) that trade credits for autonomy. The announcement claims "10x more autonomous" and "Max Autonomy" runs of **200+ minutes** — the only consumer product publishing a per-run duration in that range.

## Ralph (open-source loop)

Source: [snarktank/ralph](https://github.com/snarktank/ralph), based on [Geoffrey Huntley's Ralph](https://ghuntley.com/ralph/). Repo read 2026-10-20.

- **(a) Decomposition and size.** The loop takes a **PRD** and splits it into `prd.json` stories, each sized to **fit in one context window**. Then: fresh instance per story → implement → run checks (typecheck/tests) → commit only if they pass → mark `passes: true` → append learnings to `progress.txt` → update `AGENTS.md` → next iteration. Default cap: **10 iterations**. Stop condition is an explicit `<promise>COMPLETE</promise>` token, not a heuristic.
- **(b) Roles and authority.** One agent per iteration, no planner/reviewer. Authority is encoded in the loop: the agent may not mark a story complete unless checks pass, and may not continue past the iteration cap.
- **(c) Human in the loop.** The human writes the PRD and reviews the resulting commits/PRs; the loop runs unattended. Amp's auto-handoff at ~90% context is the documented way to keep a session going.
- **(d) Environment and CI parity.** The repo insists that **feedback loops must exist and CI must stay green — "broken code compounds"**. UI stories require browser verification before being marked passing. The loop starts each iteration from a clean checkout, which makes environment drift visible immediately.
- **(e) Verification.** Deterministic checks (typecheck, tests, browser) gate the commit; progress notes are the audit trail; `AGENTS.md` accumulates corrections so the next iteration starts smarter.
- **(f) Model choice.** Model-agnostic; the design assumes a _cheap enough_ model to run many iterations, and compensates with fresh context rather than a stronger model.
- **(g) Outcomes.** No published metrics; the artifact is a reproducible loop, not a benchmark.
- **(h) Simplified/removed.** Ralph is itself a simplification: it removes multi-agent orchestration, vector memory and long-lived context in favour of **one story, one context, one commit**. Its popularity is evidence that the minimal loop is a viable baseline.

## Anneal (open-source loop)

Source: [mosonlab/anneal](https://github.com/mosonlab/anneal). Repo read 2026-10-20.

- **(a)/(b) Decomposition and roles.** Anneal is the closest published analogue to Colony's chain, made explicit as a **12-step workflow**: spec → plan → plan review → revise → implement → **two blind code reviews** → apply fixes → docs → regression → **mechanical merge readiness** → merge execution. Two properties stand out:
  - **"Whoever wrote the code never judges it"** — the implementer is excluded from review.
  - **Roles are data**: each step's model and reasoning effort are configuration, editable without code changes.
  - The two reviews are **blind** (neither sees the other), which reduces anchoring; a later step adjudicates findings before fixes.
- **(c) Human in the loop.** The pipeline "stops only when a human decision is needed": an **Inbox** for questions, gated steps, and escalations. This is a designed escalation channel rather than an exception path.
- **(d) Environment and CI parity.** Regression runs before merge readiness; merge readiness **recomputes the head**, requires regression **PASS evidence**, performs a **server-side ancestry check**, and authorizes only the **exact head** it validated; merge execution re-verifies preconditions immediately before merging. This is the most rigorous published merge gate found.
- **(e) Verification.** Two blind reviews + adjudication + regression + mechanical gate + pre-merge re-check.
- **(f) Model choice.** Per-step model/effort configuration; the docs describe assigning stronger models to review/adjudication and cheaper ones to implementation.
- **(g) Outcomes.** Anneal is reported to be built by Anneal itself (self-hosting claim); no external metric. Runs on the user's own subscriptions; the repo warns the agent is **unsandboxed**.
- **(h) Simplified/removed.** No removal narrative; the design is deliberately linear and inspectable rather than adaptive.

## Cross-cutting lessons, mapped to Colony's five failures

### Failure 1 — implementers forbidden to deviate, so wrong requirements become human blocks

Every peer that has published on this treats **spec deviation as a routing decision, not a compliance failure**.

- OpenAI's Symphony tried strict state-machine transitions and rejected them: "treating agents as rigid nodes in a state machine doesn't work well"; they moved to giving agents objectives and tools instead of strict transitions, letting them "cook" ([Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/)).
- Cursor's lesson is the same at the harness level: "we moved logic out of the harness into tools the agent controls" because harness-embedded policy could not keep up ([Cursor](https://cursor.com/blog/cloud-agent-lessons)).
- Factory's orchestrator is explicitly allowed to "re-plan around the obstacle, reorder features, and steer individual workers", and the operator can tell it to mark a worker's task complete and move on ([Factory](https://docs.factory.ai/missions/overview)).
- Jules replaces the human approval gate with a **critic** on the auto-approve path, and attributes a 9.5% failure reduction to it ([Jules](https://jules.google/docs/changelog)).
- Devin's reviewer findings are filtered, not obeyed literally: the coding agent uses its broader context to decide which findings are in scope and fixes them in the same session, while the reviewer's clean context is what makes the findings valuable ([Cognition](https://cognition.com/blog/multi-agents-working)).
- Anneal goes furthest on adjudication: two blind reviews, then a step that **adjudicates** findings before fixes, with an **Inbox** for genuine human decisions ([Anneal](https://github.com/mosonlab/anneal)).

**Mapping.** Colony's 10/10 human blocks in one project are the predicted outcome of making "deviation" illegal while the cheap implementer often already knows the requirement is wrong. The peers' pattern is: implementer may _propose_ a deviation, an adjudicator (reviewer + a synthesis step, or a critic) decides, and only unresolved judgment calls reach the human. The human block should be the _last_ rung, not the only legal way to disagree.

### Failure 2 — colliding mechanisms: watchdog kills legitimate tests, steering silently fails, scopes park with runnable work

- **Mechanism sprawl is the diagnosed disease.** Anthropic: "every component in a harness encodes an assumption about what the model can't do … stress testing … they can go stale", and they deleted two components as models improved ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Durable execution beats local watchdogs.** Cursor replaced in-process coordination with Temporal-backed workflows; the migration took it "past two 9s of reliability", and >40% of its PRs now come from cloud agents ([Cloud agent lessons](https://cursor.com/blog/cloud-agent-lessons)).
- **Keep the deterministic kernel small and narrow.** OpenHands' watchdog does exactly one thing — merge when independent acceptance and CI statuses pass on the exact head — and everything else is the reviewer's job; their reviewer cannot push code ([OpenHands](https://docs.all-hands.dev/usage/software-factory)).
- **Steering must be a real channel, not a spec edit.** Factory's Mission Control lets the operator talk to the orchestrator mid-run; Amp's Puck is a coordinator that "starts, monitors and steers agents"; Cursor's background agents accept remote desktop takeover. None of them implement steering as an asynchronous amendment to a frozen document ([Factory](https://docs.factory.ai/missions/overview), [Amp](https://ampcode.com/manual), [Cursor](https://cursor.com/blog/cloud-agent-lessons)).
- **Timeouts and budgets should be explicit settings, not inferred liveness.** Claude Code's headless mode documents a default 10-minute background-wait ceiling (overridable) and a `--max-budget-usd` cap that stops remaining work; Cursor's Temporal migration split activities out "to better capture timeouts and retries". Colony's 20-minute tool watchdog killed 23-minute tests because it inferred legitimacy from silence rather than from a declared budget ([Claude Code](https://code.claude.com/docs/en/headless), [Cursor](https://cursor.com/blog/cloud-agent-lessons)).
- **Parking with runnable work is a scheduler bug, and peers schedule on dependencies, not phases.** Symphony runs a DAG and only starts unblocked tasks; Kiro computes waves from a dependency graph; OpenHands resumes in-flight work after restart instead of re-queuing or parking the whole scope ([Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md), [Kiro](https://kiro.dev/docs/specs/parallel-task-execution/), [OpenHands](https://docs.all-hands.dev/usage/software-factory)).

**Mapping.** The 20-minute tool watchdog vs 23-minute tests is a _local_ timeout with _global_ consequences; the spec-amendment steering that failed 9/9 is a mechanism that was never observable. Peers' answer is: one deterministic merge gate, explicit and observable steering channels, dependency-based scheduling, and a willingness to delete mechanisms rather than add compensations.

### Failure 3 — frontier architect spends whole turns thinking into the 64k output cap

- **Planners are kept coarse on purpose.** Anthropic's 2026 harness uses a high-level planner because "granular spec errors cascade"; sprint contracts bound what a single planning step must produce ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- **Plan state lives outside the context window.** OpenAI checks exec plans into the repo; Anthropic's initializer writes a 200+ feature JSON file specifically because models preserve JSON more reliably than Markdown; Ralph writes `prd.json` plus `progress.txt` per iteration ([OpenAI](https://openai.com/index/harness-engineering/), [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Ralph](https://github.com/snarktank/ralph)).
- **Effort should be a per-step setting.** Factory exposes `--orchestrator-reasoning-effort` and per-role variants; Kiro documents a reasoning-effort control; Anneal stores model and effort per pipeline step; Amp exposes low/medium/high/ultra as a per-task choice ([Factory](https://docs.factory.ai/missions/reference), [Kiro](https://kiro.dev/docs/models/), [Anneal](https://github.com/mosonlab/anneal), [Amp](https://ampcode.com/manual)).
- **A max-effort turn that loses its work is a checkpointing failure.** The peers all persist intermediate artifacts (plans, progress files, per-step commits) so a truncated turn is recoverable; none relies on a single long generation as the unit of state.

**Mapping.** Colony's architect should not be allowed to spend an unbounded single turn at max effort with no durable artifact. Bound the planning step, persist a structured plan (features/tasks with acceptance criteria) incrementally, and make the effort setting a per-role/per-step knob. The model may still be frontier; the _turn_ must be finite and its output must land somewhere other than the lost context.

### Failure 4 — sandbox differs from CI (tool versions, glibc), causing reviewer/implementer/CI disagreements

- **Define the environment as a CI artifact.** GitHub Copilot's agent runs _in_ Actions, with `copilot-setup-steps.yml` executed as a normal workflow, validated when it changes, and optionally on self-hosted runners "to match how you run CI/CD" ([GitHub](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)).
- **Environment quality is a measured first-order effect.** Cursor: "environment quality is the single biggest factor", with incomplete setups producing "subtle degradation in output quality" ([Cursor](https://cursor.com/blog/cloud-agent-lessons)).
- **Boot the real app.** OpenAI boots the app per worktree and drives it over Chrome DevTools Protocol, with per-worktree observability queries; the harness post treats "can the agent run and observe the system?" as table stakes ([OpenAI](https://openai.com/index/harness-engineering/)).
- **Make CI reconciliation the agent's job.** Jules auto-fixes CI failures; Devin's Autofix iterates on CI/lint until checks pass; Symphony watches CI, rebases, retries flakes and resolves conflicts; Copilot can read Actions results. None of them ask a reviewer to arbitrate "sandbox says pass, CI says fail" ([Jules](https://jules.google/docs/changelog), [Cognition](https://cognition.com/blog/how-cognition-uses-devin-to-build-devin), [Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/)).
- **Agent-verifiable setup is a prerequisite, not a nice-to-have.** Factory gates missions on Agent Readiness L4+ and tells operators to turn QA validation off if the environment can't support it ([Factory](https://docs.factory.ai/missions/overview)).

**Mapping.** Colony's reviewer and implementer are comparing two different worlds. The fix peers converge on: make the sandbox image _be_ the CI image (or run the agent on the CI runner), boot and exercise the real app, and give the implementer a CI-fix loop. A reviewer should never be the mechanism that discovers a glibc mismatch.

### Failure 5 — serial plans, long 3 h runs on cheap models

- **Smaller units are the norm.** Devin: ~3-hour rule, "break down large tasks", keep sessions small. Copilot: hard 59-minute cap, "break complex tasks into smaller issues". Ralph: one story per context window, 10 iterations by default ([Devin](https://docs.devin.ai/get-started/devin-intro), [GitHub](https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/coding-agent-best-practices), [Ralph](https://github.com/snarktank/ralph)).
- **Parallelism comes from dependencies, not from chains.** Kiro computes a dependency graph and executes waves; Symphony starts only unblocked DAG tasks and lets agents file follow-up issues; OpenHands runs six developers concurrently; Cursor runs hundreds of planners/workers with a judge ([Kiro](https://kiro.dev/docs/specs/parallel-task-execution/), [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md), [OpenHands](https://docs.all-hands.dev/usage/software-factory), [Cursor](https://cursor.com/blog/scaling-agents)).
- **A serial chain with a 20-task cap is a single point of failure by design.** Cognition's counterexample is instructive: they keep _writes_ single-threaded but parallelize intelligence, so a stuck reviewer/search does not block the writer ([Cognition](https://cognition.com/blog/multi-agents-working)).
- **Cheap tiers are fine for bounded work, not for open-ended work.** Jules uses Flash as base for well-scoped tasks with a critic on the plan; Factory pairs fast workers with a strong orchestrator; Cursor routes by predicted task complexity rather than by a fixed tier ([Jules](https://jules.google/docs/changelog), [Factory](https://docs.factory.ai/missions/reference), [Cursor](https://cursor.com/blog/how-cursor-router-works)).

**Mapping.** Colony's serial chains plus 3-hour cheap runs maximize both latency and failure blast radius. The peers' pattern is: short, independently verifiable units; a DAG that lets independent work proceed; cheap models on units they can finish; and an explicit hand-off/escalation when a unit exceeds its budget.

### "Should I just use stronger models?"

Short answer from the published evidence: **no single tier wins; route by role, verify with an independent clean-context reviewer, and re-justify the harness every model generation.** The evidence splits into four findings.

1. **A weak primary caps the whole system.** Cognition: "SWE-1.5 was not good enough to be our primary model. The quality ceiling is set by your primary model" ([Cognition](https://cognition.com/blog/multi-agents-working)). Colony's cheap implementer tier is therefore not free; the failures it produces propagate.
2. **Frontier everywhere is not the observed practice.** Jules defaults to Gemini 3 Flash. Factory documents fast workers under a strong orchestrator. Cursor's learned router beats a frontier model's satisfaction at 68% lower cost, and its Auto Balance beats Opus 4.8 at 41% lower cost ([Jules](https://jules.google/docs/changelog), [Factory](https://docs.factory.ai/missions/reference), [Cursor](https://cursor.com/blog/how-cursor-router-works)).
3. **Routing is learned from outcomes, not from a static tier table.** Cursor's Compass scores complexity 0–1, classifies task/modifiers, switches only above a 75% predicted-uplift threshold, and is explicit that per-model strengths shift between generations. Amp keeps roles stable while models change. Anneal makes model+effort per-step data ([Cursor](https://cursor.com/blog/how-cursor-router-works), [Amp](https://ampcode.com/docs/models-and-subagents), [Anneal](https://github.com/mosonlab/anneal)).
4. **Model upgrades should delete harness complexity.** Anthropic removed context resets for Opus 4.5 and sprint decomposition for Opus 4.6; the harness post's conclusion is that components encode stale assumptions and must be stress-tested or removed ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

A defensible Colony policy derived from this: keep the **architect and reviewer on the frontier tier**, but bound their turns and persist their artifacts; keep implementation on a fast tier **only for units sized to it**, with an escalation path when the unit exceeds its budget or the reviewer finds a blocker; and replace the fixed "flash/strong/frontier" mapping with a small, measurable router (task class → model/effort) that is re-evaluated when models change. The published counter-evidence to "just use stronger models" is not that strength doesn't matter — it is that _where_ the strength sits (planner, reviewer, adjudicator) and _whether the unit fits the model_ dominate total cost and intervention rate.
