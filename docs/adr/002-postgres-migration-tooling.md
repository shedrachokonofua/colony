# ADR-002: Postgres migration tooling

**Status:** Accepted
**Date:** 2026-04-24

## Context

Colony owns the `colony` Postgres database (`design.md` §19). The schema includes:

- An `audit_log` table with insert-only grants (`design.md:305`, COL-0.6) — no UPDATE or DELETE at the role level.
- Custom indexes for dependency-readiness queries and state-range scans.
- Likely future use of Postgres-native features: partial indexes, check constraints, `GENERATED` columns, triggers for audit, and possibly RLS if we want per-scope tenant isolation.
- Explicit role separation (`colony_writer`, `colony_reader`) with GRANTs per table.

The schema is first-party and stable — we are not generating it from application code.

## Decision

Use **`node-pg-migrate`** for `colony` schema migrations.

Temporal's own schema is managed with Temporal's supported migration path (see `design.md` §19, §Migrations) and is not covered by this ADR.

## Alternatives Considered

- **Drizzle (`drizzle-kit`).** TypeScript-first, schema-as-code, autogenerated migrations. Rejected because the schema shape must stay authoritative in SQL (append-only grants on `audit_log`, RLS, raw index choices, custom check constraints). Schema-as-TS conflates "shape of the table" with "shape of the ORM type," and the generated SQL is not always the SQL we want to write.
- **Prisma (`prisma migrate`).** Heavy, opinionated, assumes Prisma Client is the query path. Colony is likely to use Kysely or `pg` directly; Prisma's ORM is unwelcome baggage.
- **Kysely migrations.** Works, but couples migrations to the query-builder choice. We want the migration tool to be useful even if the query layer changes.
- **Umzug.** Just an orchestrator — still needs a SQL layer. Buys little over `node-pg-migrate`.
- **Hand-rolled `psql` scripts + a runner.** Tempting for pure SQL, but we lose transactional migration semantics, rollback, and "up/down" tooling for free from `node-pg-migrate`.
- **`sqitch`.** Great tool, but an extra non-Node dependency that complicates the Nix dev shell and CI image.

## Rationale

- SQL-forward: migrations are written as SQL or as `pgm.*` methods that map 1:1 to SQL. What goes in the file is what runs in Postgres.
- TypeScript-native: runs under Node, uses the same `pg` driver the apps will use, integrates cleanly with `npm` scripts and CI.
- Reversible: up/down patterns for dev iteration; production rollouts prefer forward-only, but dev churn benefits from reversibility.
- Transactional by default: each migration runs in a transaction.
- Mature: widely used, minimal surface, rarely a blocker.

## Consequences

- `packages/db` (or an early migrations directory, e.g. `migrations/`) holds migration files. A `db:migrate` script migrates against the Compose-hosted Postgres in local dev and against Aether Postgres in CI/prod.
- Migrations are raw SQL in the general case (`pgm.sql("...")`). Typed helpers are used only for trivial cases.
- `audit_log` insert-only grants are enforced by a migration that `GRANT INSERT ON audit_log TO colony_writer; REVOKE UPDATE, DELETE ON audit_log FROM colony_writer;` and tested in `packages/db` (COL-0.6).
- Query-builder choice (Kysely, `pg` directly, or something else) is decoupled from migration tooling and can be made later.

## Revisit When

- `node-pg-migrate` stops receiving updates or falls behind Postgres version compatibility.
- We need online schema changes (e.g. `pg_repack`, `pt-online-schema-change` equivalents) that the tool cannot model — at which point the tool becomes "write SQL, apply with X" and `node-pg-migrate`'s value drops.
- The schema becomes multi-tenant enough that declarative RLS generation or logical replication setup forces a richer tool.
