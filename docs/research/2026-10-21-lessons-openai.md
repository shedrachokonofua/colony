# Lessons from OpenAI's agent-factory sources (research snapshot: 2026-10-21)

Scope: first-party OpenAI sources only — the "harness engineering" essay, the Symphony announcement, `SPEC.md` and the `openai/symphony` reference repository, the long-horizon Codex post, the Codex cloud environment documentation, and the 2026 engineering posts on the Codex agent loop, the App Server, exec plans, maintenance agents, and prompt/skill hygiene. Quotes are verbatim from the fetched pages. Publication dates are the page's own where stated; where the page is undated, the date is sourced from OpenAI's cookbook/blog index or third-party coverage and marked as such. Nothing here was verified against internal Colony data; "Colony problem N" refers to the ranked list in the brief.

## 1. Lessons for Colony

1. **The repository is the durable memory; the orchestrator is not.** OpenAI's agent-first repo puts every artifact an agent needs under version control — a ~100-line `AGENTS.md` that acts as "the table of contents", a `docs/` tree with design docs, product specs, quality grades and checked-in exec plans — because "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist" ([harness engineering](#21-harness-engineering-leveraging-codex-in-an-agent-first-world-2026-02-11)). Exec plans are explicitly written so that "it should always be possible to restart from _only_ the ExecPlan and no other work" ([PLANS.md](#28-exec-plans--plansmd-openai-cookbook-archived)). _Bears on:_ Colony problem 2 (repairs restart with cold context) and the daimyo decision — journaled tasks are useful for scheduling, but the resumable knowledge must live in the repo/workspace, not only in a database row.

2. **One owner carries a leaf through review, CI and merge; continuation beats restart, and a restart should be a decision, not the default.** Symphony's redesign lesson is that "treating agents as rigid nodes in a state machine doesn't work well" and that they "moved toward giving agents _objectives_ instead of strict transitions" — one agent per issue handles multiple PRs, reads review feedback, watches CI, rebases and lands ([Symphony](#22-an-open-source-spec-for-codex-orchestration-symphony-2026-04-27)). Within a worker, continuation turns reuse the same live thread and workspace (`max_turns` default 20), and retry prompts say "Resume from the current workspace state instead of restarting from scratch." Only `Rework` is a deliberate reset: "Treat `Rework` as a full approach reset, not incremental patching" ([SPEC.md §7.1, `elixir/WORKFLOW.md`](#23-symphony-specmd-and-reference-repository)). _Bears on:_ Colony problem 2 (11–13 runs, 3–6 review rounds on large tasks) and the "one writer owning each leaf through review/CI" direction.

3. **Keep the orchestrator's mechanism set small, give state exactly one authority, and recover crashes by re-reading external truth.** The Symphony spec defines the service as "a scheduler/runner and tracker reader", states that "The orchestrator is the only component that mutates scheduling state", and recovers from a crash with "tracker-driven and filesystem-driven" restart recovery "without a durable orchestrator DB" — retry timers and live sessions are simply not restored ([SPEC.md §7, §14.3](#23-symphony-specmd-and-reference-repository)). One retry mechanism (a continuation delay and a failure backoff), one reconciliation loop, one stall timeout, one workspace lifecycle. _Bears on:_ Colony problems 1 and 4 — 46% non-model deaths and silently colliding hand-built mechanisms (watchdog, attempt budgets, review epochs, adoption, autosave, steering) are what a small, single-authority mechanism set is meant to prevent.

4. **Layer timeouts and failure classes by meaning, and make every failure operator-visible.** Symphony separates a turn-silence timeout (1 h, reset by any output), a stall timeout (5 min of event inactivity), hook timeouts (60 s), a retry backoff cap (5 min) and distinct terminal reasons (`Failed`, `TimedOut`, `Stalled`, `CanceledByReconciliation`); validation failures must be operator-visible, and an invalid `WORKFLOW.md` reload keeps "the last known good effective configuration" ([SPEC.md §5.3.6, §6.2, §7.2](#23-symphony-specmd-and-reference-repository)). _Bears on:_ Colony problem 4 directly — a single 20-minute watchdog killing a 23-minute test run, and a steering mechanism failing 9/9 for three weeks unnoticed, are both missing-semantics / missing-observability failures, not model failures.

5. **Put workflow policy in the repository, version it with the code, and let it hot-reload; keep the orchestrator policy-free.** Symphony's `WORKFLOW.md` carries the prompt, runtime settings, hooks and tracker config, is watched and re-applied without restart, and "a coding agent can implement the config layer quickly" because the contract is explicit ([SPEC.md §5, §6.2](#23-symphony-specmd-and-reference-repository)). The repo's `WORKFLOW.md` is where the status map, PR feedback sweep, workpad template and completion bar live — not in service code. _Bears on:_ the "keep Colony's factory policy" decision and Colony problem 3: policy changes (e.g. "deviate/rebut with evidence") should be reviewable repo edits with tests, not hidden runtime knobs that can fail silently.

6. **Make the environment as legible as the code: per-worktree app boot, browser driving, local logs/metrics queries, and environment setup captured as a tested artifact.** OpenAI made "the app bootable per git worktree", wired Chrome DevTools Protocol into the agent runtime, and gave each worktree "a local observability stack that's ephemeral" so prompts like "ensure service startup completes in under 800ms" become tractable ([harness engineering](#21-harness-engineering-leveraging-codex-in-an-agent-first-world-2026-02-11)). Codex Cloud captures setup as an install script plus a start skill, tests it during environment creation, caches the prepared filesystem, and keeps secrets out of the agent phase ([cloud environments](#25-codex-cloud-environment-documentation-living-docs-accessed-2026-10-21)). _Bears on:_ Colony problem 5 (sandbox differs from CI) — parity is an environment-contract problem solved by making one reproducible environment serve both agent and CI, not by adding another review rule.

7. **Enforce invariants mechanically, and put the remediation in the error message.** "By enforcing invariants, not micromanaging implementations, we let agents ship fast without undermining the foundation"; layers and dependency directions are enforced by custom linters and structural tests, and "we write the error messages to inject remediation instructions into agent context" ([harness engineering](#21-harness-engineering-leveraging-codex-in-an-agent-first-world-2026-02-11)). _Bears on:_ Colony problems 2 and 3 — reviewer findings that recur (naming, boundaries, test placement, forbidden patterns) should graduate into lints that fire in the implement run, before an adversarial review round exists.

8. **Schedule entropy collection; do not pay for it in bursts.** The team spent "every Friday (20% of the week) cleaning up 'AI slop'" until it stopped scaling; the replacement is golden principles plus background Codex tasks that "scan for deviations, update quality grades, and open targeted refactoring pull requests", most "reviewed in under a minute and automerged" — "This functions like garbage collection" ([harness engineering](#21-harness-engineering-leveraging-codex-in-an-agent-first-world-2026-02-11)). A year later the same pattern deleted "over 800k lines of code" across "more than 1,400 pull requests" ([maintenance](#29-maintaining-software-with-the-gpt-6-family-2026-10-14)). _Bears on:_ the "small leaves" direction — a factory that merges ~9 PRs in 19 h accumulates drift faster than humans can clean; GC must be a recurring, agent-executed work type with its own quality metric.

9. **Route every failure into the harness, never into the instance.** "When something failed, the fix was almost never 'try harder.'" Engineers asked "what capability is missing, and how do we make it both legible and enforceable for the agent?" ([harness engineering](#21-harness-engineering-leveraging-codex-in-an-agent-first-world-2026-02-11)); Symphony: "Instead of patching the result manually, we added guardrails and skills so the agents could succeed the next time" ([Symphony](#22-an-open-source-spec-for-codex-orchestration-symphony-2026-04-27)). _Bears on:_ Colony problems 3 and 4 — the switch to "deviate/rebut with evidence" is the same move at the policy layer; the 9/9 steering failure should have produced a harness fix or deletion, not three weeks of silent no-ops.

10. **Specify destination, acceptance and completion bar; let the agent choose the steps, and make out-of-scope discoveries into follow-up work instead of scope creep or human blocks.** Symphony gives agents objectives because "The power of models comes from their ability to reason, so give them tools and context and let them cook"; agents "simply file a new issue that we can evaluate and schedule later" for improvements outside the task ([Symphony](#22-an-open-source-spec-for-codex-orchestration-symphony-2026-04-27)). The reference `WORKFLOW.md` encodes the same rule ("file a separate Linear issue instead of expanding scope"), a "Completion bar before Human Review", and a blocked-access escape hatch that requires "exact human action needed to unblock" ([`elixir/WORKFLOW.md`](#23-symphony-specmd-and-reference-repository)). _Bears on:_ Colony problem 3 and the "planners that can add leaves at runtime" direction — agents already create work; the DAG grows through `blocked_by`/follow-ups rather than a fixed 20-task up-front plan.

11. **Human attention is the binding constraint; manage work at the ticket level and make human gates explicit and few.** In practice "most people could comfortably manage three to five sessions at a time before context switching became painful", so Symphony moved the control plane to the issue tracker: humans approve plans, move tickets into `Merging`, and can file work from a phone; non-engineers (PM, designer) can file tickets and receive a review packet ([Symphony](#22-an-open-source-spec-for-codex-orchestration-symphony-2026-04-27)). A successful run may end at a workflow-defined handoff state such as `Human Review`, "not necessarily `Done`" ([SPEC.md §1](#23-symphony-specmd-and-reference-repository)). _Bears on:_ Colony's 4–6 operator actions per merge on the hard project and the human-block failure mode — each human touch should be a designed gate (plan approval, merge approval), not a side effect of a stuck mechanism.

12. **Treat prompts, skills and model choice as tunables that go stale: prune guidance each model generation, and choose models by measured cost per accepted outcome.** OpenAI's own guidance is that accumulated instructions "can take many forms: skills, `AGENTS.md`, and your task prompts" and must be revisited per release; over-specified guidance and stop-for-review instructions now _cause_ failures ("A requirement to stop for review after the first implementation will pull the model toward an earlier stopping point") ([rethinking skills](#210-rethinking-skills-and-prompts-for-gpt-6-astra-2026-09-05-secondary-date)). The maintenance team publishes cost per accepted finding — $0.77 (Astra Ultra), $0.12 (Sol Ultra), $0.06 (Sol Medium) — and notes a cheaper model reached "92% as many findings … at 14% of the API cost" ([maintenance](#29-maintaining-software-with-the-gpt-6-family-2026-10-14)). _Bears on:_ Colony problem 2 and the cheap-"flash"-implement decision — cost per _merge_, not per run, is the number that decides whether 11–13 cheap runs beat 2–3 stronger ones.

### 1.1 Mechanism comparison for problems 1 and 4

The table contrasts what Colony runs today (per the brief) with what the OpenAI sources actually specify. It is the most actionable single artifact in this file.

| Concern               | Colony today                                          | Symphony / harness-engineering primitive                                                                                       | Consequence for Colony                                                                             |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Liveness watchdog     | 20-min watchdog (killed 23-min test runs, 31 runs)    | Two separate clocks: turn-silence timeout (1 h, any output resets) and stall timeout (5 min of _event_ inactivity)             | A wall-clock kill is the wrong instrument; kill on absence of events, not on duration              |
| Retries               | Attempt budgets + adoption + steering + review epochs | One retry path: continuation retry (~1 s) after clean exit; `min(10s·2^(n−1), 5m)` after failure; reconciliation on every tick | Fewer mechanisms, one owner of state; budgets belong in the tracker/workflow, not in the scheduler |
| Crash recovery        | colonyd restarts/deploys (129 runs)                   | In-memory scheduler; recovery = re-poll tracker + reuse workspace; no timer replay                                             | Restart should be a non-event: external truth (tracker, git, workspace) is authoritative           |
| Config/policy changes | Runtime steering (failed 9/9 silently)                | `WORKFLOW.md` in repo, hot-reloaded, invalid reload keeps last-known-good and logs operator-visible error                      | Policy edits are reviewed like code and cannot silently no-op                                      |
| Completion signal     | Fixed plan; spec forbidden to deviate                 | Objectives + per-issue workpad comment + completion bar + agent-owned PR feedback sweep                                        | One artifact states what "done" means and survives cold restarts                                   |
| Human gate            | Human block on impossible requirements                | `Human Review` handoff state with blocker brief naming exact unblock action; `Merging` is human-approved                       | Human time is spent on judgment, with a written ask                                                |

### 2.1 "Harness engineering: leveraging Codex in an agent-first world" (2026-02-11)

Author: Ryan Lopopolo, Member of the Technical Staff. URL: https://openai.com/index/harness-engineering/

- **Architecture.** An internal beta product built with "**0 lines of manually-written code**" over five months; first commit to an empty repository in late August 2025. The initial scaffold (repo structure, CI, formatting, package manager, framework) was generated by Codex CLI with GPT-5 "guided by a small set of existing templates"; even the first `AGENTS.md` was written by Codex. Five months later: "on the order of a million lines of code" across product, infrastructure, tooling, docs and internal utilities; "roughly 1,500 pull requests" merged by "a small team of just three engineers", later seven. Human workflow: describe a task, let the agent open a PR; to finish a PR, Codex reviews its own changes locally, requests additional specific agent reviews locally and in the cloud, responds to feedback, and iterates "in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop)". Agents use `gh`, local scripts and repository-embedded skills directly. Recently the repo crossed a threshold where one prompt drives a feature end-to-end: validate state, reproduce the bug, record a failure video, fix, validate by driving the app, record a resolution video, open a PR, respond to feedback, remediate build failures, "Escalate to a human only when judgment is required", merge.
- **Repository knowledge layout.** `AGENTS.md` is "roughly 100 lines" and is "**the table of contents**", not the encyclopedia. The real knowledge base is a structured `docs/` tree: `design-docs/` with `index.md` and `core-beliefs.md`; `exec-plans/active/`, `exec-plans/completed/`, `tech-debt-tracker.md`; `generated/db-schema.md`; `product-specs/`; `references/` (vendored `*-llms.txt` files); plus `DESIGN.md`, `FRONTEND.md`, `PLANS.md`, `PRODUCT_SENSE.md`, `QUALITY_SCORE.md`, `RELIABILITY.md`, `SECURITY.md`, and `ARCHITECTURE.md` as a top-level domain/layering map. Design docs are catalogued with verification status; a quality document "grades each product domain and architectural layer, tracking gaps over time". "Plans are treated as first-class artifacts": ephemeral plans for small changes, exec plans with progress and decision logs checked in for complex work. Dedicated linters and CI jobs validate that the knowledge base is current, cross-linked and correctly structured; a recurring "doc-gardening" agent opens fix-up PRs for stale documentation.
- **Failure modes and fixes.**
  - The "one big `AGENTS.md`" approach failed in four predictable ways: context is scarce; "Too much guidance becomes _non-guidance_"; "It rots instantly" into "an attractive nuisance"; and it "is hard to verify" mechanically. Fix: map-plus-progressive-disclosure with mechanical freshness checks.
  - Early progress was slower than expected "not because Codex was incapable, but because the environment was underspecified" — missing tools, abstractions and internal structure. Fix: depth-first construction of building blocks and legibility work.
  - As throughput rose, "our bottleneck became human QA capacity". Fix: make the UI, logs and metrics directly legible (per-worktree boot, CDP, ephemeral observability stack).
  - Entropy: "Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift." Fix: golden principles + recurring GC agents (see below).
- **What they removed or stopped doing.** Manual code (never written); the monolithic `AGENTS.md`; the Friday "AI slop" cleanup (20% of the week) as a human ritual; reliance on external (non-repo) knowledge, because "Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible to the system". Human PR review stopped being required: "Humans may review pull requests, but aren't required to. Over time, we've pushed almost all review effort towards being handled agent-to-agent."
- **Coordination and merge strategy.** "The repository operates with minimal blocking merge gates. Pull requests are short-lived. Test flakes are often addressed with follow-up runs rather than blocking progress indefinitely. In a system where agent throughput far exceeds human attention, corrections are cheap, and waiting is expensive." Agents "often squash and merge their own pull requests." The post concedes this "would be irresponsible in a low-throughput environment."
- **Memory and context strategy.** Progressive disclosure from a small stable entry point; plans and decision logs as versioned artifacts; skills and repo-embedded tooling for context gathering "without humans copying and pasting"; explicit preference for technologies an agent can "fully internalize and reason about in-repo" — "boring" tech, stable APIs, sometimes reimplementing a small library subset (they wrote their own map-with-concurrency helper instead of depending on `p-limit`, with 100% test coverage and OpenTelemetry integration).
- **Verification and review.** Layered: local self-review → targeted agent reviewers locally and in the cloud → CI → "all agent reviewers satisfied" → merge. Mechanical enforcement: fixed domain layers (Types → Config → Repo → Service → Runtime → UI), dependency directions enforced by custom linters and structural tests, cross-cutting concerns through a single `Providers` interface, plus "taste invariants" (structured logging, schema/type naming, file-size limits, platform reliability requirements). Custom lint errors carry remediation text. "Enforce boundaries centrally, allow autonomy locally."
- **Stuck and drift detection.** Doc-gardening agent; quality grades per domain; background scans against golden principles; lint/structural tests. No per-run watchdog is described — liveness is delegated to the harness and CI signals.
- **Human role.** Prioritize work, "translate user feedback into acceptance criteria, and validate outcomes"; when the agent struggles, identify the missing tool, guardrail or documentation and "always by having Codex itself write the fix". Humans "steer" at the level of intent; "Agents execute."
- **Model mix and cost.** GPT-5 for the initial scaffold; otherwise "Codex" without a published routing table. No cost figures. One efficiency claim: "We estimate that we built this in about 1/10th the time it would have taken to write the code by hand."
- **Published numbers.** ~1M LoC; ~1,500 PRs; 3 → 7 engineers; "3.5 PRs per engineer per day", with throughput _increasing_ as the team grew; ~6-hour single runs "often while the humans are sleeping"; 20% of the week previously spent on cleanup; ~100-line `AGENTS.md`.
- **Explicit caveats.** The end-to-end single-prompt behavior "depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment". Open questions: "how architectural coherence evolves over years in a fully agent-generated system" and where human judgment adds the most leverage.

### 2.2 "An open-source spec for Codex orchestration: Symphony" (2026-04-27)

Authors: Alex Kotliarskyi, Victor Zhu, Zach Brock. URL: https://openai.com/index/open-source-codex-orchestration-symphony/

- **Architecture.** Symphony "turns a project-management board like Linear into a control plane for coding agents. Every open task gets an agent, agents run continuously, and humans review the results." Each open Linear issue maps to a dedicated agent workspace; a long-running service watches the board, restarts crashed or stalled agents, and picks up new work. Ticket statuses are the state machine. "In practice, Symphony decouples work from sessions and from pull requests. Some issues produce multiple PRs across repos; others are pure investigation or analysis that never touch the codebase." Complex work: an agent analyzes codebase/Slack/Notion and produces a plan; once accepted, the agent "generates a tree of tasks, breaking the work into stages and defining dependencies between tasks. Agents only start working on tasks that aren't blocked" — so execution follows the DAG and parallelizes naturally (their example: React upgrade `blocked_by` a Vite migration). Agents also create work: out-of-scope improvements become new issues "that we can evaluate and schedule later—many of these follow-up tasks also get picked up by agents."
- **Failure modes and fixes.**
  - The bottleneck after harness engineering was context switching: "most people could comfortably manage three to five sessions at a time before context switching became painful. Beyond that, productivity dropped." Fix: stop supervising sessions; dispatch from the tracker.
  - Losing mid-flight steering meant "Sometimes the agent produced something that completely missed the mark. That was useful—those failures revealed gaps in the system and helped us make it more robust." Fix: "Instead of patching the result manually, we added guardrails and skills so the agents could succeed the next time" — end-to-end tests, Chrome DevTools driving, QA smoke tests, better docs, "clarified what good looks like".
  - Treating agents as rigid nodes in a state machine: "Models get smarter and can solve bigger problems than the box we try to fit them in." Early versions only asked Codex to implement; it proved "too limiting". Fix: tools (`gh`, CI-log skills) and objectives — "much like a good manager would assign a goal to a direct report"; agents close old PRs, report on completed vs abandoned work.
  - v1 was "just a Codex session running in `tmux`, polling Linear and spawning sub-agents for new tasks. It worked, but it wasn't particularly reliable." Fix: a service around Codex App Server (JSON-RPC), with dynamic tool calls used to expose raw `linear_graphql` "without relying on MCP or exposing the access token to containers".
- **What they removed or stopped doing.** Stopped supervising individual sessions. Stopped encoding step-by-step transitions. "We removed a lot of incidental complexity, like dependencies on specific repositories or Linear MCP." Symphony itself was reduced to "technically just a `SPEC.md` file"; it is "an intentionally minimal orchestration layer" and "we don't plan to maintain Symphony as a standalone product" — a reference implementation. To find spec ambiguities they had Codex implement it in TypeScript, Go, Rust, Java and Python as well as Elixir.
- **Coordination and merge strategy.** The system "watches CI, rebases when needed, resolves conflicts, retries flaky checks, and generally shepherds changes through the pipeline. By the time a ticket reaches **Merging**, we have high confidence the change will make it into the main branch without human babysitting." Work is abstracted to tickets, so "tickets can represent much larger units of work."
- **Memory and context strategy.** The tracker is the durable record of intent and status; the workflow document (`WORKFLOW.md`) is the durable record of process; per-issue workspaces are persistent; the agent's proof-of-work (CI status, review feedback, complexity analysis, walkthrough video) is attached to the ticket. Not described in the announcement beyond this.
- **Verification and review.** Agents produce proof-of-work review packets including "a video walkthrough of the feature working inside the real product". A human (or the next ticket state) reviews. For monorepo last-mile they treat CI as the verification surface to be actively driven.
- **Stuck and drift detection.** "If an agent crashes or stalls, Symphony restarts it. If new work appears, Symphony picks it up." The service is the liveness authority; the SPEC makes this concrete (see 2.3).
- **Human role.** "humans review the results"; engineers keep the hard, ambiguous work: "Some problems still require engineers working directly with interactive Codex sessions, especially ambiguous problems or work that requires strong judgment and expertise." PM and designer can file feature requests directly and receive a review packet without checking out the repo. One engineer "made three significant changes from the Linear app on his phone from a cozy cabin on shoddy wifi."
- **Model mix and cost.** Not disclosed. The spec treats the coding agent as a pluggable component behind the app-server protocol; the reference `WORKFLOW.md` pins `model="gpt-5.5"` and `model_reasoning_effort=xhigh`.
- **Published numbers.** "500% increase in landed pull requests on some teams" — later stated as "the number of landed PRs increase by 500% in the first three weeks"; 15K GitHub stars "as of April 23" 2026. Linear's founder publicly noted a spike in workspaces created.

### 2.3 Symphony SPEC.md and reference repository (Draft v1; public c. March 2026)

URLs: https://raw.githubusercontent.com/openai/symphony/main/SPEC.md · https://github.com/openai/symphony · https://raw.githubusercontent.com/openai/symphony/main/elixir/WORKFLOW.md · Repo public before the 2026-04-27 announcement (the post cites 15K stars by 2026-04-23 and embeds posts dated 2026-03-06..08) — public-release date is [INFERENCE], spec status is "Draft v1 (language-agnostic)".

- **Architecture.** Four operational problems are named: repeatable daemon workflow instead of scripts; per-issue workspace isolation; workflow policy in-repo (`WORKFLOW.md`); enough observability to debug concurrent runs. Components: workflow loader, typed config layer, tracker adapter, orchestrator, workspace manager, agent runner, optional status surface, logging. Six layers are prescribed for portability: policy (repo), configuration (typed), coordination (orchestrator), execution (workspace + agent subprocess), integration (tracker adapter), observability. The boundary is explicit: "Symphony is a scheduler/runner and tracker reader." Ticket writes are "typically performed by the coding agent through provider-native tools executed by Symphony with the configured tracker credential"; "A successful run can end at a workflow-defined handoff state (for example `Human Review`), not necessarily `Done`."
- **Defaults and mechanisms** (the concrete numbers Colony should compare against):

  | Setting                       | Default                          | Meaning                                              |
  | ----------------------------- | -------------------------------- | ---------------------------------------------------- |
  | `polling.interval_ms`         | 30 000                           | poll tick; reconciled before each dispatch           |
  | `agent.max_concurrent_agents` | 10                               | global slots                                         |
  | `agent.max_turns`             | 20                               | continuation turns per worker session                |
  | `agent.max_retry_backoff_ms`  | 300 000                          | backoff cap                                          |
  | continuation retry            | ~1 000 ms                        | after a clean worker exit                            |
  | failure retry                 | `min(10 000·2^(attempt−1), cap)` | after abnormal exit                                  |
  | `codex.turn_timeout_ms`       | 3 600 000                        | max _silence_ while streaming; each output resets it |
  | `codex.read_timeout_ms`       | 5 000                            | startup/sync request timeout                         |
  | `codex.stall_timeout_ms`      | 300 000                          | event-inactivity kill, disabled if ≤ 0               |
  | `hooks.timeout_ms`            | 60 000                           | all workspace hooks                                  |
  | `workspace.root`              | `<temp>/symphony_workspaces`     | per-issue directories retained                       |

- **Dispatch, reconciliation, retry.** A single authoritative in-memory state (`running`, `claimed`, `retry_attempts`, totals, rate limits). Every tick: reconcile active runs, validate config, fetch candidates, sort (priority 1–4, then oldest, then identifier), dispatch while slots remain. Reconciliation has two parts: stall detection (kill on event inactivity) and tracker state refresh (terminal → stop + clean workspace; non-active → stop without cleanup; still active → refresh snapshot; fetch failure → keep workers). Retry refresh re-fetches by ID so terminal/non-routable issues are released rather than re-run. Normal worker exit schedules a ~1 s continuation retry so the tracker can be re-checked; a worker may run up to `max_turns` back-to-back turns on the same thread, with "continuation guidance" instead of resending the original prompt.
- **Failure classes.** Five families — workflow/config, workspace, agent session, tracker, observability — each with a defined recovery: skip dispatch, retry with backoff, keep workers, or "do not crash the orchestrator". "A run MUST NOT stall indefinitely waiting for user input." Restart semantics: "No retry timers are restored"; "No running sessions are assumed recoverable"; recovery is startup workspace cleanup, fresh polling, re-dispatch. Workspaces "are intentionally preserved after successful runs."
- **Non-goals (what it deliberately leaves out).** "Rich web UI or multi-tenant control plane"; any prescribed dashboard/TUI; "General-purpose workflow engine or distributed job scheduler"; "Built-in business logic for how to edit tickets, PRs, or comments. (That logic lives in the workflow prompt and agent tooling.)"; a mandated sandbox or approval posture; a single default operator-confirmation policy. The tracker boundary is deliberately small — a read kernel (`fetch_issues_by_states`, `fetch_issues_by_ids`) plus optional provider-native tools; the spec warns: "Do not add generic comment/state/attachment CRUD merely to make providers look alike." Open TODOs in the spec's checklist: persist retry queue/session metadata across restarts; make observability settings configurable; "Extract common semantic helper tools only after multiple adapters demonstrate real duplication."
- **Repository contract (`WORKFLOW.md`).** YAML front matter + Markdown prompt body, repo-owned and versioned; strict template rendering with `issue` and `attempt`; dynamic reload required; invalid reload keeps last-known-good and logs; `after_create`, `before_run`, `after_run`, `before_remove` hooks (failure semantics differ: create/run abort the attempt, after/remove are logged and ignored); safety invariants (agent cwd == workspace path, workspace path under root, sanitized collision-resistant keys). Secrets are `$VAR` references resolved host-side; tracker credentials "SHOULD NOT be inherited by the coding-agent child process"; provider-native tools execute host-side with the adapter credential.
- **Reference implementation.** Elixir/OTP (the FAQ cites supervision, hot code reload without stopping subagents, and the BEAM ecosystem); adapters for Linear, GitHub Issues, Jira Cloud, Asana and GitLab; optional Phoenix LiveView dashboard and JSON API (`/api/v1/state`, `/api/v1/<issue_identifier>`, `/api/v1/refresh`); Burrito single-binary releases for four platforms; live end-to-end tests that create disposable Linear resources and run a real `codex app-server` session, plus SSH-worker E2E using disposable Docker workers. Blocked entries from operator-input/approval requests are "in memory only; restarting the orchestrator clears that blocked map". The README calls it "a low-key engineering preview for testing in trusted environments."
- **The actual factory policy (`elixir/WORKFLOW.md`).** This is the most transferable artifact in the repo. Status map: `Backlog` (out of scope, human must move to `Todo`) → `Todo` (immediately transition to `In Progress`) → `In Progress` → `Human Review` (PR attached and validated, waiting on human) → `Merging` (human approved; run the `land` skill loop, "do not call `gh pr merge` directly") → `Done`; `Rework` = reviewer requested changes. Standing rules:
  - Start every task by opening a single persistent workpad comment (`## Codex Workpad`) and treating it as "the source of truth for progress"; it holds an environment stamp `<host>:<abs-workdir>@<short-sha>`, a hierarchical plan, acceptance criteria, validation commands, notes and a `Confusions` section; never post separate "done"/summary comments.
  - Treat any ticket-authored `Validation` / `Test Plan` / `Testing` section as "non-negotiable acceptance input".
  - "Reproduce first: always confirm the current behavior/issue signal before changing code."
  - Out-of-scope improvements: "file a separate Linear issue instead of expanding scope", with title, description, acceptance criteria, same project, `related` link and `blockedBy` when dependent.
  - PR feedback sweep: gather top-level comments, inline review comments and review summaries; "Treat every actionable reviewer comment (human or bot), including inline review comments, as blocking until" it is addressed or has "explicit, justified pushback"; "Repeat this sweep until there are no outstanding actionable comments."
  - Blocked-access escape hatch: only for true external blockers (missing tools/auth), with a brief naming "exact human action needed to unblock"; GitHub auth is explicitly "**not** a valid blocker by default".
  - Completion bar before `Human Review`: checklist complete, acceptance and ticket-provided validation done, tests green on the latest commit, feedback sweep clean, PR checks green, PR linked and labeled, media captured for app-touching changes.
  - `Rework` handling: full approach reset — close the PR, delete the workpad, fresh branch from `origin/main`, rebuild the plan, execute end-to-end.
  - Guardrails: one workpad per issue; never edit the issue body for progress; temporary proof edits must be reverted before commit; in `Human Review` make no changes and poll; in `Done` shut down.
- **Spec-level lessons for Colony.** (a) The orchestrator's authority is scheduling, not workflow semantics; (b) liveness has two clocks with different meanings and neither is a wall-clock task limit; (c) the tracker (plus git and the workspace) is the recovery source of truth, so a scheduler crash cannot strand work; (d) policy lives in a repo file that can be diffed, tested by porting the spec, and reloaded without restart; (e) a "successful" run may legitimately stop at a human handoff state.

### 2.4 "Run long horizon tasks with Codex" (2026-02-23)

Author: Derrick Choi. URL: https://developers.openai.com/blog/run-long-horizon-tasks-with-codex (date per OpenAI's cookbook listing of the same post, "Feb 23, 2026")

- **Architecture.** A single Codex run on a blank repository, asked to build a design tool from scratch with GPT-5.3-Codex at "Extra High" reasoning. Result: "Codex ran for about 25 hours uninterrupted, used about 13M tokens, and generated about 30k lines of code." Explicitly "an experiment, not a production rollout."
- **The loop.** Plan → edit code → run tools (tests/build/lint) → observe results → repair failures → update docs/status → repeat. The post argues long-horizon coherence comes from "the agent loop the model operates inside", not one giant prompt: real feedback (errors, diffs, logs), externalized state (repo, files, docs, worktrees, outputs), and steerability over time.
- **Memory and context strategy (the core technique).** "The most important technique was durable project memory" — four Markdown files the agent revisits:
  - `docs/prompt.md`: spec + deliverables; goals/non-goals, hard constraints, deliverables, and a "Done when" section, to "Freeze the target so the agent doesn't 'build something impressive but wrong.'"
  - `docs/plans.md`: "Milestones small enough to complete in one loop", acceptance criteria and validation commands per milestone, a "Stop-and-fix rule: if validation fails, repair before moving on", decision notes "to avoid oscillation", intended architecture.
  - `docs/implement.md`: the runbook — plan file is source of truth, run validation after each milestone, "Keep diffs scoped (don't expand scope)", update the documentation file continuously.
  - `docs/documentation.md`: status + decisions + how to run/demo + known issues; "the shared memory and audit log. It's how I can step away for hours and still understand what happened."
- **Failure modes and fixes.** Drift and "impressive but wrong" outputs are the named risks; the fixes are a frozen spec, milestone-sized work, validation gates and a live audit log. Verification was run "for every milestone" (lint, typecheck, tests, build, export) and failures were repaired before continuing.
- **What they removed or stopped doing.** Not framed as removals, but the explicit shift is "less babysitting, more delegation with guardrails" and steering "at milestones instead of micromanaging every line". Note the caveat that the harness's newer native plan mode may supersede the hand-rolled files.
- **Coordination and merge strategy.** Single agent, single branch; no multi-agent coordination described.
- **Verification and review.** Continuous, milestone-scoped verification; the bar was "does it follow the instructions, and does it actually work?" rather than "it compiles". Result "not perfect or production-ready, but it was real and testable."
- **Stuck and drift detection.** The `documentation.md` status file plus the stop-and-fix rule; decision notes prevent oscillation between approaches.
- **Human role.** Wrote the spec, constraints, milestones and runbook up front; steered at milestones; reviewed the audit log.
- **Model mix and cost.** One model (GPT-5.3-Codex), highest reasoning effort; 13M tokens reported, no dollar cost.
- **Published numbers.** ~25 h, ~13M tokens, ~30k LoC; METR framing of "a rough ~7 month doubling time" for task length at ~50%/80% reliability.
- **Colony relevance.** This is the concrete recipe for Colony problem 2: a cold repair run is only as good as the checked-in plan/status artifacts it can read, and milestones must be sized to "one loop".

### 2.5 Codex cloud environment documentation (living docs, accessed 2026-10-21)

URLs: https://learn.chatgpt.com/docs/environments/cloud-environments (current) · https://learn.chatgpt.com/docs/environments/cloud-environment (legacy)

- **Architecture.** A cloud environment is "the reusable setup that tasks use: repositories, dependencies, tools, and access settings." Each new task gets "its own isolated workspace from the published environment." Environment creation is itself agent-assisted: Codex inspects repositories, installs dependencies, tests the workflow, and records the result as an **install script** plus a **start skill** ("instructions to start services and check that they're ready"); publishing "captures the prepared filesystem for new tasks."
- **Execution model (legacy doc, still the clearest description).** Container created, repo checked out at branch/SHA, setup script (plus optional maintenance script on cached resume) runs, internet settings applied, then "The agent runs terminal commands in a loop. It edits code, runs checks, and tries to validate its work. If your repo includes `AGENTS.md`, the agent uses it to find project-specific lint and test commands." Finally it shows the diff and can open a PR.
- **Caching and drift control.** "Codex caches container state for up to 12 hours"; on resume it checks out the requested branch and runs the optional maintenance script because "the setup script ran on an older commit"; the cache is invalidated automatically when setup/maintenance scripts, env vars or secrets change; enterprise caches are shared.
- **Secrets and network.** Secrets are encrypted and "only available to setup scripts… secrets are removed before the agent phase starts." Network: setup has internet; agent internet is off by default and can be limited or unrestricted through an HTTP/HTTPS proxy; "Network secrets" deliver a placeholder to programs and substitute the real value only for allowed destinations; OIDC issues short-lived cloud credentials; Tailscale provides private networking; an egress IP feed exists for IP-allowlisted services.
- **Failure modes addressed.** Missing dependencies (auto-setup for npm/yarn/pnpm/pip/pipenv/poetry or a manual script); slow provisioning (cached prepared filesystem); credential leakage (secrets scoped to setup, proxy substitution); environment drift after repo changes (maintenance script, explicit cache reset); network abuse (proxy + allowlists). Note the documented footgun: setup scripts run "in a separate Bash session from the agent, so commands like `export` do not persist".
- **Colony relevance.** Environment setup is a versioned artifact that is _tested while it is created_ and _reused by both the agent and the task's checks_. This is the shape Colony problem 5 needs: one published environment definition, exercised by the agent, by CI, and by the operator.

### 2.6 "Unrolling the Codex agent loop" (2026-01-23)

Author: Michael Bolin. URL: https://openai.com/index/unrolling-the-codex-agent-loop/

- **Architecture.** The agent loop is inference → tool call → tool output appended → re-inference, until the model emits an assistant message; a turn may contain many such iterations. The prompt is assembled from server system message, `instructions` (developer), `tools`, and an `input` list. Codex prepends: a `<permissions instructions>` developer message (sandbox applies only to Codex's own shell tool — MCP tools "are responsible for enforcing their own guardrails"); optional `developer_instructions`; user instructions aggregated from `AGENTS.override.md`/`AGENTS.md` in `$CODEX_HOME` and up the tree from project root to cwd (32 KiB default budget), plus skills metadata; and an `<environment_context>` (cwd, shell).
- **Memory and context strategy.** History grows quadratically in bytes but prompt caching makes sampling linear when prefixes match; Codex deliberately keeps requests stateless (no `previous_response_id`) to support Zero Data Retention. Cache misses are caused by changing tools mid-conversation, changing the model, or changing sandbox/approval/cwd; they mitigate by appending a _new_ permissions or environment message instead of editing earlier ones, and by enumerating tools deterministically (a bug where MCP tools were enumerated inconsistently caused cache misses). Compaction replaces `input` above a threshold with a compacted item set via the `/responses/compact` endpoint, preserving an opaque `encrypted_content` item that carries the model's latent understanding; it is now automatic (`auto_compact_limit`) rather than a manual `/compact`.
- **Failure modes and fixes.** Context-window exhaustion (compaction); cache misses and their cost (stable prefixes, append-only config changes); tool-list instability (consistent ordering; MCP `list_changed` notifications are dangerous mid-conversation).
- **What they removed or stopped doing.** Manual compaction; stateful `previous_response_id` (rejected for statelessness/ZDR); the old "TUI talks directly to Rust core types" architecture is being refactored onto the same app-server protocol (see 2.7).
- **Verification and review / stuck detection / human role / model mix / numbers.** Not the subject of this post. Its transferable lesson is mechanical: mid-run configuration changes must be append-only, tool sets must be stable, and compaction must be a first-class harness primitive — all of which apply to any Colony run that expects a cold or long-lived context to stay coherent.

### 2.7 "Unlocking the Codex harness: how we built the App Server" (2026-02-04)

Author: Celia Chen. URL: https://openai.com/index/unlocking-the-codex-harness/

- **Architecture.** A bidirectional JSON-RPC protocol over stdio plus a long-lived process hosting Codex core threads. Three primitives: **item** (typed atomic input/output with `item/started`, `item/*/delta`, `item/completed`), **turn** (one unit of agent work from user input to final output), **thread** (durable conversation container that can be created, resumed, forked, archived; history persisted so clients reconnect). The protocol is bidirectional: the server can request approval and pause the turn until the client responds.
- **Origin and failure modes.** MCP-as-the-harness-API "proved difficult" for VS Code's semantics; the first JSON-RPC version was "not designed as a stable API"; demand from JetBrains/Xcode and the desktop app's need to "orchestrate many Codex agents in parallel" forced a backward-compatible platform surface. In the web runtime, a worker provisions a container, launches the App Server inside it and keeps a long-lived stdio channel; the browser talks HTTP/SSE. Because sessions are ephemeral, "the web app cannot be the source of truth for long-running tasks. Keeping state and progress on the server means work continues even if the tab disappears."
- **What they removed or stopped doing.** MCP as the primary integration protocol; the TUI's special-case in-process path (being refactored to a normal app-server client); `previous_response_id` statefulness (from 2.6).
- **Coordination and merge strategy.** Not applicable; this is a protocol, not a workflow.
- **Memory and context strategy.** Thread persistence and resume/fork/archive; server-side state so clients can disconnect; the harness owns compaction.
- **Verification and review.** Approvals are protocol messages: the agent can request permission and the client decides allow/deny. This is the mechanism Symphony's spec builds on when it says approvals "MUST NOT leave a run stalled indefinitely."
- **Stuck and drift detection.** Turn lifecycle events (`turn/started`, `turn/completed`, deltas) are the heartbeat that a supervisor can watch — exactly what Symphony's `last_codex_timestamp` stall detection consumes.
- **Human role.** Approvals and interrupts are first-class protocol operations, so the human can intervene at any point the client exposes.
- **Model mix and cost.** Not applicable.
- **Published numbers.** None; clients implemented in Go, Python, TypeScript, Swift, Kotlin.
- **Colony relevance (daimyo).** A durable session server with explicit turn/item events and an approval channel is the right substrate for Colony's "journaled tasks, sessions, harness agents" plan; the lesson is to keep _product_ state (work status) outside the session server, and let the session server own only conversation durability and tool approvals.

### 2.8 Exec plans / PLANS.md (OpenAI cookbook, archived)

URL: https://developers.openai.com/cookbook/articles/codex_exec_plans · Referenced by the 2026-02-11 harness post as the "execution plans" pattern. Archived; written for `gpt-5.2-codex`. Original publication date not stated — [UNVERIFIED], c. late 2025.

- **Architecture.** `AGENTS.md` gets one rule ("When writing complex features or significant refactors, use an ExecPlan … from design to implementation"); `PLANS.md` defines the document contract. The post says this exact approach "has enabled Codex to work for more than seven hours from a single prompt."
- **The contract (the transferable part).**
  - "Every ExecPlan must be fully self-contained" — "Treat the reader as a complete beginner to this repository: they have only the current working tree and the single ExecPlan file you provide."
  - "ExecPlans are living documents… it should always be possible to restart from _only_ the ExecPlan and no other work."
  - Mandatory living sections: `Progress` (checkbox list with timestamps; "Every stopping point must be documented here"), `Surprises & Discoveries` (observation + evidence), `Decision Log` (decision, rationale, date/author), `Outcomes & Retrospective`.
  - Acceptance is behavioral and observable: e.g. "after starting the server, navigating to http://localhost:8080/health returns HTTP 200 with body OK", not "added a HealthCheck struct".
  - Milestones are narrative and "independently verifiable"; prototypes are explicitly allowed and labeled; parallel implementations during a migration are allowed if both paths are validated and one is retired safely; validation is "not optional"; recovery/idempotence is specified.
- **Failure modes it prevents.** Agents implementing "the letter of a feature" while doing nothing meaningful; outsourcing key decisions to the reader; relying on prior context; oscillation between approaches (hence the Decision Log); unreviewable progress.
- **What it deliberately avoids.** Checklists outside `Progress`; nested code fences; external pointers ("Do not point to external blogs or docs; if knowledge is required, embed it in the plan itself").
- **Colony relevance.** This is the missing artifact in Colony's cold repair loop: a per-task, checked-in plan/status file that a fresh run can resume from, with the decision log explaining why the previous run chose what it chose. It also gives the reviewer something better than a diff to judge.

### 2.9 "Maintaining software with the GPT-6 family" (2026-10-14)

Author: an engineer on OpenAI's Core Experimentation team. URL: https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family (date per OpenAI's blog index)

- **Architecture.** Maintenance as an agent-executed, evidence-gathering workflow, not a static-analysis pipeline. Dead-code removal started as a short, ambiguous prompt ("Can you help identify and clean up dead code in the repo please, feel free to check slack, statsig … or any other source you need"); GPT-6 Astra responded by reading past PRs, Slack threads, internal trackers and production profiling tables, and explaining its rationale per deletion. Stale-experiment cleanup used a prompt that names the evidence sources and safeguards, requires "one small draft PR per cleanup, linking its Statsig configuration console link in the summary", and forbids modifying live configs. A follow-up `/goal` prompt asked for a full-repo audit, and Astra produced "a markdown report grouping all verified candidates into parallelizable ownership/file workstreams, including production values, evidence, owners, callsites, and observed evaluation or CPU costs".
- **Failure modes and fixes.** Static analysis had known false negatives and incident history; short prompts were too ambiguous for the previous model (explicitly "too ambiguous for GPT-5.6 Sol to handle completely"); too many candidate cleanups create a prioritization problem. Fixes: evidence requirements in the prompt, per-change small PRs, human validation of the largest wins, and instrumentation to rank by measured cost.
- **What they removed or stopped doing.** Replaced bespoke static-analysis systems with promptable, evidence-gathering agents for some tasks: "These targeted prompts were easier to develop and maintain than our existing static analysis systems, with similar reliability." Also stopped treating cleanup as a periodic project: "The hard part isn't proving that documentation is useful; it's making the documentation cheap enough to create while the work is happening" is the sibling post's framing, and here the work is continuous, prompt-driven maintenance.
- **Coordination and merge strategy.** Five engineers ran prompt variations across repositories, fanned reviews out to the teams that owned each area, and merged small PRs. Guidance: "Start small, review, and expand" — incorporate review feedback into the next prompt before scaling.
- **Memory and context strategy.** Evidence lives in the PR description (config console links, profiling data, rationale); reusable prompts become the durable artifact; "Finding error patterns like this helps us develop prompts that correct for them".
- **Verification and review.** Human review of evidence, not of code volume; "I carefully validated those larger results". One judgment case: Astra flagged a "Permanent" feature flag for human review rather than deleting it, and the eventual removal was estimated at "0.42% CPU saving in the main affected service".
- **Stuck and drift detection.** Not applicable per run; the drift signal is the audit report and measured CPU/CI cost.
- **Human role.** Choose scope, review evidence, validate large results, own prioritization ("some proposals added more complexity than their expected benefit justified, so prioritization and measurement remained an important part of our workflow").
- **Model mix and cost (published table).** Same prompt, same subdirectories (>6,000 files, ~1M LoC across Python, TypeScript, Go, Rust), three configurations: GPT-6 Astra Ultra — $109.06, 142 findings, $0.77/finding; GPT-6.1 Sol Ultra — $15.12, 131 findings, $0.12/finding; GPT-6.1 Sol Medium — $5.27, 86 findings, $0.06/finding. "GPT-6.1 Sol Ultra produced 92% as many findings as GPT-6 Astra Ultra at 14% of the API cost."
- **Published numbers.** "more than 1,400 pull requests, deleting over 800k lines of code" in about two weeks part-time by five engineers; container image 3.31 GB → 1.72 GB (48%); ~400 visual snapshot variants removed; ~30 CI-optimization PRs; median CI completion 10 → 4.5 min and p90 12.5 → 6 min; a 63-test resolver suite 592.6 s → 29.8 s (95% reduction, all tests retained).
- **Colony relevance.** This is the best published template for lesson 8: GC work is ordinary factory work (small PRs, evidence, review), and its prompts are iterated like code as models change.

### 2.10 "Rethinking skills and prompts for GPT-6 Astra" (2026-09-05, secondary date)

Author: Eric Provencher (per third-party coverage). URL: https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra · Date from third-party coverage (explainx, AI Weekly, HN); the page itself is undated.

- **Architecture.** An audit of accumulated agent instructions across three carriers: skills, `AGENTS.md`, and task prompts. The argument is that guidance written for weaker models now actively harms stronger ones.
- **Failure modes and fixes.**
  - Too many skills with long descriptions: "Codex starts shortening their descriptions to fit", so the model sees less of each and routes worse; descriptions can contradict or over-emphasize. Fix: "skill descriptions should be as short as possible while making it clear when the model should use them"; progressive disclosure (a minimal root router pointing to supporting docs/scripts); avoid "elaborate itineraries or recipes".
  - `AGENTS.md` that demands reading a stack of docs "before every edit is excessive for a typo fix"; pointing at docs contextually is fine. Fix: conditional pointers ("Use architecture.md for service boundaries, database.md for schema changes…").
  - Stale encouragement: "Previous models needed encouragement to run tests and check their work. GPT-6 Astra does that on its own, so the same instructions can lead to unnecessary testing."
  - Over-strong decision boundaries: instructions written to stop weaker models from overreaching can make Astra "stop work where you'd actually be happy for it to continue."
  - Tentativeness: "A requirement to stop for review after the first implementation will pull the model toward an earlier stopping point, so check whether that's a decision you actually need to make." Fix: "define completion before starting"; say what to explore and where to stop.
  - Repo skills are shared across contributors using different models: "Guidance that helps Sol or Luna may overconstrain GPT-6 Astra."
- **What they removed or stopped doing.** Long skill descriptions, skill bloat, unconditional "read these docs first" rules, and blanket permission-asking language.
- **Human role.** An explicit house-cleaning ritual per model generation: audit the instructions rather than rewriting them all by hand ("ask GPT-6 Astra to do an audit based on what was discussed in this article").
- **Colony relevance.** Colony problem 4's "spec steering failed 9/9 for 3 weeks" is the same class of bug as an `AGENTS.md` rule that silently no longer binds: instructions must be minimal, testable, and re-validated when the model changes. It also directly supports Colony problem 3: telling an agent to stop for review is itself a cause of premature stops.

### 2.11 "Shell + Skills + Compaction: Tips for long-running agents that do real work" (2026-02-11)

URL: https://developers.openai.com/blog/skills-shell-tips (date per OpenAI's blog index)

- **Architecture.** Three primitives: **skills** ("procedures the model can load on demand" — a `SKILL.md` manifest plus files), a **shell tool** (hosted container or local runtime), and **compaction** (server-side, automatic mid-stream, or the standalone `/responses/compact` endpoint). The stated goal is long-running agents that "handle real knowledge work".
- **Failure modes and fixes.** Skill availability can _reduce_ correct triggering: "Glean saw this directly: skill-based routing initially dropped triggering by about 20% in targeted evals, then recovered after they added negative examples and edge case coverage in descriptions." Fix: descriptions as routing logic ("When should I use this? When should I not?"), negative examples, templates inside skills (free when unused), explicit "Use the `<skill name>` skill" when determinism matters. Long runs without continuity cause restarts; fix: reuse the same container, pass `previous_response_id`, treat compaction as a default primitive. Skills plus open networking is a data-exfiltration path; fix: org-level and request-level allowlists, `domain_secrets`, `/mnt/data` as the artifact handoff boundary.
- **Coordination and merge strategy.** Not applicable.
- **Memory and context strategy.** Compaction as a long-run primitive; container reuse for stable dependencies and intermediate outputs; artifacts written to disk as the review boundary.
- **Model mix and cost.** Not a model comparison; reports Glean's production numbers.
- **Published numbers.** Glean: ~20% initial triggering drop, recovered; Salesforce-oriented skill raised eval accuracy "73% -> 85%" and reduced "time-to-first-token by 18.1%".
- **Colony relevance.** Two mechanisms Colony already needs: artifact-on-disk as the review boundary (workpad/exec plan) and compaction as a first-class part of long implement runs, rather than a last-resort rescue.

### 2.12 "Codex as a platform: build on the open agent harness" (2026-08-19, secondary date)

URL: https://developers.openai.com/blog/codex-as-a-platform · Date from third-party coverage; the page itself is undated.

- **Architecture.** The Codex harness (agent loop, conversation state, tool execution, sandbox/approval policy, streaming) is exposed as an open-source component with three integration layers: `codex exec` for bounded scripts/CI, the Codex SDK for programmatic workflows, and the App Server for applications where "the agent is part of the product itself." The application owns product context, business rules and tools (often via MCP); the harness owns the loop and sandboxed execution.
- **Failure modes and fixes.** Not a failure post; the argument is against forcing all work into "a generic chat window": build the interface around the actual job (operations dashboard, security investigation, support console) and require approval for consequential writes (the Relay example rebooks a shipment only after human approval).
- **What they removed or stopped doing.** The assumption that an agent must live in a chat UI; the assumption that every team should move work into a general-purpose coding assistant.
- **Coordination and merge strategy.** Not applicable.
- **Memory and context strategy.** Thread state and streaming live in the harness; product state stays in the application's system of record.
- **Verification and review.** Human approval at the point of consequential action.
- **Human role.** The human selects context and approves writes; the application supplies the business view.
- **Model mix and cost.** No routing table; one headline harness result: on ARC-AGI-3, "retained reasoning and context compaction raised GPT-5.6 Sol's score from 13.3% to 38.3% while reducing output tokens sixfold" — i.e., harness design can matter more than model choice.
- **Colony relevance.** Direct support for the daimyo direction: keep the agent runtime as a reusable harness and put the _factory_ semantics (work state, policy, approvals) in the surrounding platform. It also cautions against making the session the unit of work.
