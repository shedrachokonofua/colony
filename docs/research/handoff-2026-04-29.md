### #20-followup — Runtime bot bootstrap (the user asked for this, design discussed)

The user's framing: "bootstrap should be a runtime thing". Operator-triggered bootstrap is fine for first-deploy, but at scale Colony should onboard itself when it first sees a project.

**Schema (new migration `1761350000012_provider-bot-credentials.sql`)**:

```sql
CREATE TABLE provider_bot_credentials (
  id text PRIMARY KEY,
  provider text NOT NULL,
  role text NOT NULL,                  -- engine / reviewer / architect / integrator / memory_consolidator
  provider_user_id text NOT NULL,
  ciphertext bytea NOT NULL,           -- encrypted PAT
  granted_by text NOT NULL,            -- actor that triggered bootstrap
  granted_at timestamptz NOT NULL DEFAULT now(),
  rotated_at timestamptz,
  revoked_at timestamptz,
  UNIQUE (provider, role, provider_user_id)
);
GRANT SELECT, INSERT, UPDATE ON provider_bot_credentials TO colony_writer;
```

Encrypt with the same `SecretEncryption` (AES-256-GCM, key from `COLONY_SECRET_ENCRYPTION_KEY`) used for `provider_oauth_connections`.

**`BotCredentialRepository`**: `upsertCredential`, `getCredentialForRole(provider, role, project_namespace)`, `rotateCredential`, `revokeCredential`, `listActive(provider)`.

**`ensureProviderBots({ scope_id })` activity**:

1. Load scope's primary `ProviderProjectRef`.
2. From `config/colony.yaml`'s `agents` map, derive expected roles.
3. For each role, look up `provider_identities` for `(actor: bot:<role>, provider, allowed_namespaces ⊇ project.namespace)`. If found → skip.
4. If any role missing, call `providerAdapter.bootstrap()` with a `BootstrapBotSpec` containing only the missing roles. Persist user IDs to `provider_identities` and PATs to `provider_bot_credentials` (encrypted).
5. Audit `provider.bots.bootstrapped` per role. `provider.bots.failed` on errors → scope to `pending_sync` via the COL-3.3 path.

**Supervisor wiring**: `scopeSupervisorWorkflow` calls `ensureProviderBots` once on first signal/heartbeat after `draft → decomposition_proposed` (or just before `startArchitectRun`). Idempotent — re-runs are no-ops if all roles present.

**Runtime swap-out (the part that _uses_ the per-bot PATs)**: this is the harder part.

The current GitLab adapter is constructed once with a static token in `apps/worker/src/activities.ts::getProviderAdapter()`. Two options:

- **(i) Per-actor adapter factory.** Worker holds a `Map<ActorId, GitLabProviderAdapter>` keyed by role. Activities receive the calling actor and resolve the right adapter. Cleanest but invasive.
- **(ii) Adapter token resolver.** Extend `GitLabProviderAdapter` constructor to accept `token: string | (actor: ActorId) => Promise<string>`. Each request internally resolves. Activities pass the calling actor as a request-scoped option.

I recommend (ii) — minimum surface area change, isolated to one adapter.

**Tests:**

- DB-backed: `ensureProviderBots` provisions missing bots, is idempotent on re-run, audits failures, marks scope pending_sync on bootstrap failure.
- Live: opt-in via `COLONY_LIVE_BOOTSTRAP=1` — provisions a real disposable group + bot users, asserts `provider_bot_credentials` rows + decryption round-trips correctly, then revokes.
