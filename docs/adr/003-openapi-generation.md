# ADR-003: OpenAPI generation

**Status:** Accepted
**Date:** 2026-04-24

## Context

Every Colony HTTP API (`apps/api`, `apps/webhook-dispatcher`, `apps/tool-gateway`) publishes an OpenAPI document so that:

- The Web UI (SvelteKit) can generate a typed client.
- Agents receive JSON Schemas for envelope validation derived from the same source.
- Operators/humans can read an accurate API reference.
- CI can diff API contract changes (COL-0.3a acceptance: "CI fails if generated schemas or OpenAPI artifacts are stale").

Envelope/packet schemas (`design.md` §6, COL-0.5) are defined once in Zod, in `packages/schemas`. They are reused at the HTTP boundary.

## Decision

- **`@hono/zod-openapi`** as the per-service OpenAPI generator. Each route is defined with `createRoute({...})` referencing Zod schemas; `OpenAPIHono` emits the document at `/openapi.json`.
- **`@scalar/hono-api-reference`** serves the human docs UI at `/docs` on every API service.
- **`@scalar/openapi-to-markdown`** produces an `llms.txt` served at `/llms.txt` for agent consumption, mirroring Foundry's pattern.
- **Checked-in artifact:** each service writes its current `openapi.json` into `schemas/openapi/<service>.json` during build. A CI job diffs the regenerated document against the checked-in copy and fails if they disagree — enforcing the "CI fails on stale schemas" acceptance.
- JSON Schema for envelopes (`schemas/envelopes/<name>.v<N>.json`) is produced from the same Zod schemas via `z.toJSONSchema(...)` (Zod 4 native) and checked in.

## Alternatives Considered

- **`zod-openapi` (separate package).** Works with any HTTP layer but duplicates wiring Hono already offers via `@hono/zod-openapi`. No compelling reason since we chose Hono.
- **Hand-written OpenAPI YAML + runtime validators.** Decouples types from runtime validation — classic source of drift. Rejected.
- **`tsoa`.** Decorator-driven OpenAPI from TypeScript types. Adds a build step and a decorator runtime, conflicts with Zod being the schema source.
- **gRPC / Connect / tRPC.** Not the MVP API transport per `design.md` §6. Revisit ADR if transport changes.
- **Generate OpenAPI from TypeBox (previous plan).** Superseded: we chose Zod end-to-end (`design.md` §6).

## Rationale

One schema library (Zod), one HTTP framework (Hono), one generator (`@hono/zod-openapi`) = one source of truth and the least glue. Foundry runs this stack and it works. Scalar renders a pleasant UI with near-zero config.

Checked-in OpenAPI + JSON Schema artifacts give CI something to diff against, give agents a stable pointer that doesn't require booting a service, and give reviewers a reviewable file for contract changes.

## Consequences

- Every API handler is authored with `createRoute({ method, path, request, responses })` referencing Zod — no ad-hoc handlers that bypass OpenAPI generation. A lint rule or convention doc enforces this over time.
- Generated artifacts live in `schemas/` at the repo root and are regenerated by a `schemas:generate` script. Running the script is part of the pre-commit or pre-push path; CI checks staleness.
- Breaking schema changes are visible in the diff against checked-in artifacts — reviewers see the contract change before approving.
- `llms.txt` must be regenerated on every schema change; a deploy-time rebuild is acceptable since it's derived from the OpenAPI doc.

## Revisit When

- `@hono/zod-openapi` stops tracking Zod or OpenAPI versions we need.
- We adopt a non-HTTP transport for inter-service traffic; OpenAPI may stop being the right contract format.
- Checked-in artifacts become too large to review — at which point we push the "diff against deployed" model to a contract-testing service instead.
